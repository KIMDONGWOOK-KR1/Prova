# 요청 해석 재현율 — 선택 넓히기 전후 (2026-08-22, Qwen2.5-7B-Instruct-AWQ)

측정 도구 `scripts/probe_request_selection.py`. 수치는 "정답 집합을 빠짐없이 담은
요청 수 / 요청 수" 다. 여유분(정답 밖 케이스)은 실패가 아니다.

## 순서 — 무엇을 보고 무엇을 고쳤는가

1. 홀드아웃 A(9건, 08-19·20)의 빠뜨림 3건(흐름·건수·정렬)을 보고 **선택 넓히기**
   (`selector.widen_selection`, R1 묶음 완성 · R2 흐름 보강 · R3 종류 낱말)를 설계했다.
   → 이 시점부터 A 는 튜닝 세트다.
2. 구현 **전에** 홀드아웃 B(10건 + 무관 요청 2건, 커밋 `4158fbd`)를 굳히고 기준선을 쟀다.
3. 구현 후 A 와 B 를 다시 쟀다. **B 를 보고 넓히기 규칙은 고치지 않았다.**

## 결과

| 세트 | 넓히기 전 | 넓히기 후 | 여유분 합 |
|---|---|---|---|
| 튜닝 세트 (10) | 9/10 (08-19) | — 재측정 안 함 | |
| 홀드아웃 A (9) — 이제 튜닝 세트 | 6/9 | **9/9** | |
| **홀드아웃 B (10) — 보고용** | 9/10 | **9/10** | 12 → 12 |

넓히기는 A 의 빠뜨림 3건을 전부 채웠지만 **B 에서는 발동할 자리가 없었다** — B 의
건수·흐름 요청은 7B 가 처음부터 묶음을 다 골랐다. 여유분이 같으므로 정밀도 손실도 0 이다.
정직한 보고 수치는 **B 9/10** 이고, 넓히기의 효과는 "A 모양의 실패를 코드가 막는다" 까지다.

B 의 남은 빠뜨림 1건:

```
"주문조회 화면 전반적으로 점검 부탁" → valid·sorted·sum·seedcount 는 골랐는데
  orders-precondition-guard 를 뺐다. 가드(비로그인 진입)를 화면의 일부로 보지 않는다.
```

넓히기 규칙 셋 중 어느 것도 닿지 않는 모양이다(화면 지목 + 종류 누락). 방어선은 기존과
같다 — 계획 화면의 "'주문 조회' 화면은 5건 중 4건만 실행됩니다" 경고(named + partial).
B 를 보고 고치면 B 도 튜닝 세트가 되므로 고치지 않았다.

## 부수로 잡은 코드 결함

무관 요청 "배송 조회가 되는지 봐줘" 가 어휘 검사를 통과해 orders-valid 1건을 골랐다.
화면 이름 '주문 조회' 를 쪼갠 **'조회'** 조각이 매치된 것 — 08-19 의 '확인' 과 같은 모양.
`_SPLIT_STOPWORDS` 에 '조회' 를 더했다. 홀드아웃을 보고 고친 것이므로 B 의 거부 2건은
더 이상 일반화 증거가 아니다.

원본 출력: 기준선·재측정 로그는 스크래치패드에만 있고 저장소에는 이 표만 둔다.

## 추기 (2026-08-24) — 집합 정의 갱신

날짜 필터 작업으로 orders 화면의 케이스가 6건 → 14건이 됐다(labels 1 + filter 8).
B 의 "화면 지목(전 종류)" 기대 목록에 `orders-labels`·`orders-filter` 를 기계적으로
추가했다 — '전 종류' 의 정의가 커진 데 따른 갱신이지 판정 기준 변경이 아니다.
다만 **갱신 후의 수치는 위 B 9/10 과 1:1 비교할 수 없다.** 재측정은 하지 않았다 —
다음 실측정(실물 기획서) 때 함께 잰다.
