# 우리가 안 만든 웹앱 — 로그인 밖의 화면 셋 (2026-09-23 측정, 09-27 마감)

## 왜 쟀는가

첫 관통([external-sites-2026-09-23.md](external-sites-2026-09-23.md))은 로그인 화면만 봤다.
그때 남긴 한계가 "회원가입·검색·표 화면은 재지 않았다" 였다. 입력란이 많고, 한 번 쓰면
끝나는 데이터가 있고, 오류를 표시하는 방식이 제각각인 화면을 골랐다.

## 무엇을 쟀는가

| 사이트 | 화면 | 우리 SUT 에 없던 모양 |
|---|---|---|
| practice.expandtesting.com | `/register` | 사이트가 공개 테스트 케이스 4개를 둔다. 오류가 `div.alert-danger`. 가입한 아이디는 다시 못 쓴다 |
| parabank.parasoft.com | `/parabank/register.htm` | 11칸 가입 폼이 `<td><b>First Name:</b></td><td><input>` 표 레이아웃 — `<label>` 이 없다. 오류가 `span.error`. Confirm 칸 하나에 문구가 둘 |
| automationexercise.com | `/products` (검색) | 검색 버튼이 글자 없는 아이콘. 광고·분석 스크립트가 콘솔 오류를 계속 낸다 |

방식은 첫 관통과 같다 — 기획서는 사이트가 **보여 주는 동작만** 옮겨 적었고, S1 은 실물
Qwen2.5-7B-AWQ, 요소 탐지는 1차 경로(VLM 없음). 기획서·리포트는 저장소에 넣지 않고,
드러난 모양을 테스트에 고정했다.

잘 된 것: expandtesting 은 올바른 아이디로 **6/6**, 공개 테스트 케이스 넷과 전부 일치했다.
예시 아이디에 `_` 를 넣었더니 사이트의 **문서에 없는 규칙**("Invalid username…")이 떠
'기획서와 다름' 으로 보고됐다 — 이건 도구가 맞게 짚은 기획-구현 불일치다.

## 고친 방법과 결과

| # | 고친 곳 | 결과 |
|---|---|---|
| A | `_classify` 는 콘솔 오류로 분류를 바꾸지 않는다. 콘솔 오류는 근거(`console_errors`, 앞 5건)와 사유 끝 "(참고: 콘솔 오류 N건 — 판정과 무관할 수 있음)" 으로. HTTP 오류로 화면을 못 연 것은 여전히 `page_error` (설계 판단 22) | 분류 규칙 변경 — 전후 건수는 따로 재지 않았다 |
| B | `_ERROR_AREA_JS` — `role=alert` + `.alert-danger` + class·id·data-test 에 error 가 든 요소. 보이는 것·글자 있는 것만, 겹치면 가장 안쪽 | 정상 케이스 FAIL 사유에 "· 화면 오류: …" |
| C | `dom_locator._table_label_locator` — 라벨 칸 다음 칸의 입력 요소(`:`·`*` 무시). 입력 유형에서 role 앞. '라벨로 요소 찾기' 케이스는 이것을 **연결 안 됨**으로 보고한다 | parabank 미탐지 12 → **11 통과** |
| 따옴표 | `text_utils.find_quoted` — 같은 짝으로만 닫고, 길이는 짝을 맞춘 뒤 거른다. 성공 문구 한도 40 → 200 | 61자 문구까지 확인(약한 확인 해소) |
| 빈 칸 문구 | 규칙 있는 요소의 에러 문구를 필수 케이스에 빌려 쓰지 않는다(모르면 '에러가 떴는가' 로 격하). 기획서 2-1 절의 `비어 있으면 "…"` 을 코드가 읽어 `UIElement.required_message` 에 — LLM 스키마에는 없다 | parabank **12/13** — Confirm 필수가 정확한 문구로 PASS. 남은 1건은 라벨이 입력란과 연결되지 않았다는 접근성 지적(의도된 FAIL) |
| D | 예시값의 `{고유}` 를 실행 직전 케이스마다 소문자·숫자 8자로 바꾼다(`unique_token.fill_unique`). 계획에는 토큰이 남아 `--resume` 도 새 값을 쓴다 | expandtesting **연속 2회 모두 6/6** (스크린샷에 `prova-f30392ee`) |
| E | 경고를 필수 입력에만 | 우리 픽스처 9종에는 원래 한 건도 없었다 — 판정 변화 없음 |

우리 픽스처 9종의 케이스 196건은 '빈 칸 문구' 수정 전후 기대값이 글자까지 같았다
(mock 백엔드로 전부 뽑아 비교). 풀스위트는 마지막 수정 후 **1271 passed**.

## 한계

- 사이트 셋, 화면 하나씩이다. 표를 **보여 주는** 화면(목록·주문 내역)은 아직 재지 않았다.
- A 의 효과는 분류 규칙으로 고쳤고, automationexercise 에서 결함이 숨었던 건수를 전후로
  세지는 않았다.
- D 는 케이스 사이에 고유값을 나누지 않는다 — 한 케이스에서 가입하고 다른 케이스에서 그
  계정으로 로그인하는 모양은 표현할 수 없다. 치환된 값의 길이(8자)는 실행 전 예시값 검사가
  보지 못한다.
- 외부 사이트는 바뀐다. 회귀 확인은 고정한 모양으로 한다
  (`tests/test_error_areas.py`·`test_table_cell_label.py`·`test_find_quoted.py`·
  `test_required_per_element.py`·`test_unique_token.py`·`test_table_header_match.py`).
