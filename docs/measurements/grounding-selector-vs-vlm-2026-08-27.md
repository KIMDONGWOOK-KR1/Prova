# 탐지 경로 비교 — selector(1차) vs VLM(2차) (2026-08-27)

명세서 §9 가 요구한 "selector 방식 vs VLM 방식의 **탐지 성공률·처리 속도** 별도
비교(하이브리드 근거)" 다. `scripts/eval_selector_speed.py` 의 출력을 그대로 옮겼다.

## 방법 — 같은 시험지 50개

`fixtures/iou/dataset.json` 은 화면·목표 라벨·정답 상자가 굳어 있는 시험지다.
2차 경로는 2026-08-22 에 이 위에서 채점됐고 결과가 좌표·신뢰도·호출 시간까지
`vlm-iou-qwen-vl-2026-08-22.json` 에 남아 있다. 같은 50개 항목을 라이브 화면에서
1차 경로(`s3_grounder.ground` — 파이프라인이 실제로 부르는 그 함수)로 쟀다.

**모집단이 같은지는 코드가 확인한다.** 처음에 1차 경로만 43개로 재고(좌표 조작
종류만) 2차의 50개 숫자와 나란히 놓을 뻔했다 — 그 제외는 정체 대조 재생(08-25)의
범위였지 IoU 채점(08-22)의 범위가 아니었다. 모집단이 다른 두 수치는 비교가 아니라
착시이고 표에서는 보이지 않으므로, `check_same_population` 이 어긋나면 멈춘다.

'찾았다' 의 정의는 두 경로가 **함께 답할 수 있는 질문**으로 맞췄다 — 적중(중심이
요소 안) + 관문 통과. IoU 는 1차 경로에 없는 개념이라 쓸 수 없다.

페이지 로드는 탐지가 아니므로 같은 화면의 항목은 한 번 연 페이지 위에서 연달아
쟀다. 섞으면 1차 경로가 실제보다 느리게 나온다.

## 결과 (시험지 536392d2154b — 13화면 50항목)

| 지표 | selector (1차) | VLM (2차) |
|---|---|---|
| 탐지 성공률 | **38/40 = 95.0%** | 36/40 = 90.0% |
| 오탐 (없는 것을 찾았다고) | **0/10 = 0.0%** | 7/10 = 70.0% |
| 호출 시간 (평균) | **15.1ms** | 737ms |
| 호출 시간 (최대) | 359.3ms | 1678ms |
| 평균 배수 | 1× | **49×** |

## 읽는 법

**1차 경로가 놓친 2건이 이 표의 핵심이다.** 둘 다 `nolabel` 화면의 '검색' —
아이콘만 있고 접근성 이름이 없는 버튼이다. 즉 1차 경로의 실패는 흩어진 잡음이
아니라 **한 가지 모양에 몰려 있고, 그 모양이 2차 경로를 만든 이유** 그대로다.
2차 경로는 `nolabel` 에서 1 PASS / 9 FAIL 을 9 PASS / 1 FAIL 로 바꾼다(노트 13).

**그래서 selector-first 는 취향이 아니라 측정 결과다.** 1차가 더 정확하고(95% vs
90%), 오탐이 없고(0% vs 70%), 49배 빠르다. 2차를 먼저 부를 이유가 하나도 없다.
2차는 1차가 **닿지 못하는 자리**에서만 값을 한다.

**오탐 0% 와 70% 의 차이가 가장 크다.** 1차 경로는 없는 요소를 지어낼 수 없다 —
DOM 에 없으면 없다. 2차 경로는 없는 요소의 좌표를 자신 있게(전부 신뢰도 0.8 이상)
답한다. 그 7건은 실행 관문(빈 곳 + 정체 대조)이 전부 막지만, 막는 장치가 필요하다는
사실 자체가 두 경로의 성질 차이다.

**속도 49배는 자리를 정한다.** 1차 경로는 케이스마다 여러 번 불러도 무해하지만,
2차는 한 번 부를 때마다 스크린샷 + 원격 호출이다. 탐지 실패 뒤의 보정(self-healing)
에서만 부르는 지금 구조가 그 비용에 맞다.

## 한계

- **두 수치는 같은 날이 아니다.** 2차는 2026-08-22 원격 GPU(MIG 1g.10gb) + SSH
  터널, 1차는 2026-08-27 로컬 브라우저다. 다만 **그게 각 경로가 실제로 도는
  조건**이라 운영 관점의 비교로는 이 편이 맞다. 같은 날로 맞추려면 VL 을 다시
  올려야 하고(7B 를 내려야 한다), 저장된 측정에는 시점이 붙어 있다.
- 1차 경로 수치는 저장하지 않았다. 이 측정은 GPU 없이 몇 초면 다시 돌아간다 —
  2차 결과를 굳혀 둔 이유(비싸고 재현이 어렵다)가 여기엔 없다.
- 시험지 범위는 4화면 + `nolabel`(login·signup·search·find_account)이다. 실물
  화면에서 1차 경로가 어디서 막히는지는 기획서를 받아 봐야 안다.

**놓친 2건은 여전히 `nolabel` 의 아이콘 전용 '검색' 둘뿐이다.** 항목이 50%
늘고 표·날짜·목록이 새로 들어왔는데도 실패는 한 모양에 그대로 몰려 있다. 위

`eval_selector_speed.py` 는 두 점수의 `dataset_id` 가 다르면 **비교표를 만들지

**-> 2026-08-28 에 채점했다. 아래 추기가 새 시험지의 비교표다.**

### 재면서 오탐을 3건 만들 뻔했다

넓힌 직후 1차 경로 점수가 **95% → 63.3%, 오탐 0 → 3건**으로 떨어졌다. 새 화면이
어려워서가 아니었다 — 채점 스크립트가 세션 없이 경로만 열어서 **상품등록·주문조회가
통째로 로그인 화면으로 리다이렉트**됐고, 거기 있는 '비밀번호' 를 '없는 요소를
찾았다' 로 집계했다.

도구 결함이 탐지 실패로 둔갑하는 모양이다. 그래서 고치는 방식을 시험지 쪽에 뒀다 —
**항목이 '이 화면에 어떻게 닿는가'(`login`)를 들고 다니고** 채점하는 쪽이 그것을
쓴다. 채점 스크립트마다 로그인 절차를 따로 적으면 한쪽만 고쳐지는 날이 온다.


## 다시 재려면

```powershell
uv run uvicorn sut.app:app --port 8100 --reload --reload-dir sut   # 별 터미널
uv run python scripts/eval_selector_speed.py --md
```

2차 경로까지 다시 재려면 VL 을 올려야 한다(7B 를 내린다 — `docs/CHEETAH_SETUP.md`).

```powershell
uv run python scripts/eval_vlm_iou.py --vlm http://localhost:8001/v1 --vlm-model qwen-vl `
    --out docs/measurements/vlm-iou-qwen-vl-<날짜>
uv run python scripts/eval_selector_speed.py --vlm-result docs/measurements/vlm-iou-qwen-vl-<날짜>.json --md
```

### 결과 (시험지 3dd2243cb229 — 18화면 74항목)

'찾았다' 의 정의는 위와 같다 — 적중 + 관문 통과. IoU 기준으로는 2차가

### 결론은 바뀌지 않았고, 간격은 벌어졌다

### 옛 화면의 점수가 한 자리도 안 변했다

옛 13화면만 떼면 `21/40 = 52.5%` · 적중 `36/40 = 90.0%` · 오탐 `7/10 = 70.0%` 로,

이건 두 가지를 동시에 말한다 — 채점이 재현되고, 데이터셋 재생성이 화면을 바꾸지
않았다. 그래서 전체 하락을 '모델이 나빠졌다' 로 읽으면 틀린다. **모집단이 넓어진
것이지 계측이 흔들린 것이 아니다.**

이 확인이 없었으면 46.7% 와 52.5% 를 나란히 놓고 회귀를 의심했을 것이다. 시험지를
넓힐 때 옛 항목을 그대로 품게 한 것이 여기서 값을 했다.

### 어디서 떨어지는가

주문조회가 가장 나쁘다 — `orders-list` 1/5 · `orders-empty` 0/3 · `table-orders` 1/4.
같은 모양의 입력이 나란히 있고(시작일/종료일), 목록·합계는 눈에 보이는 테두리가
없다. **좌표를 통째로 놓친 항목(IoU 0.00)이 처음 나왔다** — 지금까지의 실패는
대개 상자가 헐거운 것이었다. 자세한 것은 `vlm-iou-qwen-vl-2026-08-28.md`.

### 한계

- 여전히 **같은 날이 아니다** — 1차는 로컬 브라우저, 2차는 원격 GPU + SSH 터널.
  각 경로가 실제로 도는 조건이라 운영 비교로는 이 편이 맞다.

  붙기 전에 굳었고, 2차는 그 스크린샷을, 1차는 라이브 화면을 봤다. 비교한 요소는

  재채점과 같은 GPU 창에서 해야 한다(`identity-guard-replay-2026-08-28.md`).
- 이 표의 오탐 9건은 **관문 앞의 성질**이다. 관문 뒤에 무엇이 남는지는 08-25 의

## 추기 (2026-08-31, 같은 날 늦게) — 타이머가 화면 여는 시간을 세고 있었다

위 표들의 1차 경로 시간에는 **`page.goto` 와 로그인이 들어 있었다.** `evaluate_selector`
의 타이머가 `locate` 전체를 감쌌기 때문이다.

증거는 값에 그대로 남아 있었다 — 같은 화면 안에서 첫 항목만 유독 느렸다.

    게이트 화면 첫 항목   orders-list 시작일 124.9ms · product-empty 상품명 116.9ms
    비게이트 첫 항목      find-empty 이메일 23.7ms · nolabel-results 검색어 31.5ms
    같은 화면 나머지      2~7ms

시험지를 넓히며 로그인 뒤 화면이 다섯 개 생기자 그 몫이 커졌다.

### 왜 고치는가 — 방향이 아니라 정의 때문이다

**고치면 1차 숫자가 좋아진다.** 결론이 이미 selector-first 이므로, 유리한 쪽으로
지표를 움직이는 것과 구별되는 근거가 필요하다. 근거는 하나뿐이다 — **두 경로가
같은 것을 재는가.**

2차 경로의 `elapsed_ms` 는 **모델 호출만** 잰다. 저장된 그림을 채점하므로 페이지
로드가 아예 없다. 그러니 1차에만 로드를 얹은 표는 1차에 **불리하게** 기울어
있었다. 고치는 것은 1차를 봐주는 것이 아니라 기울기를 없애는 것이다.

화면을 여는 일은 `prepare` 로 나갔고 타이머는 `locate` 만 감싼다. 탐지 성공률과
오탐은 손대지 않았다(61/63 · 0/14 그대로) — 시간만 달라져야 맞다.

### 결과 (시험지 8f3de91023aa · 77항목)

| 지표 | selector (1차) | VLM (2차) |
|---|---|---|
| 탐지 성공률 | **61/63 = 96.8%** | 57/63 = 90.5% |
| 오탐 (없는 것을 찾았다고) | **0/14 = 0.0%** | 10/14 = 71.4% |
| 호출 시간 (평균) | **6.8ms** | 839ms |
| 호출 시간 (최대) | 22.9ms | 2465ms |
| 평균 배수 | 1× | **124×** |

    평균 19.7ms -> 6.8ms      최대 385.2ms -> 22.9ms      배수 43x -> 124x

최대값의 변화가 가장 크다. 385ms 는 통째로 페이지 로드였다.

### 남은 기울기

게이트 화면의 첫 항목이 아직 ~13.8ms 로 같은 화면의 나머지(~6ms)보다 높다. 갓
로드된 페이지에서의 첫 `ground()` 호출이라 그렇다. 100ms 대의 편향은 사라졌지만
0 은 아니므로, 평균 6.8ms 는 **약간 높게 잡은 값**이다. 낮춰 적을 이유는 없다.
