# 우리가 안 만든 웹앱 — 표를 보여 주는 화면 셋 (2026-09-27 측정, 09-28 마감)

## 왜 쟀는가

스파이크 2([external-sites-2-2026-09-27.md](external-sites-2-2026-09-27.md))가 남긴 한계가
"표를 **보여 주는** 화면(목록·주문 내역)은 아직 재지 않았다" 였다. 우리 SUT 의 주문조회는
우리가 만든 마크업이라 `aria-label` 이 붙은 목록, '테스트 주문 데이터' 라는 절 제목, 날짜
최신순 정렬, '합계' 라벨을 전제로 코드가 자랐다. 그 전제가 남의 화면에서 어떻게 깨지는지 봤다.

## 무엇을 쟀는가

| 사이트 | 화면 | 우리 SUT 에 없던 모양 |
|---|---|---|
| the-internet | `/tables` | 같은 머리글의 이름 없는 `<table>` 두 개 |
| demoqa | `/webtables` | 검색어를 치는 즉시 거르는 표 — 조회 버튼이 없다 |
| saucedemo | `/inventory.html` | 아이디(Username)로 로그인하는 전제, `div` 카드 목록, 정렬 select, **정상 화면에 HTTP 404** |

방식은 스파이크 2 와 같다 — 기획서는 사이트가 보여 주는 동작만 옮겨 적었고, 기획서·리포트는
저장소에 넣지 않았다. 처음 잴 때 S1 은 실물 Qwen2.5-7B-AWQ, 수정 뒤 재확인 일부는 Qwen3.5-4B
(같은 날 기본 모델 전환, [model-compare-qwen35-4b-2026-09-28.md](model-compare-qwen35-4b-2026-09-28.md)).

**처음 결과의 실패 중 진짜 결함은 0건이었다.** 전부 도구 쪽 가정이 깨진 것이다.

## 찾은 것 (위험한 순)

| # | 모양 | 무엇이 잘못됐나 | 방향 |
|---|---|---|---|
| 1 | 이름 없는 표 | 기대 건수가 있는데 목록을 이름으로 못 찾으면 '기획서와 다름'. 안내 문구 케이스도 "요소를 찾지 못함" 만으로 같았다 | 오분류(오탐) |

확인할 입력이 없다는 사실은 커버리지 경고로 정직하게 보고됐다.

## 고친 방법과 결과

| # | 고친 곳 | 결과 |
|---|---|---|
| 1 | `CollectionCount.lookalikes`(목록을 못 찾았을 때 화면의 이름 없는 표·목록 수) → `_classify` 가 있으면 탐지 실패로. 목록 비슷한 것이 없으면 예전처럼 결함 — 결과 0건이라 목록을 안 그린 구현(SUT 검색 bad)이 숨지 않게 (`414cd63`) | '기획서와 다름' → 탐지 실패 |
| 3 | 실패 조건 '비어 있음' 행의 주인을 가린다 — 라벨이 정확히 하나면 그 칸, 일반 문장이면 화면 공통, 모르면 쓰지 않고 경고. 모델이 그 문구를 화면 공통으로 내면 지운다 (`317c613`, 일부만 옮겨 적은 것도 지우게 `f0a6ac6`) | saucedemo 로그인 5/5 |
| 2 | 예시 표의 입력 열은 채울 수 있는 요소(입력·선택·체크·날짜)만 인정. 건수만 적은 예시 표도 읽는다 (`f08e5b7`) | 데이터 표 오독 0 |
| A | 0건 기대인데 이름 없는 표·목록이 보이면 통과가 아니라 "0건인지 확인할 수 없습니다" (`f398046`) | 빈 통과 0 |
| 4a | 절 제목을 '테스트 ○○ 데이터' 로 넓힘 (`92a1886`) | |
| 4b | 계정 표는 2열이고 둘째가 비밀번호면 인정, 로그인 화면은 ID 가 없으면 비밀번호 칸이 있는 **유일한** 화면, 아이디 칸은 비밀번호가 아닌 **유일한** 입력란. 전제 스텝은 로그인 화면 명세로 찾는다 (`bfe7dfe`) | saucedemo 전제 5스텝 성공 |

| 5b | 같은 태그·클래스의 보이는 형제 3개 이상, 각자 하위 요소 3개 이상, nav·header·footer 밖이면 목록 비슷한 것으로 센다 | saucedemo 상품 목록 1개로 셈, 빈 장바구니 화면(메뉴만) 0 |
| B | 처음 가정("load 이벤트를 기다린다")이 틀렸다 — goto 는 이미 domcontentloaded 까지만 기다리고, 재 보니 dcl 과 load 가 같았다. 느린 것은 첫 접속(8초, 이후 2.7초 — Heroku 가 잠든 서버를 깨우는 시간). 페이지 열기에 요소 조작과 따로 **30초** 제한을 둔다(`execution.navigation_timeout_ms`) | 분류는 원래 정직했다(시간 초과) — 불필요한 실행 문제를 줄인다 |

**5 의 첫 설계는 틀렸다.** 처음에는 "404 인데 본문에 글자가 있으면 계속, 요소를 못 찾으면
페이지 오류" 였다. SUT 판정 비교에서 1960줄 중 **134건**이 페이지 오류 → '기획서와 다름' 으로
바뀌었다 — 우리 SUT(FastAPI)는 없는 화면에 JSON `{"detail":"Not Found"}` 를 주는데, 그 글자를
'화면이 그려졌다' 로 읽었다. 오탐 방향이다. HTML 일 때만 계속하고, 계속한 뒤의 실패는 전부
페이지 오류로 두도록 좁혔다. 대가는 404 를 주는 사이트의 진짜 결함도 '실행 문제' 로 분류된다는
것 — 사유에 판정 내용이 그대로 실려 결함이 사라지지는 않는다. 오탐보다 미탐이 낫다.

모든 수정은 SUT 판정 비교(`scripts/dump_verdicts.py`, 기획서 9 × 변형 10 = 1960줄)와 픽스처
케이스 비교(`scripts/dump_cases.py`, 196개)가 수정 전과 같음을 확인한 뒤 올렸다.

## 한계

- 4c(정렬 기준·합계 표기의 다양성)는 보류했다. 날짜 내림차순·쉼표 정수가 아닌 정렬·합계는
  케이스가 **만들어지지 않고 경고만** 남는다 — 조용한 누락은 아니지만 검증도 아니다.
- 5b 의 반복 구조 판별은 휴리스틱이다. 카드 모양의 반복(추천 상품·광고 묶음)이 있는 화면에서는
  목록을 안 그린 결함이 '탐지 실패' 로 숨을 수 있다.
- 5 는 404 만 다룬다. 다른 4xx 로 앱 화면을 주는 호스팅은 여전히 바로 페이지 오류다.
- 외부 사이트는 바뀐다. 회귀 확인은 고정한 모양으로 한다
  (`tests/test_not_found_classification.py`·`test_scenario_tables.py`·`test_seed_heading.py`·
  `test_precondition_username.py`·`test_spa_404.py`·`test_navigation_timeout.py`).
