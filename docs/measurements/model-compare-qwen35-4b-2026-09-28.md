# 모델 비교 — Qwen3.5-4B 한 대 vs 7B + VL-3B 두 대 (2026-09-28)

## 왜 쟀는가

지금 GPU 조각(A100 MIG 1g.10gb, 9.5GiB)은 모델 둘을 **시간분할**로 쓴다 — 추출(S1)은
Qwen2.5-7B-Instruct-AWQ, 요소 탐지(S3 2차 경로)는 Qwen2.5-VL-3B-Instruct-AWQ. 둘은
동시에 올라가지 않는다(`docs/cheetah-setup.md`). 2026년 3월에 나온 Qwen3.5 소형 모델은
이미지를 기본으로 읽으므로, **한 모델이 두 일을 다 하면** 교체 운영이 사라진다.

## 후보를 어떻게 좁혔나

| 후보 | 결론 | 이유 |
|---|---|---|
| Qwen3.5-9B (4bit) | 제외 | 가장 작은 4bit 판(cyankiwi)도 **8.45GiB**. 어휘 24.8만 개의 임베딩·출력층(각 1.89GiB)이 양자화되지 않는다. 9.5GiB 조각에 KV 캐시 자리가 남지 않는다. 공개 자료의 "4bit 약 6GB" 는 틀렸다 — 파일 헤더를 직접 읽어 확인했다 |
| **Qwen3.5-4B (4bit)** | 측정 | `cyankiwi/Qwen3.5-4B-AWQ-4bit`(compressed-tensors) 3.76GiB. 적재 3.91GiB, KV 캐시 2.8GiB(7.5만 토큰) |
| Qwen3.8 | 제외 | 공식 소형이 없다(최소 27B). 9B 는 비공식 증류판 |
| Gemma 4 E4B·12B | 보류 | 12B 는 조각에 빠듯하고 E4B 는 4B 와 겹친다 |

서버 vLLM 0.24 가 `Qwen3_5ForConditionalGeneration` 을 지원한다(레지스트리 확인).

## 결과

같은 시험지·같은 코드로 모델만 바꿨다. 7B 기준값은 같은 날 다시 쟀다.

| 지표 | 지금 (7B / VL-3B) | Qwen3.5-4B |
|---|---|---|
| S1 골든 (`test_s1_golden.py`) | 105/105 | 103/105 |
| 픽스처 케이스 196개 (`dump_cases.py --llm vllm`) | 정답(mock)과 동일 | **7B 와 동일** |
| 흔들림 (같은 모델 두 번) | 0줄 | 0줄 |
| 탐지 성공률 (IoU≥0.5) | 36/63 = 57.1% | **51/63 = 81.0%** |
| 적중률 (중심이 요소 안) | 57/63 = 90.5% | 52/63 = 82.5% |
| 오탐 (없는 것을 찾았다고) | 10/14 = 71.4% | **1/14 = 7.1%** |
| 평균 IoU | 0.504 | 0.724 |
| 호출 시간 | 골든 155초 · 탐지 평균 839ms | 골든 178초 · 탐지 평균 1247ms |

VL-3B 수치는 `vlm-iou-qwen-vl-2026-08-31.md`(같은 데이터셋 `8f3de91023aa`), 4B 수치는
`vlm-iou-qwen35-4b-2026-09-28.md`.

- 골든 실패 2개는 같은 원인 — 회원가입 '약관 동의' 의 `error_message` 를 비웠다. 빈 칸
  문구는 코드가 기획서에서 읽어 채우므로(`required_message`) 케이스에는 영향이 없었다.
- 탐지 약점은 주문조회 화면이다(`orders-list` 2/6, `table-orders` 1/5) — 상태 select·합계·
  표 안의 요소.
- 케이스 196개가 같다는 것은 **약한 시험**이다. 픽스처 기획서는 코드가 표를 거의 다
  읽으므로 7B 도 정답과 한 줄도 다르지 않다. 모델 차이는 코드가 못 읽는 문서에서 난다
  (아래).

## 드러난 것 두 가지 — 둘 다 모델을 바꾸기 전에 고쳐야 한다

### 1. 좌표 규약이 섞인다

0~1 상대값을 달라는 프롬프트에 4B 는 한 화면 안에서도 `[0.36, 0.44, …]` 와
`[365, 532, …]`(0~1000)를 섞어 냈다. 기존 규칙은 1 보다 크면 픽셀로 보고 1280×800 으로
나눠 365 → 0.285(정답 0.367)를 만들고, **그 값이 화면 안이라 `is_sane()` 을 통과한다.**

| 좌표 해석 | 탐지 성공률 | 적중률 |
|---|---|---|
| 기존 (`pixel`) | 12/63 = 19.0% | 13/63 = 20.6% |
| `norm1000` (0~1000 을 명시하고 전부 1000 으로 나눔) | 51/63 = 81.0% | 52/63 = 82.5% |

`QwenVLClient(coords="norm1000")` 로 고쳤다. 기본값(`pixel`)의 프롬프트는 바이트 단위로
예전과 같다.

### 2. 추출 스키마가 생략을 허용한다

`probe_s1_robustness.py`(훼손 6종)에서 표 머리글을 바꾼 기획서와 표를 산문으로 쓴
기획서 — **코드가 표를 못 읽어 모델만 읽는 경우** — 에 4B 는 요소 0개를 냈다. 응답이
`{"screen_id", "screen_name", "url_path", "precondition"}` 뿐이었다. `ScreenSpec` 의
`elements` 는 기본값이 있어 스키마상 선택이고, 정형 출력은 그 생략을 그대로 허락한다.

`elements` 를 필수로 둔 스키마로 다시 부르자 같은 4B 가 요소 3·규칙 4·안내 2 를 7B 와
똑같이 읽었다. **구멍은 7B 에도 있다** — 지금까지 우연히 생략하지 않았을 뿐이다.
그래서 모델 교체와 별개로 먼저 고쳤다(`extractor.EXTRACTION_REQUIRED`).

고치면서 하나 더 나왔다. 키를 필수로 두자 **7B** 가 주문조회 '상태' select 에 선택지를
이어 붙인 `pattern` 을 지어내 골든 하나가 깨졌다. 필수 필드를 셋 중 무엇 하나로 바꿔도
같았다 — 스키마가 조금만 바뀌어도 흔들리는 경계 항목이다. 선택·체크 요소의 문자 규칙은
S2 가 이미 무시하므로(`NON_TEXT_TYPES`) S1 에서 버리고 알리게 했다
(`_drop_non_text_constraints`). 그 뒤 7B 골든 105/105, 케이스 196개 동일.

## 운영 메모

- 가중치를 `hf download` 로 받으면 파드에서 멈췄다(45초에 20MB). `curl -L -C -` 는
  초당 5~7MB. 메모리에 적힌 증상 그대로다.
- `pkill -f "hf download"` 를 ssh 명령 안에서 쓰면 그 명령줄 자신도 패턴에 걸려 세션이
  죽는다. `"[h]f download"` 로 쓴다.
- 기동 시 컴파일에 약 7분(7B 는 1~3분).
- `serve_vllm.sh` 에 `QUANT` 를 두었다 — compressed-tensors 형식에 `awq_marlin` 을 강제하면
  기동이 실패한다. `QUANT=` 로 비우면 vLLM 이 고른다.
- 4B 는 **공식판이 아닌 커뮤니티 양자화**다. Qwen 공식 4bit 판은 없다(2026-09-28 기준).

## 남은 것 (채택 전에)

1. 4B 로 훼손 6종을 다시 잰다 — 이번 수정 뒤에도 요소를 채우는지.
2. 외부 사이트 기획서(스파이크 2·3)를 4B 로 다시 돌린다 — 픽스처 밖 문서에서의 차이.
3. 기본 모델 전환 — `configs/default.yaml`, `QwenVLClient` 기본 규약, 골든 테스트의
   '다른 모델 서빙 중' 가드 문구.
