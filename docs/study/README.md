## 왜 이 순서인가

1학년에게 처음부터 "이 모델을 ~한 원리로 ~한 코드를 써서 ~하게 씁니다" 로 들어가면

> **우리 프로젝트를 먼저 이해한다 → 그 안에서 모델이 무슨 역할을 하는가 →
> 그 역할을 하려면 어떤 종류의 AI 가 필요한가(분류) → 그 분류의 대표적 예시 →

### 프로젝트를 5분에 (설명)

기획자가 "비밀번호는 8자 이상, 대문자 1자 이상" 이라 썼는데 개발자가 대문자 검사를

코드가 바뀌면 처음부터 다시.

**Prova 는 기획서를 읽고 규칙마다 그 규칙만 어기는 값을 만들어, 진짜 크롬을 열어
넣어 보고, 기획서가 지정한 에러가 뜨는지 본다.**

### 팀장 시연 (15분)

`good`(기획서를 지킨 구현)과 `bad`(검증을 일부러 빼먹은 구현)에 같은 기획서로 돌린
리포트를 나란히 연다. 두 앱의 **HTML 은 완전히 같고 검증 로직만 다르다** — 변수를
하나만 두는 것.

```powershell
# 팀장 화면. 학생은 보기만 한다
uv run uvicorn sut.app:app --port 8100 --reload --reload-dir sut
uv run prova run --pdf fixtures/specs/login_spec.pdf --url http://localhost:8100/good --backend mock
uv run prova run --pdf fixtures/specs/login_spec.pdf --url http://localhost:8100/bad  --backend mock
```

**`good` 10/10 PASS · `bad` 4 PASS / 6 FAIL** (2026-09-14 실측).
`--headed --slow 500 --only require_uppercase` 로 브라우저가 스스로 입력하는 것도
한 번 보여준다.

`bad` 에 심어 둔 결함은 **4개**인데 FAIL 은 **6건**이다 — 비밀번호 복잡도 검증
하나가 빠지면 최소길이·대문자·특수문자 **세 규칙**이 함께 무너지기 때문이다.
4회차 '규칙 하나당 케이스 하나' 의 예고편으로 여기서 한 번 짚는다.

### 지도를 함께 그린다 (20분)

6단계를 칠판에 적고 **AI 가 관여하는 곳에만 표시**한다. 두 곳뿐이다.

```
S1 기획서 PDF  → 화면과 규칙        <- 글을 읽는 AI
S2 규칙        → 넣어 볼 값들       <- 사람이 짠 규칙 (AI 아님)
                 어떤 케이스를 볼까  <- 같은 AI
S3 라벨        → 화면의 실제 요소   <- 못 찾으면 그림을 보는 AI
S4 브라우저 조작                    <- SW팀
S5 PASS/FAIL 판정                   <- SW팀 · AI 아님
S6 리포트                           <- SW팀
```

여기서 **오늘의 분류**를 선언한다.

| | 무엇을 받아 무엇을 내놓나 | 우리 프로젝트에서 |
|---|---|---|
| **글을 읽고 쓰는 AI** | 글 → 글 | 기획서를 읽어 규칙을 뽑는다 |
| **그림을 보는 AI** | 그림 + 글 → 글 | 화면 사진에서 버튼 위치를 찾는다 |

두 사람이 이미 아는 것으로 잇는다 — ChatGPT 에 글을 쓰게 한 적 있는가?
사진을 올려 물어본 적은? **그 둘이 각각 이 두 칸이다.**

## 2회차 — S1 의 역할, 그리고 LLM 이란 (9/29)

**목표** LLM 이 무엇인지, 왜 우리가 ChatGPT 대신 Qwen 을 서버에 올렸는지 말할 수 있다.

### 지도에서 오늘 팔 곳 → 모델의 역할

**S1.** 기획서 PDF 를 받아 "화면 이름은 로그인, 요소는 셋, 비밀번호 규칙은 세 개" 같은
**정해진 칸을 채운다.** 글을 읽고 글을 쓰는 일이다.

### 분류(a) — LLM

**Large Language Model.** 다음에 올 단어를 맞히는 것을 아주 크게 한 것.
그것만으로 요약·번역·구조화가 되는 이유는 "다음 단어를 잘 맞히려면 앞의 내용을
이해해야 하기 때문" 이다. **원리는 여기까지. 속은 다음 주에 그림으로 본다.**

### 대표 예시(b)

| | 대표 | 특징 |
|---|---|---|
| **닫힌 모델** | GPT(OpenAI) · Claude(Anthropic) · Gemini(Google) | 회사 서버에서만 돈다. API 로 부른다. 강하다 |

### 우리는 어떻게 썼는가 — 왜 ChatGPT 를 안 썼나

여기가 오늘의 핵심이다. 세 가지 이유가 있다.

1. **기획서는 고객 자산이다.** ㈜WITCHES 의 미공개 기획서를 외부 API 로 보낼 수 없다.
2. **재현성.** 어제와 오늘의 판정이 같아야 QA 도구다. 남의 서버 모델은 예고 없이 바뀐다.
3. **비용.** 화면 하나에 여러 번 부른다. 실험 단계에서 API 비용은 그대로 개발 속도다.

## 3회차 — 모델 속을 그림으로: 어텐션 (10/6)

**목표** 모델이 문맥을 어떻게 보는지 그림으로 설명할 수 있다. **수식은 없다.**

### 지난주 질문에서 출발

"위 규칙 중 하나라도 위반하면" 의 **'위'** 는 바로 앞 네 줄을 가리킨다. 사람은 당연히
안다. 모델은 어떻게 아는가? — **문장 안에서 서로 어디를 보는지 정하는 장치**가 있다.
그게 **어텐션(attention)** 이다.

### 분류(a) — 문맥을 보는 방식

옛 방식은 문장을 앞에서부터 한 단어씩 순서대로 읽었다(RNN). 그러면 문장이 길어질수록
앞을 잊는다. 어텐션은 **모든 단어가 모든 단어를 동시에 본다.** 그리고 각자
"나는 이 단어를 얼마나 볼 것인가" 에 가중치를 준다.

```
    "비밀번호"  "는"  "8자"  "이상"  "이다"
         ^                      |
         +------- 강하게-------+      "이상" 이 무엇의 이상인지 알려면
                                       "8자" 와 "비밀번호" 를 봐야 한다
```

칠판에 화살표를 그린다. 굵기가 곧 가중치다.

### 대표 예시(b) — 번역에서 시작한 이야기

기계 번역에서 "이 단어를 번역할 때 원문의 어디를 볼까" 를 풀려고 나왔고(2015),
2017년에 **"어텐션만 있으면 된다"**(Transformer)로 정리됐다. 지금 GPT·Claude·Gemini·
Qwen 이 전부 그 구조 위에 있다. **T** 가 Transformer 다 — GPT = Generative
Pre-trained **Transformer**.

### 손으로 (25분) — 종이와 펜

1. 짧은 문장에서 대명사가 가리키는 것에 화살표를 긋는다.
   *"예원이가 선진이에게 노트북을 빌려줬는데 **그것**이 고장 났다."* → 무엇이?
2. 우리 기획서의 진짜 문장으로 같은 것을 한다.
   *"위 규칙 중 하나라도 위반하면 ... 를 노출한다."* → **'위 규칙'** 은 몇 번째 줄들인가?
3. 여기서 화살표를 잘못 그으면 무슨 일이 일어나는가?

## 5회차 — AI 에게 형식을 강제한다 (10/27)

**목표** 왜 프롬프트만으로는 부족한지, 정형 출력이 무엇을 보장하는지 말할 수 있다.

### 문제부터

S1 은 JSON 을 받아야 한다. 그 JSON 을 다음 단계가 그대로 읽기 때문이다.
그런데 **7B 급 모델에게 "JSON 으로 줘" 라고 부탁만 하면**

- 마크다운 코드펜스로 감싸서 준다
- 필드 이름을 지어낸다 — `screen_name` 을 요구했는데 `screenName` 이 온다
- 중괄호를 하나 빠뜨린다

필드 이름이 흔들리면 `constraints` 키가 흔들리고, 그러면 값 생성이 규칙을 통째로
놓친다. **조용히.**

### 분류(a) — 정형 출력 (structured output)

**모델이 스키마를 벗어난 토큰을 애초에 생성하지 못하게 막는 기능.** 부탁이 아니라
제약이다. 생성 단계에서 차단하므로 "고쳐 달라고 다시 부탁하는 루프" 가 필요 없다.

### 대표 예시(b)

| 어디 | 이름 |
|---|---|
| OpenAI 표준 (우리가 쓰는 것) | `response_format={"type": "json_schema", ...}` |
| Anthropic | structured outputs |
| vLLM 자체 확장 | `guided_json` — **우리는 안 쓴다** |

### 우리는 어떻게 썼는가 — 그리고 실제로 데인 이야기

`llm/vllm_backend.py` 는 OpenAI 표준 `response_format` 을 쓴다. vLLM 확장인
`guided_json` 을 쓰지 않는 이유가 문서에 남아 있다.

> vLLM 0.24 에서 제거됐다. `extra_body={"guided_json": ...}` 로 보내면
> **오류 없이 조용히 무시된다** — 요청한 필드명(`screen_name`)이 아니라 모델이
> 지어낸 이름(`screenName`)이 돌아오고 응답이 마크다운 코드펜스로 감싸진다.

**QA 도구에서 이런 무성 실패(silent failure)가 가장 위험하다.** 에러가 났으면 고쳤을
텐데, 아무 말 없이 잘못된 결과가 흘러간다.

그리고 `temperature=0.0` — 창의성을 끈다. 추출·구조화는 **같은 입력에 같은 출력**이
나와야 한다. 어제의 초록불과 오늘의 초록불이 같은 뜻이려면 그래야 한다.

### 팀장 시연 (10분)

ChatGPT 에 같은 요청을 두 번 한다 — (1) 그냥 "JSON 으로 줘" (2) 필드를 정확히 지정.
두 번씩 돌려 답이 흔들리는지 본다.

## 6회차 — AI 는 지어낸다 (11/3)

**목표** 환각이 무엇이고, 우리가 그것을 어떻게 막았는지 네 겹으로 설명할 수 있다.

지난주 질문의 답이 오늘이다. **형식은 강제할 수 있지만 내용의 진실은 강제할 수 없다.**

### 분류(a) — 환각 (hallucination)

모델이 **없는 것을 그럴듯하게 만들어 내는 것.** 모르는 것을 모른다고 하지 않고
자연스러운 답을 지어낸다. 다음 단어를 잘 맞히도록 학습했기 때문에, 사실이 아니어도
**자연스러운 쪽**을 고른다.

### 대표 예시(b)

- 있지도 않은 논문·판례를 제목과 저자까지 붙여 인용한다
- 없는 함수 이름을 그럴듯하게 지어낸다
- 표에서 빠진 칸을 "있었을 법한 값" 으로 채운다 ← **우리가 겪은 것**

### 우리 프로젝트에서 실제로 일어난 일

`s1_spec_extractor/extractor.py` 의 `_drop_invented_strings` 에 그대로 적혀 있다.

> 기획서 요소 표에서 '안내 문구' 열을 지우고 돌렸더니, 7B 가 `'이메일 입력'` 을
> **지어냈다.** 문서에 그런 말이 한 글자도 없다.

그러자 도구가 이렇게 보고했다.

```
FAIL 입력 안내 문구 확인
     문구가 다름 — '이메일': 기대 '이메일 입력', 화면 '이메일을 입력하세요'
```

**올바른 구현을 FAIL 로 보고한 것이다.** 없는 결함을 자신 있게. 그리고 경고가
하나도 없었다. 개발자는 없는 버그를 찾다가 도구를 믿지 않게 된다.

### 방어는 네 겹이다

| 겹 | 무엇 |
|---|---|
| 1 | **표는 코드가 읽는다** — 표에 적힌 사실은 LLM 에게 묻지 않는다. 읽었으면 표가 이긴다 |
| 2 | **문서에 없는 문자열은 버린다** (`_drop_invented_strings`) |
| 3 | **스키마 강제** (5회차) — 형식은 애초에 못 벗어난다 |
| 4 | **버렸다는 사실을 경고로 남긴다** — 조용히 처리하지 않는다 |

2번의 판별 기준이 영리하다. "표에 있는가" 가 아니라 **"문서 본문 어디에든 있는가"** 로
본다. 표로만 보면 산문으로 쓴 기획서에서 검증이 사라지기 때문이다.

버린 뒤에는 그 케이스가 '에러가 떴는가' 만 확인하도록 격하된다 —
**검증이 약해지지만 거짓이 되지는 않는다.** 이 교환이 이 프로젝트의 태도다.

### 손으로 (25분) — 도구가 하는 검사를 직접 해 본다

## 7회차 — 그림을 보는 AI와 채점 (11/10)

**목표** VLM 이 무엇인지, 그리고 "정확도 90%" 가 무엇의 90%인지 따질 수 있다.

### 지도에서 오늘 팔 곳 → 모델의 역할

**S3.** 평소에는 라벨로 요소를 찾는다("이메일" 이라고 적힌 입력란). 그런데 **아이콘만
있는 버튼**은 라벨이 없어 그 길이 통째로 막힌다. 사람은 그 화면을 보면 어디를 눌러야
할지 안다. 그 능력을 도구에 주는 것이 2차 경로다.

### 분류(a) — VLM (Vision-Language Model)

**그림 + 글 → 글.** 이미지를 보고 질문에 답한다. 우리는 "이 화면에서 '로그인' 버튼이
어디 있니?" 라고 묻고 **좌표(네모 상자)** 를 받는다.

좌표는 `0~1 상대값`으로 받는다. 모델마다 좌표 규약이 다르기 때문이다 — 절대 픽셀을
내는 모델도, 0~1000 정규화를 쓰는 모델도 있다. **백엔드가 자기 규약을 0~1 로 바꿔서
돌려준다.** 그래야 모델을 바꿔도 S3 를 안 고친다.

### 대표 예시(b)

GPT-4V(OpenAI) · Gemini(Google) · Claude · **Qwen2.5-VL**(Alibaba, 우리 것).
2회차의 닫힌/열린 구도가 여기도 그대로 있다.

### 손으로 (1) — 정답 상자를 눈으로 본다 (10분)

```powershell
uv run python docs\study\tools\draw_boxes.py --state login-empty
start runs\study\iou-boxes.html
```

전체를 보려면 `--state` 없이. 화면 18장 · 정답 상자 63개가 나온다.
**'없음' 으로 넣어 둔 항목 14개**도 함께 본다 — 그 화면에 없는 것을 모델이 찾았다고
하면 그게 오탐이다. 시험지에 일부러 넣어 둔 함정이다.

### 손으로 (2) — 직접 채점해 본다 (20분)

```python
from prova.vlm.metrics import iou, center_hit, center_error

truth = (0.3671875, 0.436875, 0.6328125, 0.484375)   # 이메일 입력란의 진짜 위치
found = (0.36, 0.42, 0.64, 0.50)                     # 모델이 이렇게 찍었다고 하자

print(f"IoU        {iou(found, truth):.3f}")
print(f"중심 적중  {center_hit(found, truth)}")
print(f"중심 오차  {center_error(found, truth):.3f}")
```

**상자를 일부러 크게/작게/살짝 옮겨** 가며 두 숫자가 어떻게 다르게 움직이는지 본다.

| 지표 | 무엇을 재나 |
|---|---|
| **IoU** | 상자가 얼마나 겹치는가 — **크기까지** 맞혀야 높다 |
| **적중** | 중심이 실제 요소 안에 드는가 — **위치만** 맞으면 된다 |

### 우리는 어떻게 보고하는가 — 두 숫자를 나란히

실측(`docs/measurements/vlm-iou-qwen-vl-2026-08-31.md`, 18화면 77항목):

| 지표 | 값 |
|---|---|
| 탐지 성공률 (IoU 0.5 기준) | 36/63 = **57.1%** |
| 적중률 (중심이 요소 안) | 57/63 = **90.5%** |

**같은 실험인데 57% 와 90% 다.** 2차 경로가 하는 일은 좌표를 눌러 조작하는 것이므로
실제 성패는 적중이다. 입력란을 '라벨까지 포함한 영역' 으로 잡으면 IoU 는 떨어지는데
클릭은 정확히 된다. 그런데 명세서가 요구한 지표는 IoU 다.

**하나로 합치면 어느 쪽이든 사실을 지운다.** 그래서 둘 다 재고 나란히 적는다.

## 8회차 — AI 를 안 쓰기로 한 결정 (11/17)

**목표** AI 를 어디에 쓰지 않을지 정하는 것이 왜 AI 엔지니어의 일인지 말할 수 있다.

### 지도를 다시 편다 — 빈칸을 본다

8주 동안 AI 가 있는 두 지점을 팠다. 오늘은 **비어 있는 칸**을 본다.

| 어디 | AI 를 안 쓴다 | 왜 |
|---|---|---|
| 값 생성 (`rule_expander.py`) | 순수 함수 | 같은 규칙에 매번 같은 값이 나와야 한다 |
| 판정 (`assertion_engine.py`) | 순수 함수 | 판정이 흔들리면 리포트를 믿을 수 없다 |
| 표 읽기 (`pdf_parser.py`) | 코드가 읽는다 | 표에 적힌 사실을 모델이 지어냈다 (6회차) |
| Figma 경로 (`s1_figma/`) | **통째로 AI 없음** | 컴포넌트 구조가 이미 결정적이다 |

### 이유는 하나로 모인다

AI 는 **확률적**이다. 같은 입력에 다른 답이 나올 수 있다. 그건 글을 쓰거나 아이디어를
낼 때는 장점이지만, **QA 도구에서는 치명적이다.**

> 어제의 초록불과 오늘의 초록불이 같은 뜻이 아니게 된다.

그래서 이 프로젝트는 AI 를 **사실을 읽는 곳(S1)** 과 **사람이 못 하던 것을 하는
곳(S3 2차 경로)** 에만 두고, 판단은 전부 코드에 뒀다. 5회차의 `temperature=0`,
6회차의 방어 네 겹이 전부 같은 태도의 다른 얼굴이다.

### 남길 문장 두 개

> **AI 를 쓰는 일의 절반은 AI 를 안 믿는 장치를 만드는 것이다.**
>
> **AI 엔지니어 일의 절반은 어디에 AI 를 쓰지 않을지 정하는 것이다.**

### 마무리 (40분) — 각자 5분 발표

8주 중 **가장 궁금했던 것 하나**를 골라 조사해 와서 5분씩 발표한다.
매주 '오늘 남길 질문' 에 적어 둔 것 중에서 골라도 좋다. 주제 예시:

- 4비트로 압축하면 얼마나 멍청해지나 (양자화 손실 측정)
- 어텐션 계산량과 문맥 길이의 관계
- 내 노트북에서 작은 모델을 실제로 돌려 보기
- VLM 이 자신 있게 틀리는 것을 막는 방법 (노트 13 의 정체 대조)
- 우리 프로젝트에 AI 를 **더** 쓸 수 있는 곳이 있을까? 있다면 왜 아직 안 썼을까?

이 발표가 다음 학기 각자의 방향이 된다.

### 두 사람이 막힐 만한 곳

1. **"LLM 이랑 ChatGPT 랑 뭐가 다른데요?"** — ChatGPT 는 제품 이름, LLM 은 그 안의
   모델 종류. 2회차에서 반드시 짚는다.
2. **파라미터 = 모델 안의 숫자 개수** — "70억 개의 무엇" 인지 4회차에서 한 번 더.
3. **IoU 와 적중이 왜 다른지** — 7회차에서 상자를 직접 움직여 보게 한다. 말로는 안 된다.
4. **환각이 "틀린 답" 과 다른 점** — 틀린 답은 티가 나고, 환각은 **그럴듯해서 안 난다.**

### 팀장 시연 준비물

2·5회차는 ChatGPT/Claude 계정으로 팀장이 직접 돌린다. **미리 한 번 해 보고 답이
어떻게 나오는지 확인해 둔다** — 현장에서 처음 돌리면 원하는 그림이 안 나올 수 있다.
