# 2차 범위 설계 — 상품등록·주문조회

명세서 §0-2 의 2차 범위 중 **대상 확장(상품등록·주문조회)** 의 설계다.
v1.0 (2026-08-19 설계 확정). 구현하며 확정되는 세부는 이 문서를 갱신한다.

**v1.1 (2026-08-19, 구현 확정) — 갱신 내역**

- 상품등록 요소의 액션은 `fill`(설계 문서에 명시가 없던 세부, S2 구현 시 확정).
- 주문조회 O1(정렬 결함)×O2(합계 결함)이 같은 SUT 변형에서 동시에 심겨 있어,
  `bad` 의 합계 판정은 정렬이 깨진 행 순서와 무관하게 실제 행 합(1,859,000)
  대 화면 표시 합(569,000)을 비교한다 — 상호작용으로 값이 갈리지 않는다.
  (`tests/test_orders_e2e.py`)
- 케이스 격리: `nodes.run_cases` 가 케이스마다 실행 전에 쿠키를 지운다.
  격리가 없으면 앞선 케이스의 로그인 세션이 남아 `precondition-guard` 케이스가
  오탐 PASS/FAIL 을 낸다 — §3-2·§4 설계대로 필터 없이 문서 전체를 돌려도
  성립함을 `TestFullDocumentNoFilter` 로 못 박았다.
- `sum_matches` 에서 합계 표시 요소가 여러 곳에서 발견돼 다중 매칭이 나면
  판정 불능(FAIL)으로 처리한다 — §3-6 이 "요소 0개는 판정 불능" 이라 정한
  원칙을 다중 매칭에도 그대로 적용했다.
- `seed_rows` 가 빈 경우(시드 표가 없는 기획서) `sorted_desc`·`sum_matches`
  케이스를 만들지 않으며, 이는 경고 없이 조용히 스킵된다 — 기획서가 데이터를
  제시하지 않으면 그 검증이 불가능하다는 §1-2 원칙의 자연스러운 결과이고,
  두 화면 모두 시드 표가 있으므로 실측에서는 발생하지 않는다.

---

## 0. 무엇이 새로운가

1차의 네 화면(로그인·회원가입·검색·비밀번호 찾기)은 전부 **빈 상태에서 열 수
있는** 화면이었다. 2차의 두 화면은 다르다.

| 화면 | 처음 생기는 것 |
|---|---|
| 상품등록 | **전제 상태** — 로그인한 판매자여야 열린다 |
| 주문조회 | **데이터 전제** — 이미 있는 주문이 보여야 하고, 정렬·합계가 맞아야 한다 |

지금의 데이터 계약에는 전제를 표현할 자리가 없고, 판정에는 순서·계산을 확인할
유형이 없다. 이 둘을 더하는 것이 이 설계의 전부다. 파이프라인의 뼈대(S1~S6),
케이스 선택 층, 웹 UI 는 바꾸지 않는다.

---

## 1. 기획서 형식 — 새 절 두 개

### 1-1. "전제" 절 (상품등록·주문조회 기획서)

```markdown
## N. 전제

이 화면은 판매자 계정으로 로그인한 상태에서 동작한다.
비로그인 상태로 접근하면 로그인 화면으로 이동시킨다.

| 이메일 | 비밀번호 |
|---|---|
| seller@test.com | Seller1! |
```

- 계정 표는 §5 "테스트 계정" 과 같은 형식이다 — 표는 코드가 읽는다는 원칙 그대로.
- 두 번째 문장(비로그인 접근 시 이동)은 **그 자체가 검증 대상**이다 (§3-3).

### 1-2. "테스트 주문 데이터" 표 (주문조회 기획서)

```markdown
## M. 테스트 주문 데이터

주문조회 화면은 아래 주문이 등록된 상태를 전제한다. 주문일 내림차순(최신순)으로
표시하며, 합계는 표시된 주문 금액의 합이다.

| 주문번호 | 주문일 | 상품명 | 금액 | 상태 |
|---|---|---|---|---|
| ORD-005 | 2026-08-15 | 노트북 | 1,290,000 | 배송중 |
| ORD-004 | 2026-08-12 | 마우스 | 39,000 | 배송완료 |
| ORD-003 | 2026-08-09 | 키보드 | 89,000 | 배송완료 |
| ORD-002 | 2026-08-03 | 모니터 | 429,000 | 취소 |
| ORD-001 | 2026-07-28 | 케이블 | 12,000 | 배송완료 |
```

- SUT 는 이 표를 그대로 시드한다. 기획서가 데이터를 제시하지 않으면 그 검증은
  불가능하고, 그건 기획서의 한계다 — Scenario 때 세운 원칙의 연장.
- 건수(5건)·특정 주문번호 노출은 기존 `expect_count`·`expect_text` 가 담당한다.
  이 표가 새로 가능하게 하는 것은 **정렬과 합계**다.

## 2. 데이터 계약 확장 (models.py)

```python
class Precondition(BaseModel):
    """화면이 성립하기 위한 전제. 지금은 로그인 하나만 표현한다."""
    requires_login: bool = False
    account_email: str = ""
    account_password: str = ""
    login_screen_id: str = "login"      # 전제를 세울 때 밟을 화면

class ScreenSpec(BaseModel):
    ...
    precondition: Optional[Precondition] = None

class TestCase(BaseModel):
    ...
    #: 전제를 세우는 스텝. S2 가 코드로 생성한다. 실패하면 케이스는
    #: FAIL + precondition_failed 로 분류된다 (§3-2).
    setup_steps: list[TestStep] = Field(default_factory=list)
```

`ExpectedType` 에 두 값을 더한다. 기존 값의 의미를 넓혀 재해석하지 않는다 —
필드 이름이 할 수 있는 일을 말해야 한다.

```python
ExpectedType = Literal[..., "sorted_desc", "sum_matches"]

class Expectation(BaseModel):
    ...
    #: sorted_desc — 순서를 확인할 반복 요소(열)의 라벨 (예: "주문일")
    order_target: Optional[str] = None
    #: sum_matches — 더할 반복 요소의 라벨 / 합계 요소의 라벨
    sum_row_target: Optional[str] = None
    sum_total_target: Optional[str] = None
```

`kind` 열거형 같은 전제 일반화는 하지 않는다 — 지금 전제는 로그인 하나다(YAGNI).
두 번째 전제 종류가 실재할 때 확장한다.

### 2-1. 새 constraints 키: `numeric`

상품등록의 가격·재고수량은 "숫자만 입력 가능" 규칙이 필요하다. `format` 은
이메일 형식에 묶여 있고 `pattern` 의 일반 정규식 위반값 생성은 결정적으로
만들기 어렵다. `numeric: true` 를 추가하고 rule_expander 가 고정 위반값
(예: `"만원"`)을 생성한다 — 규칙 하나당 케이스 하나, 위반값은 그 규칙만 어긴다.

## 3. 각 단계의 몫

### 3-1. S1 — 전제 절 추출

전제 절이 있으면 `requires_login: true` 와 계정을 옮겨 적는다. **그것뿐이다.**
로그인 스텝을 만드는 판단은 S1 에 주지 않는다 — 7B 에 선택지를 늘리면 추출이
흔들린다(Scenario 의 expect_text 결정과 같은 이유). 골든에 precondition 을
포함해 추출 정확도를 기존 방식대로 잰다.

### 3-2. S2 — 전제 스텝 생성 (순수 함수)

```
expand_precondition(pre, doc) -> list[TestStep]
  1. navigate  login_screen_id 의 url_path
  2. input     로그인 화면의 이메일 라벨   <- pre.account_email
  3. input     로그인 화면의 비밀번호 라벨 <- pre.account_password
  4. click     로그인 화면의 제출 라벨
```

라벨은 로그인 화면 ScreenSpec 에서 가져온다 — 흐름이 값을 라벨로 잇는 것과
같은 원리다. 로그인 화면이 문서에 없으면 전제 케이스를 만들지 않고 경고를
남긴다(기획서의 문제이므로).

전제가 있는 화면의 **모든 케이스**에 같은 setup_steps 가 붙는다
(§3-3 의 역방향 케이스만 예외 — 비로그인 상태 자체가 그 케이스의 조건이다). 케이스의
test 스텝은 지금처럼 대상 화면 navigate 로 시작하므로 setup 은 자기완결이다.

### 3-3. S2 — 전제 역방향 케이스

전제 절의 "비로그인 상태로 접근하면 로그인 화면으로 이동시킨다" 에서 케이스
하나를 만든다: setup_steps **없이** 대상 화면으로 직접 이동 →
`Expectation(type="redirect", url_contains=<로그인 경로>)`. bad 의 가드 누락
결함(§4)을 이 케이스가 잡는다. case_id: `{screen}-precondition-guard-NNN`.

### 3-4. S2 — 정렬·합계 케이스 (자기일관 검증)

주문 데이터 표와 기획서 문장("주문일 내림차순", "합계는 표시된 금액의 합")에서
케이스 두 개를 만든다.

- `sorted_desc`: order_target(주문일 열)의 반복 요소를 전부 찾아 값을 파싱,
  **내림차순인지** 비교. 날짜 형식은 `YYYY-MM-DD` 로 고정한다.
- `sum_matches`: sum_row_target(금액 열)의 반복 요소 값을 합산,
  sum_total_target(합계)의 값과 비교. 금액 파싱은 **쉼표·'원'·공백을 제거한
  정수**로 고정한다.

화면 스스로 모순인지를 보므로 LLM 없이 결정적이고, 시드 표가 바뀌어도 판정
로직은 흔들리지 않는다. 반복 요소를 라벨로 찾는 경로는 건수 세기(expect_count,
노트 10)가 이미 뚫어 놓았다 — 그 경로를 재사용하고 '값 파싱 + 비교' 만 얹는다.

### 3-5. S4 — setup 실행

setup_steps 를 test 스텝보다 먼저, 같은 실행기로 돈다. StepResult 에
`phase: "setup" | "test"` 를 남겨 리포트가 구분해 보여준다. setup 중 실패하면
test 스텝은 실행하지 않는다.

### 3-6. S5 — 판정

- setup 실패 → **FAIL + 새 실패 분류 `precondition_failed`**. Verdict 는
  PASS/FAIL 이진을 유지한다 — 제3의 판정값은 summarize·리포트·UI·통과율
  정의 전부에 파급되므로 만들지 않는다.
- `sorted_desc`·`sum_matches` 판정 함수는 assertion_engine 에 순수 함수로
  추가하고 단위 테스트로 고정한다 (파싱 실패·요소 0개·1개 경계 포함.
  요소 0개는 판정 불능이므로 FAIL — 0건 목록이 "정렬돼 있다" 로 통과하면
  아무것도 확인하지 않은 초록불이다).

### 3-7. S6 — 리포트

`CATEGORY_LABELS` 에 추가:

```python
"precondition_failed": ("전제 미충족",
    "전제(로그인)를 세우지 못했습니다. 이 화면의 결함이 아닙니다 — "
    "로그인 화면의 결과를 먼저 확인하세요."),
```

화면별 집계에서 precondition_failed 는 따로 센다 — 흐름을 화면 칸에 섞지 않은
것과 같은 이유다. 로그인이 깨지면 로그인 화면 케이스가 이미 FAIL 을 내므로,
상품등록 케이스들의 전제 실패를 그 화면의 결함 수에 합치면 **같은 결함이 여러
화면의 결함처럼 읽힌다.**

### 3-8. 케이스 선택 층 (기존, 확인만)

새 화면 이름("상품 등록"·"주문 조회")과 요소 라벨이 어휘에 자동으로 들어가고,
화면별 확인 범위(ScreenCoverage)도 자동으로 센다 — 선택 층 코드는 바꾸지
않는다. 수용 기준에서 요청 예시("주문 내역이 최신순으로 나오는지")로 확인한다.

## 4. SUT 확장

**세션이 처음 생긴다.** 로그인 성공 시 서명 쿠키를 발급하고, good 의
상품등록·주문조회는 비로그인 접근을 로그인으로 리다이렉트한다. 변형(good/bad)별
분리는 REGISTERED 와 같은 원칙 — 세션도 변형별로 격리한다.

새 화면과 심는 결함 (결함:케이스 = 1:1, 오탐 검증을 위해 나머지는 동일):

| 화면 | good | bad 에 심는 결함 | 잡는 케이스 |
|---|---|---|---|
| 상품등록 `/{v}/product` | 상품명(required·max_length 50)·가격(required·numeric)·재고수량(required·numeric) 검증 | **P1** 가격에 문자 허용 (numeric 누락) | `product-price-numeric-*` |
| | 비로그인 → 로그인 이동 | **P2** 가드 누락 — 비로그인도 열림 | `product-precondition-guard-*` |
| 주문조회 `/{v}/orders` | 주문일 내림차순 · 합계 = 행 합 | **O1** 오래된순 정렬 | `orders-*-sorted_desc` |
| | | **O2** 합계에서 마지막 행 누락 | `orders-*-sum_matches` |

기획서 픽스처: `fixtures/specs/product_spec.md`·`orders_spec.md` (+ pdf·golden),
`scripts/make_spec_pdf.py` 에 등록. 주문조회 기획서의 화면 요소 표에는 주문일·
금액·합계가 **라벨 있는 요소**로 적힌다 — S3 가 라벨로 찾을 수 있어야 한다.

## 5. 수용 기준

1. **good 전부 PASS** — 상품등록·주문조회 각각, 그리고 기존 네 화면 회귀 유지.
2. **bad 는 심은 결함 4종(P1·P2·O1·O2)을 정확히 지목, 오탐 0건.**
3. **전제 실패 시나리오**: 전제 절에 **잘못된 비밀번호**를 적은 테스트 전용
   기획서 픽스처로 good SUT 를 돌리면 — 새 SUT 변형 없이 — 상품등록 케이스들이
   `precondition_failed` 로 분류되고, 리포트가 "이 화면의 결함이 아닙니다" 를
   보여준다. 화면별 집계에 결함으로 합산되지 않는다.
4. **정렬·합계 판정 단위 테스트**: 정렬 위반·합계 불일치·파싱 실패·요소 0개
   경계 전부. 0개는 FAIL 이다.
5. **자연어 요청**: "주문 내역이 최신순으로 나오는지 확인해줘" 가 orders 의
   sorted_desc 케이스를 포함해 고른다 (실모델, probe 스크립트에 추가).
6. **웹 UI**: 새 화면이 계획 화면의 그룹·확인 범위에 자동으로 나타난다
   (코드 변경 없이 — 확인만).

## 6. 구현 단계

- **Phase A — 상품등록**: 세션 → 전제(모델·S1·S2·S4·S5·S6) → SUT 상품등록 →
  픽스처 → 수용 기준 1·2(P1·P2)·3.
- **Phase B — 주문조회**: 시드 표 → sorted_desc·sum_matches → SUT 주문조회 →
  픽스처 → 수용 기준 나머지.

A 가 전제 기반을 검증한 뒤 B 를 얹는다. 각 Phase 끝에 전체 회귀.

## 7. 하지 않는 것

- **SKIPPED 판정값** — FAIL + 분류로 충분하고, 이진 판정의 파급을 피한다.
- **전제 종류 일반화(kind)** — 로그인 하나뿐이다. 두 번째가 실재할 때.
- **날짜 필터·기간 조회** — 입력↔재조회 상호작용은 복잡도가 확 뛴다. 이후 과제.
- **seed/reset API** — 도구가 SUT 전용 API 에 의존하면 실물 확장성을 해친다.
  시드는 SUT 기동 시 한 번, 기획서 표 그대로.
- **storage_state 세션 캐시** — 매 케이스 로그인이 느려지면 그때 최적화한다.
  로그인 경로가 검증에서 빠지는 비용이 있으므로 기본값으로는 채택하지 않는다.

## 8. 위험과 대응

- **7B 의 전제 절 추출 정확도** — 골든 대조로 잰다. 표(계정)는 코드가 읽으므로
  모델의 몫은 "전제 절이 있다" 판별에 가깝다. 흔들리면 절 제목 매칭(결정적)으로
  강등할 수 있게 S1 안에서 한 함수로 격리한다.
- **금액·날짜 파싱의 지역성** — 형식을 기획서에 고정(YYYY-MM-DD, 쉼표 구분
  정수)하고 파서를 순수 함수 + 단위 테스트로 둔다. 실물 기획서가 다른 형식을
  쓰면 그때 형식을 추가한다 — 미리 넓히지 않는다.
