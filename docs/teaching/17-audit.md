# 17 · 각각은 옳은데 함께 두면 구멍이 난다

이전: [16-forbidden-text.md](16-forbidden-text.md) — 없어야 할 것이 없는가

---

## 왜 멈추고 점검했나

1차 범위가 닫혔습니다. 테스트 523개가 통과하고, 화면 넷과 흐름을 검증하고, 오탐 0건입니다.
기능을 더 붙이기 좋은 시점처럼 보입니다.

그런데 지금까지 이 프로젝트가 찾은 결함은 대부분 **새 기능을 만들다가** 우연히 드러난
것이었습니다. 안내 문구 열을 더하다 '표가 페이지를 넘어간다' 를 만났고, 훼손 측정을 하다
'모델이 요구사항을 발명한다' 를 만났습니다.

우연에 기대지 않고 **찾으러 가면** 무엇이 나오는지 보기로 했습니다.

---

## 가장 값진 발견 — 새로운 종류의 결함

지금까지의 사고는 전부 **"한 기능이 틀렸다"** 였습니다. 이번에 나온 것은 다릅니다.

```
비동기 대기 (노트 15)      '있어야 할 것' 이 나타날 때까지 기다린다. PASS 면 멈춘다.
금지 문구   (노트 16)      '없어야 할 것' 이 없는지 본다.
```

**각각은 옳습니다.** 그런데 함께 두면 이렇게 됩니다.

```
1. 금지 문구 케이스를 판정한다 → 아직 안 나타났으니 PASS
2. 대기 로직: "PASS 니까 멈춘다"
3. 400ms 뒤 '등록되지 않은 이메일입니다.' 가 나타난다
4. 아무도 보지 않았다
```

비동기로 렌더하는 화면에서 **계정 존재 여부 노출을 놓칩니다.** 그리고 이 미탐은
**대기를 넣은 것 때문에 새로 생겼습니다** — 노트 15의 수정이 노트 16의 기능에 구멍을
뚫은 것입니다.

### 왜 만들 때는 안 보였나

노트 15를 쓸 때 대기의 위험을 이렇게 정리했습니다.

> 대기는 FAIL 을 PASS 로 바꿀 수 있고 그 반대는 없다. 그 방향성이 결함을 덮는 데
> 쓰이면 이 도구의 값이 사라진다.

그래서 상한을 두고, 기다린 시간을 남기고, 끊긴 케이스는 기다리지 않게 했습니다.
**그때 있던 판정 유형 아홉 개에 대해서는 그 방어가 충분했습니다.**

문제는 그 뒤에 **열 번째 판정 유형이 추가된 것**입니다. `text_absent` 는 통과의 뜻이
반대인 유일한 판정이고, 대기 로직은 그것을 모릅니다.

> **한 방향으로만 바꾸는 장치는, 새 판정이 추가될 때마다 방향을 다시 확인해야 한다.**

이게 이 노트에서 가장 남기고 싶은 문장입니다. 대기·보정처럼 "결과를 한쪽으로만
움직이는" 장치는 그 쪽이 늘 안전한 방향이라는 가정 위에 서 있습니다. 새 판정이 그 가정을
깨는지 아무도 알려주지 않습니다.

### 고친 방법

```python
watching_for_leak = case.expected.type == "text_absent"
if verdict.verdict == ("FAIL" if watching_for_leak else "PASS"):
    return verdict
```

금지 문구만 창 전체를 감시하고 **FAIL 이 나오는 순간** 멈춥니다. 나타나지 않으면 상한까지
기다린 뒤 통과입니다.

그리고 늦게 나타났다는 사실을 남깁니다(`appeared_after_ms`) — 즉시 노출과 늦은 노출은
구현이 다릅니다.

### 증명을 함께 뒀다

`slowleak` 변형을 만들었습니다 — `bad` 와 같은 결함인데 누출 문구가 400ms 뒤에 나타납니다.

```
대기 켬  →  absent-005 FAIL  (늦게 나타남 300ms)
대기 끔  →  absent-005 PASS  ← 미탐
```

**두 번째 줄이 회귀 테스트에 있는 것이 중요합니다.** 그게 없으면 첫 줄이 무엇 덕분에
통과하는지 알 수 없습니다.

## 나머지 발견은 모양이 하나였다

> **있는 것과 동작하는 것은 다르다.**

이 프로젝트가 계속 만나 온 문장인데, 이번에는 **우리 코드가 그 대상**이었습니다.

| 무엇 | 있는 것 | 실제 |
|---|---|---|
| 설정 파일 18개 키 | 값을 고치면 동작이 바뀔 것 | **10개가 읽히지 않았다** |
| `AgentState.heal_count` | 보정 횟수를 센다 | 아무도 안 읽는다. 실제로는 `ExecutionContext` 의 동명 필드가 센다 |
| `PageState.http_status` | 4xx/5xx 판정에 쓴다 | 설정도 소비도 없다 |
| `STRATEGY_LABELS` | 주석: "리포트와 평가 지표에 쓴다" | 어디에도 안 쓴다. `vlm` 도 빠져 있다 |
| `dom_snapshot` | 스텝마다 저장한다 | 리포트에 링크가 없어 **아무도 열어 볼 수 없다** |
| `SIGNUP_PATHS` | 가입 경로 목록 | 죽어 있고 템플릿이 목록을 따로 적어 뒀다 |

### 설정이 특히 나빴다

```yaml
llm:
  max_tokens: 3072     # 읽지 않는다. 실제로는 2048 이 쓰인다
```

값을 고쳐도 아무 일이 없습니다. 그런데 **에러 메시지는 실제값을 보여줍니다.**

```
vLLM 이 빈 응답을 반환했습니다. max_tokens 가 너무 작아 생성이 중간에
끊겼을 수 있습니다 (현재 2048).
```

설정에 3072라고 적어 두고 에러가 2048이라고 말합니다. 사용자는 설정을 6144로 올리고, 또
2048이라는 메시지를 봅니다. **거짓 약속이 침묵보다 나쁩니다.**

고칠 때 두 갈래로 갈랐습니다.

- **필요한 셋은 끝까지 배선했다** — `screenshot_every_step` · `max_heal` ·
  `vlm_confidence_threshold`(하드코딩된 `MIN_CONFIDENCE` 를 인자로 뺐다)
- **소비자가 없는 일곱은 지우고, 왜 두지 않는지 적었다**

지운 것에 이유를 적은 게 중요합니다. 그냥 지우면 다음 사람이 "왜 없지?" 하며 다시 넣습니다.

```yaml
#   grounding.strategies
#                   탐지 전략 우선순위(명세서 §5-1)는 코드에 있다. 순서 자체가
#                   설계 판단이고, hint 에 따라 전략을 끼워 넣는 로직이 있어서
#                   평평한 목록으로 표현되지 않는다. 설정으로 열면 탐지를 깨는
#                   길만 열린다.
```

### 저장하면서 보여주지 않는 것

`dom_snapshot` 은 스텝마다 DOM 을 파일로 남깁니다. 그런데 리포트에 링크가 없습니다.

케이스 152개 × 스텝 몇 개 = 수백 개 파일을 쓰면서 **아무도 열어 볼 수 없었습니다.** 그리고
탐지 실패를 조사할 때 가장 필요한 자료가 그것입니다. 스텝 표에 '자료' 열을 두고 링크했고,
34개 링크가 전부 실존하는지 확인했습니다.

## 중복이 실험의 전제를 무너뜨리고 있었다

이건 흔한 DRY 얘기가 아닙니다.

로그인 핸들러가 **다섯 벌**(good·slow·spa·hashed·native), 검색이 **세 벌** 있었고
사실상 동일했습니다. 각 변형은 이런 전제로 재는 실험입니다.

> 검증 로직은 `good` 과 **완전히 같고** 변수 하나만 다르다.

복사해 두면 그 전제가 **코드로 보장되지 않습니다.** 한쪽만 고치면 그 변형이 재는 변수가
둘이 되고, **그 사실이 조용히 숨습니다.** 실험 결과가 무엇 때문인지 알 수 없게 됩니다.

그래서 검증을 한 벌로 모으고 변형은 표에 '다른 점' 만 선언합니다.

```python
LOGIN_VARIANTS = {
    "good": False, "slow": False, "hashed": False, "native": False,
    "spa": True,          # 성공해도 URL 이 바뀌지 않는다
}
```

**`bad` 는 공유하지 않습니다** — `bad` 의 차이는 검증 로직 자체이고 그게 실험의 변수입니다.
그걸 공유 함수에 섞으면 그 함수가 '기획서를 지킨 검증' 이 아니게 됩니다.

> **공유할 곳과 나눌 곳을 가르는 기준은 '같은 코드인가' 가 아니라 '무엇이 실험의
> 변수인가' 다.**

### 지우다 함수를 하나 날렸다

`good/search` 구역을 지웠더니 `find_products` 가 함께 사라졌습니다 — 화면 구역 안에
정의돼 있었기 때문입니다. 임포트 검사에서 바로 잡혔지만, **정리하다 지우는 사고**가
실제로 일어난다는 증거입니다. 헬퍼 구역으로 옮겼습니다.

## 자동 스캔이 두 번 틀렸다

낡은 숫자를 찾는 스캔을 돌렸더니 13건이 걸렸습니다. 문맥을 읽어 보니 **2건은 오탐**이었습니다.

```
docs/teaching/overview.src.html  테스트 400  <-- 실제 493
```

그 문장은 이랬습니다.

> 테스트 400개가 통과하고, 세 화면과 화면 사이 흐름을 검증하고, 오탐 0건을 유지하고
> **있었다.** 그런데 그 문장에 조건이 숨어 있었다.

**과거 서술입니다.** 그때는 400개였고, 그 숫자가 이야기의 일부입니다. 고치면 이야기가
망가집니다.

그리고 라우트 핸들러 31개가 '쓰이지 않는 함수' 로 걸렸습니다 — FastAPI 가 프레임워크에서
부르므로 이름으로 참조되지 않습니다.

> **스캔은 후보를 주고, 판단은 문맥이 한다.** 스캔 결과를 그대로 일괄 수정하면 역사
> 서술을 지우고 프레임워크 진입점을 삭제합니다.

### 숫자가 썩는 것을 어떻게 다루나

썩은 숫자가 실제로 여럿 있었습니다.

```
docs/pr/00-reading-guide.md      테스트 422 → 493, 설계 판단 11 → 13, 노트 14 → 16
docs/teaching/06-langgraph.md    테스트 374개 통과
README.md                        티칭 노트 13개
```

규칙을 정했습니다.

- **현재를 말하는 문서**(README·PR 가이드)에는 숫자를 둔다. 대신 그곳이 유일한 출처다.
- **이야기를 하는 문서**(티칭 노트)에는 **시점을 붙인다** — "이 시점의 전체 테스트는
  331개였습니다" 처럼. 시점이 붙으면 그 숫자는 영원히 맞습니다.
- 시점을 붙일 수 없으면 **숫자를 뺀다.** `06-langgraph.md` 의 "테스트 374개 통과" 는
  "전 케이스 통과" 로 바꿨습니다.

## 문서도 코드처럼 검사할 수 있다

`README.md` 가 점검 시점에 760줄이었고 설계 판단 절만 379줄이었습니다. 목차를 넣었는데
**앵커 13개 중 3개가 깨져 있었습니다** — 제목에 em dash(`—`)가 있어 GitHub 의 앵커 규칙과
제가 짠 규칙이 달랐습니다.

목차를 넣고 링크를 확인하지 않으면 **목차가 오히려 방해**입니다. 그래서 검사를 돌렸습니다.

```
내부 링크 13개 · 깨짐 0개
문서 29개의 파일 링크 검사 → 없는 대상 0개
```

문서는 컴파일되지 않으니 이런 것을 사람이 눈으로 봐야 한다고 생각하기 쉽습니다. **앵커와
파일 경로는 기계가 확인할 수 있습니다.**

## '아직 안 한 것' 절이 통째로 낡아 있었다

README 의 그 절이 이렇게 시작했습니다.

> Figma 연동 · **VLM 요소 탐지(S3 fallback)** · **Self-Healing 루프** ·
> **아이디/비밀번호 찾기 화면** · ...

굵게 표시한 셋은 **이미 끝난 것들**입니다. 그리고 근거로 방금 지운 죽은 필드를 들고
있었고, `LocateAnything-3B` 라는 쓰지 않는 모델의 추정치를 적어 두고 있었습니다.

**끝낸 일을 '안 한 것' 에서 지우는 것은 아무도 안 합니다.** 새 기능을 만들 때 그 절을 열
이유가 없으니까요. 점검이 아니면 9월 티칭에서 팀원이 그 목록을 보고 "VLM 은 아직 안
했구나" 라고 이해했을 것입니다.

## 이 노트에서 남길 것

1. **각각 옳은 두 기능이 함께 구멍을 만든다.** 지금까지의 사고는 '한 기능이 틀렸다' 였고,
   이건 처음 만난 종류입니다. 기능을 그 기능만 시험하면 안 잡힙니다.
2. **한 방향으로만 바꾸는 장치는 새 판정이 추가될 때마다 방향을 재확인한다.** 대기·보정은
   "그 방향이 늘 안전하다" 는 가정 위에 있고, 새 판정이 그 가정을 깨는지 아무도
   알려주지 않습니다.
3. **'있는 것과 동작하는 것은 다르다' 를 우리 코드에도 적용한다.** 설정 18개 중 10개,
   상태 필드 셋, 상수 둘, 저장하지만 못 보는 자료 하나. 남에게 쓰던 잣대를 자기에게
   대 본 적이 없었습니다.
4. **거짓 약속은 침묵보다 나쁘다.** 읽지 않는 설정 키는 값을 고쳐도 아무 일이 없고,
   에러 메시지가 다른 값을 보여줘 사용자를 헷갈리게 합니다.
5. **지울 때는 왜 두지 않는지 적는다.** 그냥 지우면 다음 사람이 다시 넣습니다.
6. **공유와 분리의 기준은 '같은 코드인가' 가 아니라 '무엇이 실험의 변수인가' 다.**
   복사한 변형은 '로직이 같다' 는 전제를 코드로 보장하지 못하고, 한쪽만 고쳐지면 그
   사실이 조용히 숨습니다.
7. **스캔은 후보를 주고 판단은 문맥이 한다.** 낡은 숫자 13건 중 2건이 오탐이었고, 그대로
   고쳤다면 과거 서술을 지웠을 것입니다.
8. **이야기 속 숫자에는 시점을 붙인다.** 시점이 붙으면 영원히 맞습니다. 붙일 수 없으면
   숫자를 뺍니다.
9. **문서의 앵커와 파일 경로는 기계가 확인할 수 있다.** 목차를 넣고 링크를 확인하지
   않으면 목차가 방해가 됩니다.
10. **끝낸 일을 '안 할 일' 목록에서 지우는 사람은 없다.** 새 기능을 만들 때 그 목록을 열
   이유가 없습니다. 주기적으로 열어 보는 것 말고는 방법이 없습니다.
11. **정리하다 지우는 사고가 실제로 난다.** 구역을 지우면서 그 안에 있던 헬퍼 함수를
   함께 날렸습니다. 정리 뒤에도 회귀를 돌려야 하는 이유입니다.
