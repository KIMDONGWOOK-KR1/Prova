# 18 · 자연어로 요청받기 — 그리고 그 해석이 결함을 덮지 못하게 하기

이전: [17-audit.md](17-audit.md) — 각각은 옳은데 함께 두면 구멍이 난다

---

## 무엇을 만들었나

계획서 1차 목표 네 개 중 마지막 것입니다.

> **자연어 → 테스트 시나리오 변환** : 사용자가 자연어("회원가입이 잘 되는지 확인해줘")로
> 요청하면 이를 실행 가능한 테스트 시나리오로 변환하는 QA Agent를 구현한다.

이제 이렇게 됩니다.

```powershell
uv run prova run --pdf fixtures/specs/login_spec.pdf --url http://localhost:8100/bad \
                 --request "비밀번호 규칙이 제대로 걸리는지 확인해줘"
```

그리고 화면으로도 쓸 수 있습니다.

```powershell
uv run prova serve      # http://127.0.0.1:7007
```

그런데 이 노트에서 하고 싶은 이야기는 "붙였다" 가 아닙니다. **이걸 붙이면 이 도구가
지켜 온 성질 하나가 깨지는데, 그걸 어떻게 막았는가** 입니다.

---

## 먼저: 무엇이 깨지는가

지금까지 케이스 선택에 LLM 은 **전혀** 관여하지 않았습니다. 노트 03에서 그은 경계입니다.

```
"8자 이상" -> min_length: 8      자연어 해석,  AI          (S1)
min_length: 8 -> "Aa1!aaa"       규칙 -> 위반값, 코드      (S2)
케이스 목록 전체를 실행           선택 없음                 (S3~S5)
```

세 번째 줄이 중요합니다. 만들어진 케이스는 **전부** 돌았습니다. 그래서 이 명제가
성립했습니다.

> 리포트에 없는 결함은 없는 결함이다.

요청 해석이 케이스를 고르기 시작하면 이게 무너집니다.

```
모델이 케이스를 잘못 골라서 결함을 못 본 것
결함이 정말 없는 것
      ↓
리포트에서 똑같이 초록불이다
```

**틀렸다는 흔적이 아무 데도 남지 않습니다.** 실행되지 않은 케이스는 리포트에 아예
없으니까요.

---

## 이 문제의 모양은 전에 본 것이다

노트 15의 대기와 같습니다.

|  | 한쪽으로만 움직인다 |
|---|---|
| 대기 (노트 15) | FAIL 을 PASS 로 바꿀 수 있다. 그 반대는 없다. |
| 요청 해석 (이번) | 있는 FAIL 을 사라지게 할 수 있다. 없던 FAIL 을 만들지는 못한다. |

방향이 한쪽뿐이라는 것은 나쁜 소식이면서 동시에 좋은 소식입니다. **안전한 쪽이
정해져 있다**는 뜻이니까요. 대기 때는 상한을 두고 기다린 시간을 기록했습니다.
여기서도 같은 방식으로 갑니다.

---

## 네 가지 장치

### 1. 모델에게 '고르는 일' 만 시킨다

모델이 돌려주는 것은 `case_ids` 목록과 근거 한 줄뿐입니다.

```json
{ "case_ids": ["login-password-min_length-005"], "reason": "비밀번호 규칙만 골랐습니다" }
```

입력값·스텝·기대값은 건드릴 수 없습니다. **그래서 해석이 틀렸을 때 나올 수 있는
최악이 "엉뚱한 케이스를 돌렸다" 이고, "엉뚱한 판정을 내렸다" 는 될 수 없습니다.**

노트 03의 경계를 그대로 지킨 것입니다 — LLM 은 자연어 판단만 하고, 판정은 코드가 합니다.

### 2. 결과는 항상 부분집합이다

모델이 목록에 없는 id 를 지어내면 무시하고 경고를 남깁니다.

```python
for cid in raw.get("case_ids", []):
    if cid in by_id:
        wanted.append(cid)
    else:
        warnings.append(f"목록에 없는 case_id 를 무시했습니다: {cid}")
```

지어낸 id 로 케이스가 생기면 **실행되지 않은 케이스가 리포트에 나타납니다.** 그러면
판정 전체가 거짓이 됩니다. 노트 14에서 모델이 요구사항을 발명해 오탐을 만든 것과
같은 종류의 사고입니다.

### 3. 해석 실패는 '더 많이 검사하는' 쪽으로 넘어진다

여기가 가장 중요합니다. LLM 이 죽거나 없으면 어떻게 할까요?

| 선택지 | 결과 |
|---|---|
| 멈춘다 | 안전하지만 도구를 못 씁니다 |
| 일부만 돌린다 | **무엇을 빼도 되는지 모르는 상태에서 뺍니다** |
| 전체를 돌린다 | 느리지만 결함이 숨지 않습니다 |

세 번째를 골랐습니다.

```python
except LLMError as exc:
    return _all(cases, text, fallback=True,
                warnings=[f"요청 해석에 실패해 전체 케이스를 실행합니다: {exc}"])
```

**적게 고르면 결함이 숨지만, 많이 고르면 숨지 않습니다.** 방향이 한쪽뿐이라 실패 시
어디로 넘어져야 하는지가 정해져 있습니다. 느린 것은 참을 수 있고 틀린 것은 참을 수
없다 — 대기 상한을 정할 때와 같은 교환입니다.

### 4. 0건은 거부한다

`--only` 필터와 같은 계약입니다.

```
'결제 화면 확인해줘' 에 해당하는 케이스가 없습니다.
  실행 가능한 케이스: login-valid-001, login-email-required-002, ...
```

빈 목록으로 진행하면 **"전체 0건, 통과 0건, 통과율 100%"** 리포트가 나옵니다.
아무것도 검증하지 않았는데 초록불입니다. 이 프로젝트가 가장 경계하는 결과입니다.

## 그리고 UI 를 붙인 진짜 이유

CLI 로도 `--request` 는 동작합니다. 그런데 CLI 에는 **해석 결과를 보여줄 자리가
없습니다.** 케이스가 조용히 좁혀지고, 사용자는 무엇이 빠졌는지 실행이 끝난 뒤에야
리포트에서 봅니다.

그래서 웹 UI 는 실행을 두 단계로 나눕니다.

```
POST /api/plan   브라우저를 열지 않고 '무엇을 테스트할지' 만 정한다
POST /api/run    사람이 승인한 목록으로 실제 실행한다
```

화면은 이렇게 흐릅니다.

```
1. 대상 정하기    URL + 기획서 PDF
2. 요청 말하기    "회원가입이 잘 되는지 확인해줘"
3. 계획 확인 ★    Prova 가 "이렇게 이해했다" 를 보여주고 사람이 승인·가감
4. 실행 · 리포트  진행 스트리밍 → 기존 report.html
```

**3단계가 이 설계의 존재 이유입니다.** 계획 화면은 고른 케이스와 함께 **제외한
케이스를 전부 보여주고, 체크박스로 도로 켤 수 있게** 합니다.

### 왜 브라우저를 아직 열지 않는가

S1~S2 는 원래 브라우저가 필요 없습니다(노트 01). 그 경계가 이미 거기에 있었기 때문에
떼어내는 데 새 구조가 필요하지 않았습니다.

```python
def build_plan(...) -> tuple[AgentState, int]:
    """브라우저를 열지 않고 S1~S2 와 케이스 선택까지만 수행한다."""
```

`run_pipeline` 도 같은 함수를 씁니다. **계획 화면이 보는 목록과 실제로 실행되는 목록이
같은 코드에서 나와야** 사람이 승인한 것과 도는 것이 어긋나지 않습니다.

테스트로 못 박았습니다 — 대상 URL 이 없는 곳(`http://localhost:1/없는곳`)을 가리켜도
계획은 나옵니다. 승인 전에는 아무것도 실행되지 않는다는 증거입니다.

### 승인 뒤에는 모델을 다시 부르지 않는다

실행 시점에 요청을 다시 해석하면, 승인과 실행 사이에 모델의 답이 달라질 수 있습니다.
그러면 **사람이 승인한 것과 다른 것이 돕니다.** 그래서 승인 목록이 오면 해석을
건너뜁니다(`select_by_ids`). 계약은 `select_cases` 와 같습니다 — 부분집합이고, 비면
예외입니다.

## 리포트에도 남는다

노트 10의 2차 경로 보정, 노트 15의 대기 시간과 같은 이유입니다.

> 도구가 판단을 했으면 그 사실이 리포트에 있어야 한다.

통과율 바로 아래에 이렇게 들어갑니다.

```
요청을 확인한 뒤 사람이 승인한 실행 (3건 실행 · 7건 제외)
  요청: 비밀번호 규칙이 제대로 걸리는지 확인해줘
  이번 실행에서 제외한 케이스 (7건) — 아래는 통과한 것이 아니라 실행하지 않은 것입니다.
  · login-valid-001
  · login-email-required-002
  ...
```

마지막 문장이 핵심입니다. 노트 12의 '확인하지 않은 것' 과 같은 성격이라 같은 자리에
같은 모양으로 둡니다.

### 누가 골랐는지도 구분한다

첫 줄이 두 가지로 갈립니다.

```
자연어 요청으로 고른 실행            모델이 골랐다 (CLI --request)
요청을 확인한 뒤 사람이 승인한 실행    사람이 확인하고 골랐다 (웹 UI)
```

화면으로 돌린 실행을 "자연어 요청으로 고른" 이라고 적으면 **사람의 판단을 모델이 한
것처럼 기록**하게 됩니다. 도구가 한 판단을 감추는 것과 방향만 반대인 같은 부정확입니다.
실제로 화면을 띄워 보고 나서야 발견했습니다 — 정적으로는 어느 쪽 문장이 나오는지
눈에 띄지 않습니다.

## 왜 확장프로그램이 아니라 로컬 웹 UI 인가

"지금 보고 있는 페이지를 그대로 테스트하고 싶다" 는 요구가 있었습니다. 그러면
크롬 확장이 답처럼 보입니다. 뜯어 보면 세 조각입니다.

| 조각 | 확장이 필요한가 | 해결책 |
|---|---|---|
| 도달성 (localhost·VPN 뒤) | 아니오 | 로컬에서 도니까 이미 해결 |
| 인증 상태 (로그인된 세션) | 아니오 | Playwright `storage_state` |
| 지목 ("이 화면") | 여기만 유리 | URL 붙여넣기로 대부분 커버 |

결정적인 것은 **확장이 Playwright 도 LLM 도 돌릴 수 없다**는 점입니다. 확장으로 가도
로컬 러너는 어차피 있어야 하고, 그러면 확장이 하는 일은 "현재 탭 URL 을 넘기기" 로
줄어듭니다. 대안이 아니라 **트리거**입니다.

호스팅 웹사이트가 아닌 이유는 배포 구조가 답합니다(`docs/CHEETAH_SETUP.md`).

```
[CHEETAH A100 MIG]                    [로컬 Windows]
 vLLM (LLM+VLM) :8000  ←─SSH 터널─→  Prova (S1·S2·S6)
                                      Playwright + Chromium (S3·S4)
                                      SUT (FastAPI :8100)
```

**브라우저와 테스트 대상은 사용자 쪽에 있고 GPU 만 원격입니다.** 호스팅 서버는
`localhost:8100` 이나 사내 스테이징에 닿을 수 없습니다.

그리고 짚어 둘 것 — **Prova 의 판정은 항상 '기획서 대비' 입니다.** 확장 버튼을 눌러도
어느 기획서와 대조할지는 골라야 합니다. 이걸 없애면 "기획서 없이 화면만 보고 문제
찾기" 라는 다른 제품이 되고, 그건 우리 차별점을 버리는 방향입니다.

## 화면을 띄워 보고서야 나온 것들

정적 검사와 테스트로는 안 잡히던 것이 셋 있었습니다.

### 1. 제외된 케이스가 정보를 잃고 있었다

계획 화면이 제외된 케이스의 본문을 갖고 있지 않았습니다. `build_plan` 이 선택된 것만
`state.cases` 에 남기니, 서버가 이렇게 위조하고 있었습니다.

```python
TestCase.model_construct(case_id=cid, screen_id="", title=cid, violates=None, ...)
```

**확인 단계의 존재 이유가 "이 제외가 안전한가" 를 사람이 판단하는 것인데, 판단이 가장
필요한 행에 정보가 가장 없었습니다.** mock 이 항상 해석 실패로 전체를 고르는 바람에
가려져 있었습니다 — 전부 선택되면 제외 행이 아예 없으니까요.

선택으로 잃기 전에 원본을 붙들어 두는 것으로 고쳤습니다(`AgentState.all_cases`).
생성 순서도 함께 복원됐습니다.

### 2. 리포트의 증거 자료가 화면에서 전부 깨져 있었다

리포트는 스크린샷을 **상대 경로**로 참조합니다.

```html
<img src='login-password-min_length-005/step1.png'>
```

`/api/report/<run_id>` 로 리포트 파일만 돌려주면 그 경로가
`/api/login-password-.../step1.png` 로 풀려 **전부 404** 가 됩니다. 브라우저 콘솔에
404 가 12건 찍혀 있었습니다.

판정의 근거를 보여주는 것이 이 도구의 값인데, 그 근거가 화면에서 사라진 상태였습니다.
실행 디렉터리를 통째로 서빙해(`/runs/<run_id>/report.html`) 상대 경로가 옆 파일을
가리키게 고쳤습니다.

### 3. 색이 두 벌이었다

UI 의 accent 는 `#2c4b8a`, 리포트는 `#2f6fed` 였습니다. 리포트는 다크모드도 없어
UI 안에 iframe 으로 뜨면 혼자 하얗게 빛났습니다. **같은 화면 안에 파란색이 두 가지였던
셈입니다.**

`theme.py` 의 `TOKENS_CSS` 하나로 합쳤습니다. 웹 UI 는 `/static/tokens.css` 로 받고,
리포트는 같은 문자열을 인라인합니다(리포트는 자기완결 단일 HTML 이어야 하므로).
그리고 **색을 두 곳에서 만들 수 없게 테스트로 막았습니다** — `report_builder.py` 와
`app.css` 에 색 리터럴이 있으면 실패합니다.

> 눈으로 확인하지 않으면 이 셋 중 어느 것도 안 나왔을 겁니다. 테스트는 전부 통과하고
> 있었으니까요. 화면이 있는 것을 만들 때는 화면을 봐야 합니다.

---

## 기술적 함정 하나

`sync_playwright` 는 **asyncio 이벤트 루프 안에서 호출할 수 없습니다.** FastAPI 는
이벤트 루프 위에서 도니까, 파이프라인을 요청 핸들러에서 그대로 부르면 Playwright 가
거부합니다.

그래서 작업은 반드시 별도 스레드에서 돕니다(`server/runner.py`). 그리고 동시 실행은
하나로 막았습니다 — 브라우저와 GPU 를 두 작업이 함께 쓰면 **대기 상한에 기대는 판정이
흔들립니다**(노트 15). 느린 것은 참을 수 있지만 판정이 흔들리는 것은 참을 수 없습니다.

## 직접 해보기

```powershell
# 테스트 대상 띄우기 (별 터미널)
uv run uvicorn sut.app:app --port 8100

# 1) 요청 없이 — 지금까지와 같다
uv run prova run --pdf fixtures/specs/login_spec.pdf --url http://localhost:8100/bad --backend mock

# 2) 요청으로 좁히기 — mock 에는 CaseSelection 응답이 없으므로
#    '해석 실패 -> 전체 실행' 으로 넘어지는 것을 볼 수 있다
uv run prova run --pdf fixtures/specs/login_spec.pdf --url http://localhost:8100/bad \

## 실모델로 재 본 것 (2026-08-19)

`scripts/probe_request_selection.py` 로 요청 10개를 측정했습니다. mock 은 미리 정한
답을 돌려주므로, 7B 가 실제로 어떻게 해석하는지는 이때 처음 봤습니다.

### 기준선 7/10 — 실패가 셋 다 같은 모양이었다

```
"이메일 입력 검증만 봐줘"      1건  (email-required 빠짐)
"회원가입이 잘 되는지 확인해줘"  1건 / 17건
"검색 결과가 제대로 나오는지"    4건 / 10건 (search-valid 빠짐)

**7B 는 "해당하는 것 전부" 가 아니라 "가장 잘 맞는 하나" 를 고릅니다.** 프롬프트에
"애매하면 넣는 쪽을 고르세요" 라고 적혀 있었지만 추상적인 지시는 먹지 않았습니다.

### 고친 것 1 — 프롬프트를 절차와 예시로

추상 규칙을 지우고 판단 절차 한 줄과 예시 세 개를 넣었습니다.

```
"이 케이스를 실행하지 않아도 사용자의 요청에 답할 수 있는가?"
답할 수 없으면 고릅니다.
```

그리고 이걸 못 박았습니다 — **"~만" 은 범위를 좁히라는 뜻이지 개수를 줄이라는
뜻이 아니다.**

### 고친 것 2 — 옮겨적기 실패 (더 중요했습니다)

프롬프트를 고치자 한 요청이 **0건 거부**로 떨어졌습니다. 원문을 보니 이랬습니다.

```
모델: signup-password_required-004         실제: signup-password-required-004
모델: signup-password_confirm_same_as-009  실제: signup-password_confirm-same_as-009
```

**모델의 판단은 정확했습니다.** 비밀번호 관련 6건을 제대로 골랐는데, `case_id` 를
옮겨 적으면서 구분자를 `_` 로 통일해 버렸습니다. `case_id` 는 이음쇠가 `-` 이고
요소 id(`password_confirm`)와 규칙 이름(`same_as`)에 `_` 가 들어갑니다 — 사람도
틀릴 모양입니다.

6건 전부 무효가 되어 0건 거부. **옮겨적기 실패가 올바른 판단을 통째로 날렸습니다.**

여기서 배울 것: **"모델이 틀렸다" 로 뭉뚱그리면 원인을 놓칩니다.** 판단이 틀린 것과
옮겨 적다 틀린 것은 고칠 곳이 다릅니다. 프롬프트만 계속 고쳤다면 이건 안 나왔습니다.

구분자·대소문자를 지운 뒤 **유일하게 대응될 때만** 고쳐 읽게 했습니다. 둘 이상에
걸리면 읽지 않습니다 — 엉뚱한 케이스를 실행하는 것이 안 하는 것보다 나쁩니다.
실제 기획서 넷의 케이스 46개에서 충돌은 없었습니다. 그리고 고쳐 읽은 사실을 경고로
남깁니다.

```
! 모델이 쓴 'signup-password_confirm_same_as-009' 를
  'signup-password_confirm-same_as-009' 로 읽었습니다 (구분자만 다릅니다).
```

없던 케이스를 만들어내지 않으므로 **부분집합 보장은 그대로입니다.**

### 결과 9/10, 그리고 남은 1건

```
"회원가입이 잘 되는지 확인해줘"  6건 / 17건
근거: "모든 필수 입력 항목과 그에 따른 위반 케이스를 모두 고른다"
빠뜨림: email-format, password-min_length, password_confirm-same_as
```

`required` 는 다 골랐는데 형식·길이 규칙을 빠뜨립니다. "형식·길이 규칙도 전부
고르세요" 를 명시해도 안 고쳐졌습니다. **프롬프트만으로는 7B 가 화면 하나의
케이스 17개를 빠짐없이 세게 만들지 못합니다.**

측정 세트가 10건이고 그 세트를 보면서 프롬프트를 고쳤으므로, 이 9/10 은
**과적합됐을 수 있습니다.** 새 기획서에서 다시 재야 합니다.

### 남은 1건의 방어선 — 화면별 확인 범위

프롬프트로 못 고치는 것은 **보이게** 만들었습니다. 선택 결과를 화면·흐름 단위로
세고(`ScreenCoverage`), **요청이 화면을 이름으로 지목했는데 일부만 골라진 경우**
(named + partial) 계획 화면과 리포트가 이렇게 짚습니다.

```
⚠ '회원가입' 화면은 17건 중 6건만 실행됩니다
  요청이 이 화면을 가리켰지만 일부만 골라졌습니다. 이대로 실행하면
  이 화면의 통과율은 화면 전체의 상태를 뜻하지 않습니다.
```

"11건 제외" 만 보이면 그 화면을 확인했다고 읽히기 때문입니다. 계획 화면에서는
사람이 체크를 바꿀 때마다 다시 세고, 도로 다 켜면 경고가 사라집니다.

반대로 "비밀번호 규칙만 봐줘" 처럼 **규칙을 지목한** 요청에는 이 경고를 내지
않습니다 — 일부 실행이 의도이기 때문입니다. 그때도 경고하면 늑대 소리가 되어
진짜 경고가 묻힙니다. 흐름은 화면과 따로 셉니다(`TestReport.summarize` 와 같은
판단 — 흐름 케이스의 screen_id 는 마지막 화면이라 합치면 그 화면 것처럼 읽힙니다).
