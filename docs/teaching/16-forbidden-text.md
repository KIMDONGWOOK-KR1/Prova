# 16 · 없어야 할 것이 없는가

이전: [15-async-rendering.md](15-async-rendering.md) — 검증 대상 웹앱도 우리가 만들었다

---

## 미뤄 뒀던 화면

명세서 §0-2 의 1차 범위에 네 화면이 있습니다 — 로그인·회원가입·검색·**아이디/비밀번호 찾기**.
마지막 하나를 이렇게 판단해서 미뤘습니다.

> 기존 기계로 대부분 덮인다 — 이메일 형식 검증과 에러 문구 대조가 대부분이어서
> 로그인의 부분집합에 가깝다.

**반쯤 맞았습니다.** 입력 검증은 실제로 로그인의 부분집합입니다. 그런데 이 화면에는
지금까지 없던 종류의 요구사항이 하나 있었습니다.

---

## 방향이 반대인 요구사항

실물 서비스의 비밀번호 찾기 화면에는 보안 요구사항이 하나 붙습니다.

```
§5 보안 요구사항

계정 존재 여부를 알려주지 않는다. 입력한 이메일이 등록되어 있든 없든 화면의
반응은 완전히 같아야 한다.
```

등록 여부에 따라 다른 문구를 노출하면 어떻게 되는지 생각해 보면 이유가 보입니다.

```
공격자가 이메일 목록을 넣어 본다
  a@x.com → "재설정 메일을 보냈습니다."      가입되어 있다
  b@x.com → "등록되지 않은 이메일입니다."    가입되어 있지 않다
```

**이 화면이 계정 목록을 알려주는 도구가 됩니다.** account enumeration 이라는 실제
취약점이고, 로그인 화면이 '이메일 또는 비밀번호가 올바르지 않습니다' 처럼 뭉뚱그려 답하는
것과 같은 이유로 막습니다.

그런데 지금까지 이 도구가 확인한 것은 **전부 '있어야 할 것이 있는가'** 였습니다.

| 판정 유형 | 확인하는 것 |
|---|---|
| `error_message` | 이 문구가 떴는가 |
| `text_visible` | 이 문구가 보이는가 |
| `result_count` | 몇 개가 렌더됐는가 |
| `options_present` | 이 항목들이 있는가 |
| `placeholders_match` | 안내 문구가 같은가 |
| `labels_findable` | 라벨로 찾을 수 있는가 |

**하나도 없습니다** — '이것이 없는가' 를 확인하는 것이.

---

## `expect_text` 로 표현할 수 없다

처음에는 기존 것으로 될 것 같았습니다. 미등록 이메일에도 "재설정 메일을 보냈습니다." 가
떠야 하니, `text_visible` 로 그 문구를 확인하면 되지 않을까.

**안 됩니다.** 이런 화면이 가능합니다.

```
재설정 메일을 보냈습니다.
등록되지 않은 이메일입니다.
```

성공 문구가 떠 있으니 `text_visible` 은 **통과합니다.** 그런데 이 화면은 계정 존재 여부를
그대로 알려주고 있습니다. 요구를 어겼는데 초록불입니다.

> **있어야 할 것과 없어야 할 것은 다른 확인이다. 필드도 판정도 달라야 한다.**

`Scenario` 의 문서가 이 상황을 미리 적어 뒀습니다.

> 나중에 건수를 DOM 에서 직접 세거나 URL 을 확인해야 하면 **필드를 추가**한다.
> 이 필드의 의미를 넓혀 재해석하면 안 된다 — 필드 이름이 할 수 있는 일을 말하고
> 있어야 한다.

그래서 `expect_absent` 를 추가하고 판정 유형 `text_absent` 를 뒀습니다.

## 기획서가 그것을 적을 자리

표에 열 하나를 더했습니다.

```
| 이메일          | 노출돼야 하는 문구      | 노출되면 안 되는 문구      |
| user@test.com   | 재설정 메일을 보냈습니다. | 등록되지 않은 이메일입니다. |
| nobody@test.com | 재설정 메일을 보냈습니다. | 등록되지 않은 이메일입니다. |
```

**두 번째 행이 §5 의 요구사항 그 자체입니다.** `nobody@test.com` 은 등록되지 않은
이메일인데 등록된 것과 똑같은 문구가 나와야 합니다.

### 이 열을 어떻게 찾는가

건수 열은 **값의 모양**으로 찾습니다 — 비어 있지 않은 칸이 전부 정수인 열. 표현("결과
건수"·"개수"·"건수")에 흔들리지 않는 방법입니다.

**금지 문구 열에는 그 방법을 쓸 수 없습니다.** 값이 그냥 문구라서 기대 문구 열과 모양이
같습니다. 그래서 헤더로 찾습니다.

```python
_FORBIDDEN_HEADER_RE = re.compile(
    r"안\s*되는|안\s*됨|안돼|금지|노출되지|없어야|보이지\s*않"
)
```

기획서마다 다르게 쓸 표현을 넉넉히 받고, 못 찾으면 이 검증을 만들지 않습니다 —
억측하지 않습니다.

**두 열이 섞이면 최악입니다.** 성공 문구를 '나타나면 안 되는 것' 으로 읽으면 그 문구를
올바르게 띄우는 정상 구현이 FAIL 이 됩니다. 그래서 헤더 판별을 테스트로 못 박았습니다 —
`노출돼야 하는 문구` 가 금지 열로 잡히지 않는 것까지.

## 필드를 추가하면서 조용히 버려진 곳

`Scenario` 에 필드를 넣고 표 독해까지 고쳤는데 **금지 문구 케이스가 하나도 생성되지
않았습니다.** 리포트는 정상으로 보였습니다.

원인은 여기였습니다.

```python
# 비교는 필드를 갖춘 형태로 맞춰서 한다.
declared = [
    {"given": dict(d.get("given", {})), "expect_text": d.get("expect_text", ""),
     "expect_count": d.get("expect_count")}     # <- expect_absent 가 없다
    for d in declared
]
```

이 정규화는 원래 **불필요한 경고를 막으려고** 만든 것입니다. 표에서 읽은 dict 에
`expect_count` 가 없고 모델 쪽에는 `None` 이 있으면 값이 같은데도 다르다고 판정되어 매
실행마다 경고가 뜹니다. 매번 뜨는 경고는 정작 중요한 경고를 묻습니다.

옳은 장치인데, **필드 목록을 손으로 적어 둔 곳**이라 새 필드가 조용히 사라졌습니다.
키 목록을 한 곳에 모으고 주석으로 못 박았습니다.

> **필드를 추가할 때 함께 고쳐야 하는 곳이 어디인지, 코드가 말해 주게 만들어야 한다.**

이번엔 실패가 눈에 보였습니다(케이스 수가 7이었고 9여야 했습니다). 만약 이 화면에 다른
케이스가 많았다면 두 건이 빠진 것을 알아채지 못했을 것입니다.

---

## 한 결함이 FAIL 두 건인 이유

`bad` 에 심은 결함은 하나입니다 — 미등록 이메일에 다른 문구를 노출한다.

```
FAIL find_account-scenario-005   문구 '재설정 메일을 보냈습니다.' 미노출
FAIL find_account-absent-005     노출되면 안 되는 문구가 화면에 있음: '등록되지 않은 이메일입니다.'
```

**중복 보고가 아닙니다.** 두 경로는 서로를 대신하지 못합니다.

- 구현이 성공 문구를 **아예 안 띄우면** 앞의 경로가 잡습니다
- 구현이 성공 문구를 띄우면서 금지 문구도 **함께** 띄우면 앞의 경로는 통과하고
  뒤의 경로만 잡습니다

검색 화면의 대소문자 결함이 문구·건수 두 경로에 잡힌 것과 같은 구조입니다. 같은 결함이 두
곳에서 보이는 것과, 한 곳에서만 보일 수 있는 결함을 놓치는 것 중에서는 앞쪽이 낫습니다.

그리고 사유가 다릅니다. 앞쪽은 **기능이 안 된다**, 뒤쪽은 **기능은 되는데 알려주면 안 되는
것을 알려준다.** 고칠 곳이 다릅니다.

## 등록된 이메일에서는 통과한다

```
absent-004  user@test.com   (등록됨)   PASS
absent-005  nobody@test.com (미등록)   FAIL
```

누출은 미등록 이메일에서만 일어나므로 이게 맞습니다. 둘 다 실패하면 판정이 '금지 문구가
있는가' 가 아니라 다른 것을 보고 있다는 뜻이고, 그래서 테스트로 못 박았습니다.

## 확장 정확도를 함께 늘렸다

`tests/test_s1_golden.py` 의 문서가 이 상황을 경고해 뒀습니다.

> `SPECS` 에 화면을 추가하면 그 화면에도 같은 강도의 대조가 걸린다. 화면을 늘릴 때
> 정확도 측정이 함께 늘어나지 않으면, **확장된 부분만 측정되지 않은 상태**가 된다.

그래서 새 화면을 넣었고 골든 대조가 54 → 69 로 늘었습니다.

그 문서가 경고한 것이 하나 더 있었습니다.

> 프롬프트의 few-shot 예시는 이 화면들과 겹치지 않는 화면('비밀번호 변경')을 쓴다.
> 예시가 측정 대상과 같으면 기획서를 읽어서 맞힌 것인지 예시를 베낀 것인지 구분할 수
> 없다. **화면을 추가할 때 그 예시와 주제가 겹치지 않는지 확인해야 한다.**

few-shot 이 '비밀번호 **변경**'(`/password-change`)이고 새 화면이 '비밀번호 **찾기**'
(`/find-account`)입니다. 이름이 인접합니다. 내용은 다릅니다(예시는 현재/새 비밀번호 입력,
이 화면은 이메일 하나). 실측에서 베낌은 없었지만, 그 판단을 골든 대조에 맡겼습니다.

### 통합 문서에는 넣지 않았다

통합 문서 픽스처가 확인하는 것은 **분할이 되는가** 입니다 — 한 문서를 화면별로 갈랐을 때
단일 문서와 같은 명세가 나오는지. 그 성질은 화면 종류가 아니라 분할기에 대한 것이고, 세
화면으로 이미 성립합니다.

화면을 늘릴 때마다 통합 문서에 넣으면 그 테스트의 기대값(케이스 총계·화면별 내역·흐름)이
계속 흔들리는데 얻는 신호는 없습니다. 그래서 목록을 둘로 나눴습니다(`SPECS` /
`MULTI_SPECS`).

**측정을 늘리는 것과 아무 데나 늘리는 것은 다릅니다.**

## 이 노트에서 남길 것

1. **'기존 기계로 덮인다' 는 판단은 절반만 맞을 수 있다.** 입력 검증은 정말 로그인의
   부분집합이었습니다. 그런데 화면마다 그 화면만의 요구사항이 하나씩 있었고, 그게 매번
   도구의 표현력을 늘렸습니다.
2. **지금까지 한 확인의 '방향' 을 물어보라.** 판정 유형 여섯 개가 전부 '있어야 할 것이
   있는가' 였습니다. 반대 방향이 하나도 없다는 것을 알아채는 데 화면 네 개가 걸렸습니다.
3. **필드의 의미를 넓혀 재해석하지 마라.** `text_visible` 로 금지 문구를 확인하려 하면
   '성공 문구와 금지 문구가 함께 떠 있는 화면' 을 통과시킵니다. 필드 이름이 할 수 있는
   일을 말하고 있어야 합니다.
4. **값의 모양으로 찾을 수 없는 것은 헤더로 찾는다.** 건수는 정수라서 모양으로 가릴 수
   있지만 금지 문구는 기대 문구와 모양이 같습니다. 방법을 하나만 고집하면 안 됩니다.
5. **두 열을 섞으면 올바른 구현이 실패한다.** 성공 문구를 금지 문구로 읽으면 정상 화면이
   FAIL 이 됩니다. 열 판별을 테스트로 못 박아야 합니다.
6. **필드를 추가할 때 조용히 버려지는 곳이 있다.** 손으로 적은 필드 목록이 그런 곳입니다.
   이번엔 케이스 수가 눈에 보여서 알았고, 다른 케이스가 많았다면 몰랐을 것입니다.
7. **한 결함이 두 곳에서 보이는 것은 괜찮다.** 한 곳에서만 보일 수 있는 결함을 놓치는
   것보다 낫습니다. 다만 사유가 달라야 합니다 — '기능이 안 된다' 와 '알려주면 안 되는
   것을 알려준다' 는 고칠 곳이 다릅니다.
8. **측정을 늘리는 것과 아무 데나 늘리는 것은 다르다.** 골든 대조에는 넣고 통합 문서에는
   넣지 않았습니다. 통합 문서는 분할기를 확인하는 픽스처이고, 화면을 늘려도 새 신호가
   없습니다.
