# 12 · 기획서에 적혀 있는데 아무도 확인하지 않는 것

이전: [11-multi-screen-flows.md](11-multi-screen-flows.md) — 한 문서 여러 화면, 화면 사이

---

## 앞 노트가 남긴 물음

11번 노트에서 얻은 것이 하나 있었습니다.

> 기획서에 적혀 있는데 아무도 확인하지 않는 항목이 있으면, 그건 기획서가 아니라
> **도구의 구멍**이다.

'유형' 열이 그랬습니다. 우리 액션을 고르는 데만 쓰이고 구현과 대조되지는 않았습니다.
그렇다면 **다른 구멍도 같은 방식으로 찾을 수 있어야 합니다.** 이 노트가 그 이야기입니다.

먼저 모델의 필드를 하나씩 물었습니다 — *이건 검증되는가, 그냥 쓰이는가, 무시되는가?*

| 기획서가 적는 것 | 지금 상태 |
|---|---|
| `constraints` | 검증됨 (이 프로젝트의 핵심) |
| `error_message` | 검증됨 (문구 대조) |
| `required` | 검증됨 (미입력 케이스) |
| `label` | 검증됨 (못 찾으면 탐지 실패) |
| `url_path` | 검증됨 (404 면 page_error) |
| `type` | 검증됨 (11번 노트에서 추가, 버튼·링크만) |
| `scenarios` | 검증됨 |
| `success_condition` | 검증됨 |
| `sample_value` | 입력에 쓰임 — 구현에 대한 주장이 아니므로 검증 대상이 아님 |
| **`options`** | **쓰이기만 함** ← 구멍 |
| **`failure_conditions`** | **일부만** ← 구멍 |
| **`placeholder`** | **기획서가 아예 안 적음** ← 반대 방향의 구멍 |

구멍이 셋 나왔습니다. 그리고 두 번째를 파 보니 **가장 처음 만든 화면**에 구멍이
있었습니다.

## 구멍 1: 선택 목록은 값을 고르는 데만 쓰였다

회원가입 기획서가 이렇게 적습니다.

```
| signup_path | 선택 | 가입 경로 | 필수 | 선택 목록: 검색, 지인 추천, 광고 | ... |
```

이 목록이 하는 일은 하나뿐이었습니다 — **정상 케이스가 넣을 값을 고르는 것.** 첫 항목
'검색' 을 골라 넣고, 그 항목이 화면에 있으니 통과합니다.

그래서 화면에 '지인 추천' 이 빠져 있어도 **아무 일도 일어나지 않습니다.** 케이스가
넣는 값은 '검색' 과 ''(미선택) 뿐이므로 나머지 항목은 한 번도 건드려지지 않습니다.

선택 항목 누락은 흔한 결함입니다. 기획서에 목록이 적혀 있는데 확인하지 않고 있었습니다.

### 요소마다 케이스 한 건

```
signup-options-signup_path-015   가입 경로 선택 목록이 기획서와 같은지 확인
```

**선택 요소를 조작하는 케이스마다 대조하지 않습니다.** 그러면 항목 하나가 빠진 결함이
그 요소를 쓰는 모든 케이스에서 터집니다 — 회원가입은 16건입니다. 결함 하나가 FAIL
14건이 되면 리포트를 읽는 사람이 규모를 잘못 읽습니다.

스텝은 `navigate` 하나뿐입니다. 선택 항목은 화면에 들어간 시점에 이미 정해져 있으므로
입력하고 제출할 이유가 없고, 필요 없는 스텝은 실패 지점만 늘립니다.

### 빠진 것만 본다

화면에 항목이 더 있어도 통과입니다. 안내용 첫 항목('선택하세요')을 걸러내려면 무엇이
안내인지 추측해야 하는데, 추측하면 **기획서에 있는 항목을 안내로 착각해 없다고 보고할
수 있습니다.** 빠진 것만 보면 그 추측이 필요 없습니다.

항목이 더 있는 것도 불일치일 수 있지만, 그건 기획서가 '이 목록이 전부다' 라고 적어 둔
경우에만 결함입니다. 그 선언이 없으므로 단정하지 않습니다.

```
FAIL 가입 경로 선택 목록이 기획서와 같은지 확인
     '가입 경로' 에서 ['지인 추천'] 을(를) 찾을 수 없습니다.
     화면의 항목: ['선택하세요', '검색', '광고']
```

## 구멍 2: 검출기를 만들어 물어봤다

두 번째 구멍은 눈으로 찾지 않았습니다. **찾는 것을 코드로 만들었습니다.**

기획서가 적어 둔 **문구**를 모두 모으고, 그중 어떤 케이스의 기대값에도 들어가지 않는
것을 셉니다. 문구는 기획-구현 대조의 단위이고, 기획서에서 결정적으로 뽑을 수 있습니다.

```
요소별 error_message  ·  화면 공통 required_message
실패 조건 표의 인용 문구  ·  성공 조건의 인용 문구
예시 시나리오의 기대 문구
```

돌려 보니 이렇게 나왔습니다.

```
== login: 기획서 문구 5개 / 확인 4개
   미확인 [failure_conditions[4]] '이메일또는비밀번호가올바르지않습니다.'
== signup: 기획서 문구 8개 / 확인 8개
== search: 기획서 문구 4개 / 확인 4개
```

### 가장 처음 만든 화면에 있었다

로그인 기획서 §4 의 네 번째 행입니다.

```
| 등록되지 않은 계정 | "이메일 또는 비밀번호가 올바르지 않습니다." 노출, 이동하지 않음 |
```

**이 문구를 확인하는 케이스가 하나도 없었습니다.** 그런데 리포트는 여러 차례
'로그인 7/7 통과' 라고 보고했습니다. 이 노트를 쓰기 전까지 README 에도 그렇게 적혀
있었습니다.

왜 빠졌는지가 중요합니다. 그 상황은 **규칙을 다 지킨 값**으로만 만들 수 있습니다 —
이메일 형식도 맞고 비밀번호 복잡도도 맞는데 등록되지 않은 계정입니다. 위반값 생성으로는
도달할 수 없습니다. 검색 화면의 `scenarios` 와 정확히 같은 성질입니다.

그때 새로 만든 경로가 이번에도 답이었습니다. 기획서에 예시를 추가합니다.

```
## 6. 예시 동작

| 이메일 | 비밀번호 | 노출돼야 하는 문구 |
|---|---|---|
| nobody@test.com | Abcd123! | 이메일 또는 비밀번호가 올바르지 않습니다. |
```

**고친 곳이 코드가 아니라 기획서라는 점**이 이 작업의 성격을 말해 줍니다. 도구는
"확인할 수 없다" 고 알려 주고, 기획서가 확인 가능한 형태로 그 상황을 제시하면 기존
기계가 그대로 검증합니다.

그리고 이걸 닫자 `bad` 의 B3 결함이 **처음으로 자기 케이스를 갖게 됐습니다.**

```
FAIL 기획서 예시: email='nobody@test.com', password='Abcd123!'
     → '이메일 또는 비밀번호가 올바르지 않습니다.' 노출 확인
     문구 '이메일 또는 비밀번호가 올바르지 않습니다.' 미노출
```

B3(기획서와 다른 에러 문구)는 처음부터 심어 둔 세 결함 중 하나였는데, 그동안 자기
케이스 없이 **다른 FAIL 의 곁증거로만** 나타났습니다("다른 문구가 노출됨: '로그인 정보를
확인해주세요.'"). 심어 둔 결함이 리포트에 잡히는 것처럼 보였지만, 실제로는 그것을
확인하는 케이스가 없었습니다.

## 확인하지 않은 것을 리포트에 쓴다

검출기를 한 번 돌려 보고 버리지 않았습니다. **리포트에 항목으로 넣었습니다.**

```
확인하지 않은 것 (1건)
기획서에 적혀 있으나 이 실행에서 대조한 케이스가 없습니다.
아래 항목은 통과한 것이 아니라 확인하지 않은 것입니다.

· 실패 조건 4번에 적힌 "이메일 또는 비밀번호가 올바르지 않습니다." 을 확인하는
  케이스가 없습니다. 그 문구가 뜨는 상황을 값의 규칙만으로 만들 수 없다면,
  기획서가 예시 입력과 기대 문구를 짝으로 제시해야 검증할 수 있습니다.
```

### 경고가 아니라 별도 항목인 이유

이건 기획서의 결함도(`spec_defects`), 구현의 결함도(FAIL) 아닙니다. **검증 범위**에
대한 사실입니다. 경고 목록에 섞으면 '기획서를 고치라' 는 말로 읽히는데, 고칠 곳은
기획서일 수도 있고 이 도구일 수도 있습니다.

그리고 통과율 바로 옆에 놓습니다. **'36/36 통과' 라는 숫자의 범위를 그 자리에서 알 수
있어야 합니다.**

### 사유에 할 일을 적는다

'확인하지 않았다' 만 알려 주면 읽는 사람이 무엇을 해야 하는지 모릅니다. 대개 기획서가
**그 상황을 만들 입력을 제시하지 않은** 경우이므로, 그 말을 사유에 넣습니다.

### 못 찾는 것

문구가 없는 요구는 이 방식으로 보이지 않습니다. "정렬 순서는 최신순" 처럼 노출 문구가
없는 요구는 문구 대조로 셀 수 없습니다. 그건 이 검출기의 한계이고, **없는 것을 있는 척
하지 않습니다** — 테스트로도 못 박아 뒀습니다.

넓히려면 기획서가 확인 가능한 형태(예시 입력과 기대 결과)로 적어야 합니다. 도구가 할 수
있는 일은 '이건 확인할 수 없다' 를 정확히 말해 주는 것까지입니다.

## 구멍 3: 기획서가 아예 적지 않은 것

앞의 두 구멍은 '기획서에 있는데 확인하지 않는' 것이었습니다. 세 번째는 방향이
반대였습니다.

```
SUT     placeholder="이메일을 입력하세요"
기획서   (없음)
```

구현에 있는 UI 문구가 **기획서 관할 밖**이었습니다. 그러면 아무도 검증하지 않습니다 —
'아이디를 입력하세요' 로 바뀌어도 통과합니다. 안내 문구는 사용자가 **가장 먼저 읽는
글자**인데 그랬습니다.

`UIElement.placeholder` 필드는 처음부터 있었습니다. 그런데 쓰인 곳은 S3 의 **탐지
폴백**뿐이었습니다 — 라벨로 못 찾으면 placeholder 로 찾아 보는 용도입니다. 필드가
있다는 것과 그 값이 검증된다는 것은 별개입니다.

### 기획서에 열을 추가했다

```
| 요소 ID | 유형 | 라벨 | 필수 | 입력 검증 규칙 | 안내 문구 | 에러 메시지 |
```

'안내 문구' 를 '에러 메시지' 앞에 뒀습니다. 입력 시점의 안내가 실패 시점의 문구보다
먼저 오는 것이 사용자가 겪는 순서와 맞습니다.

`bad` 의 로그인 이메일 칸을 '아이디를 입력하세요' 로 바꿔 놓고 돌리면:

```
FAIL 입력 안내 문구 확인
     문구가 다름 — '이메일': 기대 '이메일을 입력하세요', 화면 '아이디를 입력하세요'
```

### 화면당 한 건으로 묶었다

선택 목록은 요소마다 한 건인데 안내 문구는 화면당 한 건입니다. 기준은 **무엇이 한 가지
확인인가**입니다.

선택 목록은 요소 하나가 목록 하나를 갖습니다. 목록이 길고, 어느 항목이 빠졌는지가 그
요소만의 사실이므로 요소가 곧 확인 단위입니다.

안내 문구는 요소마다 짧은 문구 하나입니다. 요소마다 케이스를 만들면 회원가입에서만
4건이 늘어나는데, 각 케이스가 확인하는 것은 문구 한 줄입니다. **리포트에 늘어나는 줄
수가 그 정보량보다 많습니다.** 대신 실패 사유에 어느 요소가 다른지 모두 적어, 한
건으로도 고칠 곳이 좁혀지게 했습니다.

### 없는 요소와 다른 문구를 구별한다

```
키가 없다   그 라벨의 요소를 화면에서 찾지 못했다
빈 문자열   요소는 있는데 placeholder 가 없다
```

개발자가 할 일이 다릅니다 — 하나는 요소나 라벨을 고치고, 하나는 속성을 넣습니다.

## 열 하나를 더한 대가: 표가 페이지를 넘어갔다

여기서 예상하지 못한 것이 나왔습니다. 요소 표가 7열이 되자 넓어져서, 회원가입 기획서의
**마지막 행이 다음 페이지로 밀렸습니다.**

PDF 는 표가 페이지를 넘어가면 헤더를 다시 그립니다. pdfplumber 는 그것을 **별개의 표 두
개**로 읽고, `_element_table()` 은 첫 표만 돌려줬습니다.

```
page 1 table 1: 요소 ID ... rows=8   ids: [email, password, ..., signup_btn]
page 2 table 0: 요소 ID ... rows=2   ids: [to_login]      <- 이게 사라졌다
```

`to_login` 이 `declared_element_ids` 에서 빠졌습니다. 그러면 **프롬프트에도 안 들어가고
누락 경고도 안 뜹니다** — 행을 빠뜨리지 않기 위해 만든 장치가 같은 이유로 무력해집니다.

헤더가 같은 표를 이어 붙이도록 고쳤습니다. 다른 표를 잘못 붙이면 없는 요소를 만들어내니,
헤더가 정확히 같을 때만 붙입니다.

**이건 내가 열을 추가해서 생긴 문제가 아닙니다.** 요소가 열 개 넘는 실물 기획서라면
열 여섯 개로도 페이지를 넘어갑니다. 열을 추가한 것이 **이미 있던 버그를 드러냈을 뿐**
입니다.

## 결과

로컬 7B 실측입니다.

| 화면 | good | bad |
|---|---|---|
| 로그인 | **9/9** | **3 PASS / 6 FAIL** |
| 회원가입 | **16/16** | **12 PASS / 4 FAIL** |
| 검색 | **9/9** | **5 PASS / 4 FAIL** |
| 통합 문서 (3화면 + 흐름 2) | **36/36** | **20 PASS / 16 FAIL** |

로그인이 7건에서 9건으로, 회원가입이 14건에서 16건으로, 검색이 8건에서 9건으로
늘었습니다. **늘어난 다섯 건이 그동안 확인하지 않던 것입니다.** 그리고 `bad` 의 FAIL 이
늘어난 것은 이 도구가 나빠진 것이 아니라, 이미 있던 결함을 이제야 보게 된 것입니다.

전체 테스트는 **366개**(이후 픽스처 일관성 검사를 더해 374개), S1 골든 대조는 54/54입니다. 커버리지 검출기 자체도 테스트로
잡아 뒀습니다 — 시나리오를 다시 빼면 다시 보고하는지까지 확인합니다.

## 이 노트에서 남길 것

1. **구멍을 찾는 방법을 코드로 만들면 눈으로 못 본 것이 나온다.** 가장 처음 만든
   화면에, 여러 차례 '전부 통과' 로 보고한 화면에 구멍이 있었다. 사람이 세는 것으로는
   못 찾았을 것이다.
2. **필드마다 물어야 한다 — 이건 검증되는가, 그냥 쓰이는가?** 기획서의 값이 우리 쪽
   동작을 고르는 데만 쓰이고 구현과 대조되지 않으면, 그 값은 검증에 아무 영향을 주지
   않는다. `options` 와 `type` 이 둘 다 그랬다.
3. **확인하지 않은 것을 리포트에 쓴다.** FAIL 은 눈에 띄지만 '확인하지 않음' 은 아무
   흔적도 남기지 않는다. 통과율 옆에 그 범위를 적어야 숫자를 신뢰할 수 있다.
4. **결함 하나가 FAIL 여러 건이 되지 않게 한다.** 선택 목록 대조를 요소를 쓰는 케이스마다
   붙이면 결함 하나가 FAIL 14건이 된다. 집계가 규모를 왜곡한다.
5. **고칠 곳이 코드가 아닐 수도 있다.** 로그인의 구멍은 기획서가 예시를 제시하자 기존
   기계로 그대로 닫혔다. 도구가 할 일은 '이건 확인할 수 없다' 를 정확히 말하는 것이다.
6. **한계를 테스트로 못 박는다.** 문구 없는 요구는 이 검출기가 못 본다. 그 사실을
   테스트로 남겨야 나중에 '다 본다' 고 착각하지 않는다.
7. **필드가 있다는 것과 그 값이 검증된다는 것은 별개다.** `placeholder` 필드는 처음부터
   있었지만 탐지 폴백으로만 쓰였다. 모델에 자리가 있는 것을 '다루고 있다' 로 착각하기
   쉽다.
8. **구멍은 양방향이다.** '기획서에 있는데 확인하지 않는 것' 과 '구현에 있는데 기획서가
   안 적은 것' 은 다른 구멍이고, 뒤쪽은 기획서를 고쳐야 닫힌다.
9. **작은 변경이 이미 있던 버그를 드러낸다.** 열 하나를 더하자 표가 페이지를 넘어가
   행이 사라졌다. 내가 만든 버그가 아니라 실물 기획서에서 먼저 터질 버그였다 — 픽스처를
   실물에 가깝게 만드는 것 자체가 검증이다.
