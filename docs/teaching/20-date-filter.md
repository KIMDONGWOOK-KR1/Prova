# 20 · 날짜 필터 — 조작한 뒤의 화면을 검증한다

이전: [19-preconditions-self-consistency.md](19-preconditions-self-consistency.md) — 전제가 있는 화면과 자기일관 판정

---

## 무엇이 새로운가

지금까지의 컬렉션 검증(정렬·합계·건수)에는 공통 가정이 하나 숨어 있었습니다 —
전부 **진입 직후 화면**에 대한 것이었다는 점입니다. navigate 한 번이면 검증할
화면이 그대로 있었습니다.

날짜 필터는 그 가정을 깹니다. 시작일·종료일을 **입력하고**, 조회 버튼을
**누르고**, 그 **재조회 결과**가 검증 대상입니다. 스텝을 밟아야만 존재하는
화면이 처음 생긴 것입니다.

```
지금까지   navigate → 판정
이번       navigate → fill(시작일) → fill(종료일) → click(조회) → 판정
```

새 기계는 없습니다 — fill·click 은 로그인 폼이 쓰던 스텝 그대로이고, 판정도
기존 유형(result_count·sorted_desc·sum_matches·text_visible·text_absent)
그대로입니다. 새로운 것은 **무엇을 기대할 것인가**입니다.

---

## 필터가 무엇인지는 기획서가 정한다

도구가 "날짜 입력 두 개와 버튼이 있으니 필터겠지" 라고 추측하게 두지
않았습니다. 기획서에 절을 하나 더 받습니다 (`orders_spec.md` §6):

| 항목 | 값 |
|---|---|
| 시작일 요소 | 시작일 |
| 종료일 요소 | 종료일 |
| 조회 버튼 | 조회 |
| 대상 목록 | 주문 목록 |
| 날짜 컬럼 | 주문일 |
| 빈 결과 문구 | 기간 내 주문이 없습니다. |

이 표를 `declared_date_filter()` 가 결정적으로 읽고(시드 표·전제 계정 표와
같은 패턴), `ScreenSpec.date_filter` 에 싣습니다. **표가 없으면 LLM 이 필터를
지어냈어도 버립니다** — 시드 표 교정보다 한 걸음 더 갑니다. 씨앗 데이터는
모델의 읽기가 보탬이 될 여지가 있지만, 필터는 '무엇을 채우고 무엇을 눌러
무엇을 다시 세는가' 라는 **실행 지시**라서, 틀리면 엉뚱한 요소를 조작한 결과를
검증 결과라고 말하게 됩니다 (`_apply_declared_date_filter`).

## 기대값의 근거를 두 층으로 뒀다

필터를 적용한 뒤의 화면에 무엇을 기대해야 할까요. 한 층만 쓰면 각각 구멍이
있습니다.

| 근거 층 | 무엇을 잡나 | 무엇을 못 잡나 |
|---|---|---|
| **시드 표 기반** — 기획서 §5 표에서 기간 내 행 수·포함/제외 주문번호를 계산 | 행 누락·경계일 제외·필터 미적용 | 합계 미재계산 — 합계는 시드가 아니라 화면이 계산하는 값 |
| **자기일관성** — 필터 후에도 '표시된 행의 합 = 합계', '주문일 내림차순' 이 성립하는가 | 합계 미재계산·정렬 붕괴 | 행이 통째로 빠지는 것 — 빠진 행끼리도 자기일관일 수 있다 |

그래서 병행합니다 (`generator._filter_cases`). 심은 결함이 그 필요를
증명합니다 — **O3(시작일 경계 제외)는 시드 층만, O4(필터 후 합계 미재계산)는
자기일관성 층만** 잡습니다.

기간도 임의로 잡지 않습니다. 시드의 고유 날짜를 정렬해 **양끝을 하나씩 남기고**
잡습니다(`start=dates[1], end=dates[-2]`) — 양끝 밖에 각 1건 이상이 남아
'걸러졌는가' 를 셀 수 있고, 경계가 실제 주문일이라 '경계일 포함' 이 우연이
아니라 설계로 검증됩니다.

케이스는 8종입니다 (모두 kind `filter` — 한 검증의 여덟 면이므로 선택
넓히기 R1 이 묶음으로 다룹니다):

| # | 기대 | 근거 층 | bad 에서 |
|---|---|---|---|
| 1 | 기간 내 행 수(3건) | 시드 | **FAIL** (O3: 2건) |
| 2 | 시작 경계일 주문번호 표시 | 시드 | **FAIL** (O3) |
| 3 | 기간 밖 주문번호 미표시 | 시드 | PASS |
| 4 | 표시 행의 합 = 합계 | 자기일관 | **FAIL** (O4) |
| 5 | 정렬 유지 | 자기일관 | **FAIL** (O1 이 필터 화면에도 남는다) |
| 6 | 빈 기간 → 0건 | 시드 | PASS |
| 7 | 빈 기간 → 빈 결과 문구 | 기획서 | PASS |
| 8 | 빈 값 → 전체 5건 | 시드+기획서 | PASS |

good 은 14/14 PASS(기존 6 + filter 8), bad 는 위 네 건 + 무필터 정렬·합계
(O1·O2) 여섯만 FAIL — 오탐 0. `table`/`badtable` 쌍둥이도 같은 판정입니다
(`test_orders_e2e.py`).

만들 수 없으면 경고합니다 — 필터 절은 있는데 시드 표가 없거나, 날짜 열이
안 읽히거나, 고유 날짜가 3개 미만이면 케이스를 만들지 않고 그 사실을
남깁니다. 반대로 필터 절 자체가 없는 화면은 침묵합니다(필터 없는 화면이
정상이므로).

## 더하면서 깨질 뻔한 것 둘

**요소 유형 '입력' 이 정상 케이스를 깨뜨릴 뻔했습니다.** 시작일을 유형 '입력'
으로 적으면 정상 케이스 생성이 이 필드에 자유 문자열 견본값을 채우려 하는데,
`input[type=date]` 는 ISO 날짜만 받아 fill 이 터집니다. 유형 **'날짜'**
(`ElementType "date"`)를 신설해 자동 채움에서 빼는 것으로 해결했습니다 —
날짜 입력의 값은 filter 케이스가 시드에서 계산해 넣는 값뿐입니다.

**표가 페이지 경계에서 조용히 잘렸습니다.** §2 에 요소 3행을 더하자 §5 시드
표가 페이지를 넘어갔고, PDF 생성기가 다음 페이지에 머리글을 반복하며 표가 두
조각이 됐습니다. `declared_seed_rows` 는 절 제목 뒤 첫 표만 읽으므로 마지막
행이 사라졌습니다 — **건수 케이스가 "5행 기대, 4행 추출" 로 잡아 줬습니다.**
검증이 검증 도구의 회귀를 잡은 셈입니다. 이번에는 기획서에 페이지 나눔을 넣어
피했지만 실물 기획서는 페이지를 조정할 수 없으므로, 머리글이 같은 연속 표를
잇는 파싱이 '남은 것' 에 올라갔습니다.

## 홀드아웃 집합의 정의가 함께 커졌다

orders 화면의 케이스가 6건 → 14건이 되면서(새 요소들의 labels 1 + filter 8),
홀드아웃 B 의 "화면 지목(전 종류)" 기대 목록도 기계적으로 갱신했습니다. 판정
기준을 바꾼 것이 아니라 '전 종류' 의 정의가 커진 것이지만, **갱신 후 수치는
기존 B 9/10 과 1:1 비교할 수 없습니다.** 재측정은 실물 기획서 측정 때 함께
합니다 (`docs/measurements/request-selection-2026-08-22.md` 추기).
