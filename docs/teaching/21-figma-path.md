# 21 · Figma 경로 — 디자인을 검증 계약으로 읽는다

이전: [20-date-filter.md](20-date-filter.md) — 조작한 뒤의 화면을 검증한다

---

## 무엇이 새로운가

지금까지 검증의 근거는 전부 **문서(기획서 PDF)** 였습니다. 실무에는 근거가 하나
더 있습니다 — 디자인 파일. 화면이 어떻게 생겨야 하는지는 기획서보다 Figma 가
먼저, 더 구체적으로 말합니다.

이 노트는 Figma 파일을 PDF 와 **같은 계약**(`SpecDocument`/`ScreenSpec`)으로
읽어 파이프라인에 넣은 이야기입니다. S2 이후는 한 글자도 바뀌지 않았습니다 —
계약을 하나로 유지했기 때문에 입력이 늘어도 판정·리포트는 그대로입니다.

## 첫 시도는 왜 폐기됐는가

계획 단계에 만들었던 첫 추출기는 노드 **이름**에 'button' 이나 '입력' 이
들어가면 요소로 주웠습니다. Figma 튜토리얼 파일로 시험하자 본문 문장 프레임까지
버튼이 됐습니다 — "1. Share this file Try sharing this…" 같은 안내 문단이
이름에 button 을 담고 있었기 때문입니다.

이름은 디자이너의 자유 텍스트라서 유형의 근거가 못 됩니다. 근거가 되는 것은
**구조**입니다 — INSTANCE 노드의 `componentId` 가 가리키는 원본 컴포넌트
이름은 디자인 시스템의 구조입니다. 그래서 다시 만든 파서는 컴포넌트 이름
(`Input`/`Button`/`Checkbox`/`Select`/`List`)만 믿고, 컴포넌트가 아닌 노드는
요소처럼 보여도 줍지 않고 **경고**합니다. 표에 그대로 적힌 사실만 결정적으로
옮긴다는 S1 의 원칙(노트 2)이 입력만 바뀐 채 그대로 적용된 것입니다.

같은 이유로 이 경로는 **LLM 을 부르지 않습니다.** PDF 는 자연어라 구조화에
모델이 필요했지만, Figma 응답은 이미 트리입니다. 여기에 모델을 끼우면 검증
가능한 사실이 검증 불가능한 추측으로 바뀝니다.

## Figma 가 말하지 않는 것 — 그리고 그걸 채우는 척하지 않기

Figma 디자인에는 세 가지가 없습니다.

| 없는 것 | 대응 |
|---|---|
| 검증 규칙 ("8자 이상") · 성공 조건 · 테스트 계정 | 비워 둔다. 리포트가 "입력: Figma — 정적 대조만 수행" 상자로 검증 범위를 말한다 |
| 화면의 경로(`/login`) | 실행 시 사용자가 `--screen-url 로그인=/login` 으로 준다. 매핑 없는 화면은 실행하지 않고 경고 |
| 흐름의 도착 판정 근거(문구·경로) | prototype 연결은 `flows` 로 추출하되 흐름 **케이스는 만들지 않는다** |

여기서 구현 중 가장 값진 발견이 나왔습니다. 스펙 초안은 "규칙 없는 스펙에서
생성기가 자연히 정적 케이스만 만든다" 고 가정했는데, **틀렸습니다** —
`generate_cases` 는 정상(valid) 케이스를 무조건 만듭니다. 성공 조건 없는 Figma
스펙에서 그 케이스는 임의 값을 제출하고, 로그인 화면은 당연히 에러를 띄우고,
판정은 FAIL 이 됩니다. **구현이 옳은데 FAIL — 오탐입니다.**

그래서 `ScreenSpec.source_kind` 를 신설했습니다. figma 출처 스펙에서 S2 는
근거가 있는 세 가지만 만듭니다:

    labels_findable      디자인의 요소가 구현 화면에 있는가
    placeholders_match   안내 문구가 디자인과 같은가
    options_present      선택 항목이 디자인과 같은가

이 셋이 실무의 "디자인↔구현 정합성 QA" 입니다. 화면을 열고 디자인과 픽셀
단위로 눈대중 비교하는 그 일이, 라벨·문구·항목 수준에서 자동으로 됩니다.

## 관통 결과 (합성 응답, 2026-08-25)

Figma REST 모양을 따라 손으로 만든 합성 응답(문구는 SUT good 과 일치)으로
로그인+회원가입 2화면을 관통했습니다.

| 대상 | 결과 |
|---|---|
| `good` | **5/5 PASS** (로그인 labels·placeholders + 회원가입 labels·placeholders·options) |
| `bad` | 심은 결함 중 정적 대조가 잡을 수 있는 **둘만 FAIL** — 로그인 이메일 placeholder 가 다르고("아이디를 입력하세요"), 가입 경로 선택 목록에서 한 항목 누락(C4). 오탐 0 |

bad 의 나머지 결함(비밀번호 복잡도 검증 없음 등)은 잡히지 않는 것이 **맞습니다**
— 규칙 검증은 이 입력의 범위 밖이고, 리포트가 그 사실을 상자로 말합니다.
초록불의 범위를 리포트가 말한다는 원칙(노트 12)이 입력 수준으로 확장된 것입니다.

실물 Figma 파일 대조는 이 문서 작성 시점에 진행 중입니다 — 픽스처 파일을
Figma 앱에서 그려 실제 API 응답으로 같은 관통을 반복하고, 합성과 실물이
어긋나면 **실물이 이깁니다.** 결과는 아래 추기에 남깁니다.

## 추기 (2026-08-25) — 실물 응답 대조: 실물이 실제로 한 번 이겼다

픽스처는 손으로 그리지 않았다 — 픽스처를 **생성하는 플러그인**을 만들어
저장소에 넣었다(`scripts/figma_fixture_plugin/`). 누구든 빈 Figma 파일에서
플러그인 한 번으로 같은 픽스처를 재현할 수 있다. 실제 API 응답을 받아
(`scripts/fetch_figma.py`, 트림 후 13KB) 대조한 결과:

- 화면 2 · 요소 10 · 함정 경고 1 — 라벨·안내 문구·선택 항목 전부 합성과 일치.
  골든(`fixtures/figma/login_signup.golden.json`)으로 굳혔다.
- **흐름은 0개가 나왔다.** 실물 API 는 prototype 연결을 문서의 legacy 표기
  (`transitionNodeId`)가 아니라 **`interactions` 배열**로 준다. 합성 픽스처는
  legacy 표기로 만들었으니 통과했고, 실물이 처음으로 그 가정을 깼다 —
  "합성과 실물이 어긋나면 실물이 이긴다" 는 원칙이 바로 이 상황을 위한
  것이었다. 파서가 양쪽 표기를 읽되 화면 이동(NODE+NAVIGATE)만 세게 고쳤고,
  실물에서 `회원가입 → 로그인` 흐름이 via `가입하기` 와 함께 추출된다.
- e2e 는 실물 픽스처로 승격했다 — good 5/5 PASS, bad 는 같은 둘만 FAIL.
  결과는 합성과 동일하다(그래야 한다 — 같은 그림이니까).

- ~~**좌표 활용**~~ — `absoluteBoundingBox` 를 IoU 시험지의 정답으로 쓰려 했으나
  **성립하지 않는다**(2026-08-27 검토). 시험지의 정답 상자는 VLM 이 보는 **SUT
  스크린샷**의 좌표이고 Figma 상자는 **디자인 캔버스**의 좌표다. 둘이 맞으려면 구현이
  디자인의 픽셀 재현이어야 하는데, 이 경로가 존재하는 이유가 바로 "디자인과 구현은
  어긋난다" 이다(노트 21·22 가 실제로 그 어긋남을 잡았다). 그렇게 채점하면 구현이
  디자인과 다른 만큼이 전부 '모델이 틀렸다' 로 집계된다 — 시험지가 낡은 것과 모델이
  못 맞힌 것을 구분할 수 없게 만드는, test_iou_dataset 이 막으려는 그 혼동이다.
  (`absoluteBoundingBox` 는 `trim_figma_response` 가 버리므로 픽스처에도 없다.)
  시험지는 대신 **실화면에서 재서** 넓혔다 — 2026-08-27, 18화면 74항목.
