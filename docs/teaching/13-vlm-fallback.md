# 13 · 화면 이미지로 요소를 찾는다 — 그리고 없는 결함을 만들지 않는다

이전: [12-coverage-gaps.md](12-coverage-gaps.md) — 기획서에 적혀 있는데 아무도 확인하지 않는 것

---

## 왜 2차 경로가 필요한가

지금까지 S3(Grounder)는 접근성 속성으로 요소를 찾았습니다. 전략이 네 개입니다.

```
1. get_by_label("이메일")        <label for=...> 연결
2. get_by_role("button", "로그인")  버튼의 접근 가능한 이름
3. placeholder 대조
4. element_id 로 CSS selector
```

`good` 변형에서는 전부 통합니다. 그런데 **실물 화면은 이렇게 친절하지 않습니다.**

```html
<!-- 기획서: 요소 '검색' -->
<button type="submit"><svg>...</svg></button>
```

아이콘만 있는 제출 버튼입니다. `aria-label`이 없으니 접근 가능한 이름이 빈 문자열이고,
라벨도 placeholder도 없습니다. 네 전략이 모두 막힙니다. 이 모양은 흔합니다 — 검색 버튼,
닫기 버튼, 아이콘 툴바가 대개 이렇습니다.

그래서 `sut/` 에 `nolabel` 변형을 만들었습니다. 검증 로직은 `good` 과 **완전히 같고**
제출 버튼 마크업만 다릅니다. 이렇게 해 두면 "보정이 되면 판정이 `good` 과 같아져야 한다"
는 기준을 세울 수 있습니다.

보정을 끄고 돌린 결과입니다.

```
9 FAIL / 1 PASS   전부 element_not_found
```

여기서 2차 경로가 하는 일은 **스크린샷을 찍어 VLM에게 "검색 버튼이 어디 있나" 를 묻고,
받은 좌표를 누르는 것**입니다.

---

## 계약을 먼저 좁혔다

VLM에게 시킬 수 있는 일은 많습니다. 화면을 설명하기, 결함을 찾기, 다음에 무엇을 눌러야
하는지 정하기. 그런데 그걸 다 시키면 **판정의 근거가 모델의 인상이 됩니다.**

그래서 인터페이스를 하나로 좁혔습니다.

```python
class VLMClient(Protocol):
    def locate(self, *, image_png: bytes, target: str, hint: str) -> Located: ...
```

*이 이미지에서 이 이름의 요소가 어디 있는가.* 그 하나만 묻습니다.

판정은 여전히 S5의 결정적 규칙이 합니다. 모델은 **좌표만** 돌려줍니다. 이 경계를 지키면
VLM이 틀렸을 때 틀리는 방식이 "좌표가 어긋난다" 하나로 제한됩니다 — 그리고 그건
확인할 수 있습니다.

```python
@dataclass
class Located:
    bbox: tuple[float, float, float, float]   # 0~1 상대 좌표
    confidence: float = 1.0
```

상대 좌표로 받는 이유: 모델이 보는 이미지 크기와 브라우저 뷰포트가 다를 수 있고,
스크린샷이 devicePixelRatio 로 확대돼 있을 수도 있습니다. 절대 픽셀로 받으면 그
불일치가 조용히 좌표 오차가 됩니다.

---

## 여기서 실제로 벌어진 일 — 없는 결함 7건

MockVLM에 좌표를 손으로 적어 넣었습니다. 화면을 보고 어림잡은 값입니다.

```python
vlm.register("검색", (0.36, 0.235, 0.64, 0.28))
```

그리고 돌렸더니 테스트가 통과했습니다. `healed > 0` 이었으니까요. 그런데 리포트를 열어
보니 **FAIL이 7건 있었습니다.** 심어 둔 결함은 하나도 없는 화면인데요.

무슨 일이 있었는지 재구성하면 이렇습니다.

```
1. 어림잡은 좌표가 버튼을 살짝 비켜 갔다 (폼 안 빈 여백)
2. Playwright 의 mouse.click(x, y) 는 거기에 아무것도 없어도 조용히 성공한다
3. 폼이 제출되지 않았다
4. 에러 문구도 결과도 나오지 않았다
5. S5 는 그것을 "기획서가 지정한 에러가 안 뜬다" 로 읽었다
6. 리포트: 구현 결함 7건
```

**이게 이 도구가 낼 수 있는 최악의 리포트입니다.** 개발자가 없는 버그를 일곱 개 찾습니다.
그리고 못 찾습니다 — 버그가 없으니까요. 그다음에는 도구를 믿지 않게 됩니다.

`fill()` 은 그래도 낫습니다. 입력란이 아닌 곳에 타이핑하면 Playwright가 에러를 냅니다.
치명적인 건 `click()` 입니다. 좌표 클릭은 **빈 공간을 눌러도 성공**합니다.

### 막은 방법 1 — 누르기 전에 그 자리에 무엇이 있는지 본다

```python
_ACTIONABLE = {
    "fill":  "input, textarea",
    "click": "button, a, input[type=submit], [role=button], [role=link]",
    "check": "input[type=checkbox], [role=checkbox]",
}

hit = ctx.page.evaluate("""([x, y, sel]) => {
    const el = document.elementFromPoint(x, y);
    if (!el) return null;
    return el.closest(sel) ? el.tagName.toLowerCase() : "";
}""", [x, y, selector])

if not hit:
    raise GroundingError(location.target, [Attempt(
        strategy=f"vlm-좌표({round(x)},{round(y)})에 조작 가능한 요소 없음", count=0)])
```

`closest()` 를 쓰는 이유: VLM이 버튼 안의 `<svg>` 나 `<span>` 을 가리키는 것이 정상입니다.
그 조상에 버튼이 있으면 누를 수 있습니다.

없으면 **누르지 않고 탐지 실패로 되돌립니다.** 살릴 수 없는 것을 살린 척하면 그 뒤의
판정이 전부 거짓이 됩니다. `element_not_found` 는 "도구가 요소를 못 찾았다" 로 읽히고,
`assertion_mismatch` 는 "구현이 틀렸다" 로 읽힙니다. **개발자가 할 일이 다릅니다.**

### 막은 방법 2 — healed 의 뜻을 고쳤다

```python
# 전
healed=any(r.location.healed for r in step_results)

# 후
healed=any(r.location.healed for r in step_results
           if r.location and r.status == "ok")
```

시도만 하고 막힌 것을 healed 로 세면, 리포트가 "이미지로 찾아 진행했다" 고 말하는데
실제로는 아무것도 진행되지 않은 상태가 됩니다. **healed는 실제로 진행된 스텝만 셉니다.**

### 막은 방법 3 — 테스트가 좌표를 손으로 적지 않는다

원인은 코드가 아니라 테스트였습니다. `healed > 0` 만 봤기 때문에 통과했습니다.

```python
def measure(sut_base, path, selector):
    """정답 좌표를 실측한다 ('완벽한 VLM' 시뮬레이션)."""
    box = page.locator(selector).bounding_box()
    return (box["x"]/1280, box["y"]/800, ...)
```

그리고 수용 기준을 바꿨습니다.

```python
def test_기능_검증이_good과_같아진다(self, report_on):
    failed = [v for v in report_on.cases if v.verdict == "FAIL"]
    assert len(failed) == 1          # 라벨 탐지 케이스 하나만
    assert "-labels-" in failed[0].case_id
```

`nolabel` 은 검증 로직이 `good` 과 같으므로, 보정이 제대로 되면 판정도 같아야 합니다.
**이 기준이 있으면 좌표가 어긋난 순간 테스트가 터집니다.**

그리고 어긋난 좌표를 **일부러 넣는 테스트**를 따로 뒀습니다.

```python
class TestWrongCoordinates:
    def test_없는_결함을_만들어내지_않는다(self, report_wrong): ...
    def test_진행하지_못했으므로_healed가_아니다(self, report_wrong): ...
```

## 보정이 사실을 지우면 안 된다

보정을 켜면 `nolabel` 이 9 PASS / 1 FAIL 이 됩니다. 좋아 보입니다. 그런데 여기에 함정이
하나 있습니다.

**'기획서의 라벨로 요소를 지목할 수 없다' 는 것 자체가 결함입니다.** 기획-구현 불일치이면서
접근성 결함입니다. 스크린 리더 사용자는 그 버튼이 무슨 버튼인지 알 수 없습니다.

보정이 그걸 조용히 메워 주면, 도구는 결함을 **숨기는 장치**가 됩니다.

그래서 라벨 탐지 자체를 확인하는 케이스를 따로 만들고, 그 케이스는 **보정을 쓰지 않습니다.**

```python
def test_보정해도_라벨_탐지는_실패로_남는다(self, report_on):
    case = next(v for v in report_on.cases if "-labels-" in v.case_id)
    assert case.verdict == "FAIL", "보정이 접근성 결함을 지웠다"
    assert case.healed is False, "라벨 탐지 확인 자체는 보정을 쓰지 않는다"
```

리포트에도 남깁니다.

```
화면 이미지로 찾아 진행한 케이스 · 3건
접근성 속성으로 요소를 찾지 못해 좌표로 조작했습니다. 통과했더라도
기획서의 라벨로 요소를 지목할 수 없다는 사실은 그대로 남습니다.
```

통과율만 보는 사람에게도 "이 PASS는 이미지로 찾아서 나온 것" 이 보여야 합니다.

## 그럴듯한 오답을 걸러내는 관문

VLM은 못 찾았을 때도 **좌표를 냅니다.** "없습니다" 라고 하지 않습니다. 그래서 세 관문을
뒀습니다.

| 관문 | 거르는 것 |
|---|---|
| `confidence < 0.5` | 모델이 스스로 자신 없다고 한 답 |
| `is_sane()` | 0~1 범위 밖, 크기 0, 뒤집힌 좌표(x2 < x1) |
| `_require_actionable` | 그 자리에 조작 가능한 요소가 없는 좌표 |

세 번째가 앞의 두 개를 통과한 오답을 잡습니다 — 좌표가 범위 안이고 모델이 자신도 있는데
그냥 틀린 경우입니다. 실제로 그런 경우가 가장 위험합니다.

보정 상한도 뒀습니다.

```python
max_heal = 2   # 케이스당
```

라벨 연결이 통째로 깨진 화면에서 모든 스텝이 보정되면, 그 케이스는 '화면을 확인한 것' 이
아니라 '이미지로 조작한 것' 이 됩니다. 그건 검증이라 부를 수 없습니다.

## MockVLM이 증명하지 않는 것

지금 초록불은 **배관**을 증명합니다. 탐지 실패 → 스크린샷 → 좌표 → 클릭 → 판정이
이어지는지. 그것만입니다.

증명하지 않는 것은 **정확도**입니다. MockVLM은 CSS selector로 정답을 실측합니다 —
'완벽한 VLM' 시뮬레이션입니다. 실제 모델이 아이콘만 있는 버튼을 '검색' 으로 알아보는지는
전혀 다른 문제입니다.

이 구분을 흐리면 mock 초록불을 보고 "2차가 동작한다" 고 말하게 되고, 정작 실물 모델이
요소를 못 찾을 때 그 사실이 어디서도 드러나지 않습니다. 그래서 두 테스트 파일의 문서
문자열에 이걸 못 박아 뒀습니다.

실물 측정은 별개 작업입니다 — 그리고 MIG 파티션에 7B가 이미 8.30 GiB를 쓰고 있어서
1.20 GiB만 남습니다. 어떤 VL 모델도 그 자리에 올라가지 않습니다.

## 이 노트에서 남길 것

1. **좌표 클릭은 실패해도 성공한다.** Playwright의 `mouse.click(x, y)` 는 빈 공간을
   눌러도 예외를 내지 않습니다. `fill()` 은 에러를 내는데 `click()` 은 조용합니다.
   조용한 실패가 판정 단계에서 **구현 결함으로 번역됩니다.**
2. **없는 결함을 보고하는 것이 결함을 놓치는 것보다 나쁠 수 있다.** 놓친 결함은
   도구의 한계로 남지만, 없는 결함 7건은 개발자의 시간을 쓰고 도구의 신뢰를 없앱니다.
3. **`healed > 0` 은 아무것도 확인하지 않는 수용 기준이다.** 보정이 일어났다는 사실과
   보정이 옳았다는 사실은 별개입니다. **"보정하면 판정이 good과 같아져야 한다"** 처럼
   결과로 기준을 세워야 합니다.
4. **테스트에 좌표를 손으로 적으면 안 된다.** 어림잡은 값이 통하는 것처럼 보이는 것이
   가장 위험합니다. 실측하거나, 틀린 좌표를 일부러 넣어 도구의 반응을 확인해야 합니다.
5. **탐지 실패와 구현 결함을 절대 섞지 않는다.** `element_not_found` 와
   `assertion_mismatch` 는 개발자가 할 일이 다릅니다. 확신할 수 없으면 탐지 실패로
   두는 쪽이 옳습니다 — 그건 "도구를 고쳐라" 로 읽히고, 그게 사실입니다.
6. **보정은 결함을 메우는 장치가 아니다.** 보정으로 살린 케이스가 통과해도 '라벨로
   지목할 수 없다' 는 사실은 리포트에 남아야 합니다. 사라지면 보정이 검증을 약화시킨
   것입니다.
7. **모델의 역할을 최대한 좁힌다.** VLM은 좌표만 냅니다. 판정은 결정적 규칙이 합니다.
   경계를 지키면 모델이 틀리는 방식이 하나로 제한되고, 그 하나는 검사할 수 있습니다.
8. **mock 초록불이 증명하는 범위를 문서에 적는다.** 배관과 정확도는 다른 문제이고,
   그 구분을 적어 두지 않으면 나중에 자기가 속습니다.
