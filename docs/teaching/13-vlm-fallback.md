# 13 · 화면 이미지로 요소를 찾는다 — 그리고 없는 결함을 만들지 않는다

이전: [12-coverage-gaps.md](12-coverage-gaps.md) — 기획서에 적혀 있는데 아무도 확인하지 않는 것

---

## 왜 2차 경로가 필요한가

지금까지 S3(Grounder)는 접근성 속성으로 요소를 찾았습니다. 전략이 네 개입니다.

```
1. get_by_label("이메일")        <label for=...> 연결
2. get_by_role("button", "로그인")  버튼의 접근 가능한 이름
3. placeholder 대조
4. element_id 로 CSS selector
```

`good` 변형에서는 전부 통합니다. 그런데 **실물 화면은 이렇게 친절하지 않습니다.**

```html
<!-- 기획서: 요소 '검색' -->
<button type="submit"><svg>...</svg></button>
```

아이콘만 있는 제출 버튼입니다. `aria-label`이 없으니 접근 가능한 이름이 빈 문자열이고,
라벨도 placeholder도 없습니다. 네 전략이 모두 막힙니다. 이 모양은 흔합니다 — 검색 버튼,
닫기 버튼, 아이콘 툴바가 대개 이렇습니다.

그래서 `sut/` 에 `nolabel` 변형을 만들었습니다. 검증 로직은 `good` 과 **완전히 같고**
제출 버튼 마크업만 다릅니다. 이렇게 해 두면 "보정이 되면 판정이 `good` 과 같아져야 한다"
는 기준을 세울 수 있습니다.

보정을 끄고 돌린 결과입니다.

```
9 FAIL / 1 PASS   전부 element_not_found
```

여기서 2차 경로가 하는 일은 **스크린샷을 찍어 VLM에게 "검색 버튼이 어디 있나" 를 묻고,
받은 좌표를 누르는 것**입니다.

---

## 계약을 먼저 좁혔다

VLM에게 시킬 수 있는 일은 많습니다. 화면을 설명하기, 결함을 찾기, 다음에 무엇을 눌러야
하는지 정하기. 그런데 그걸 다 시키면 **판정의 근거가 모델의 인상이 됩니다.**

그래서 인터페이스를 하나로 좁혔습니다.

```python
class VLMClient(Protocol):
    def locate(self, *, image_png: bytes, target: str, hint: str) -> Located: ...
```

*이 이미지에서 이 이름의 요소가 어디 있는가.* 그 하나만 묻습니다.

판정은 여전히 S5의 결정적 규칙이 합니다. 모델은 **좌표만** 돌려줍니다. 이 경계를 지키면
VLM이 틀렸을 때 틀리는 방식이 "좌표가 어긋난다" 하나로 제한됩니다 — 그리고 그건
확인할 수 있습니다.

```python
@dataclass
class Located:
    bbox: tuple[float, float, float, float]   # 0~1 상대 좌표
    confidence: float = 1.0
```

상대 좌표로 받는 이유: 모델이 보는 이미지 크기와 브라우저 뷰포트가 다를 수 있고,
스크린샷이 devicePixelRatio 로 확대돼 있을 수도 있습니다. 절대 픽셀로 받으면 그
불일치가 조용히 좌표 오차가 됩니다.

## 여기서 실제로 벌어진 일 — 없는 결함 7건

MockVLM에 좌표를 손으로 적어 넣었습니다. 화면을 보고 어림잡은 값입니다.

```python
vlm.register("검색", (0.36, 0.235, 0.64, 0.28))
```

그리고 돌렸더니 테스트가 통과했습니다. `healed > 0` 이었으니까요. 그런데 리포트를 열어
보니 **FAIL이 7건 있었습니다.** 심어 둔 결함은 하나도 없는 화면인데요.

무슨 일이 있었는지 재구성하면 이렇습니다.

```
1. 어림잡은 좌표가 버튼을 살짝 비켜 갔다 (폼 안 빈 여백)
2. Playwright 의 mouse.click(x, y) 는 거기에 아무것도 없어도 조용히 성공한다
3. 폼이 제출되지 않았다
4. 에러 문구도 결과도 나오지 않았다
5. S5 는 그것을 "기획서가 지정한 에러가 안 뜬다" 로 읽었다
6. 리포트: 구현 결함 7건
```

**이게 이 도구가 낼 수 있는 최악의 리포트입니다.** 개발자가 없는 버그를 일곱 개 찾습니다.
그리고 못 찾습니다 — 버그가 없으니까요. 그다음에는 도구를 믿지 않게 됩니다.

`fill()` 은 그래도 낫습니다. 입력란이 아닌 곳에 타이핑하면 Playwright가 에러를 냅니다.
치명적인 건 `click()` 입니다. 좌표 클릭은 **빈 공간을 눌러도 성공**합니다.

### 막은 방법 1 — 누르기 전에 그 자리에 무엇이 있는지 본다

```python
_ACTIONABLE = {
    "fill":  "input, textarea",
    "click": "button, a, input[type=submit], [role=button], [role=link]",
    "check": "input[type=checkbox], [role=checkbox]",
}

hit = ctx.page.evaluate("""([x, y, sel]) => {
    const el = document.elementFromPoint(x, y);
    if (!el) return null;
    return el.closest(sel) ? el.tagName.toLowerCase() : "";
}""", [x, y, selector])

if not hit:
    raise GroundingError(location.target, [Attempt(
        strategy=f"vlm-좌표({round(x)},{round(y)})에 조작 가능한 요소 없음", count=0)])
```

`closest()` 를 쓰는 이유: VLM이 버튼 안의 `<svg>` 나 `<span>` 을 가리키는 것이 정상입니다.
그 조상에 버튼이 있으면 누를 수 있습니다.

없으면 **누르지 않고 탐지 실패로 되돌립니다.** 살릴 수 없는 것을 살린 척하면 그 뒤의
판정이 전부 거짓이 됩니다. `element_not_found` 는 "도구가 요소를 못 찾았다" 로 읽히고,
`assertion_mismatch` 는 "구현이 틀렸다" 로 읽힙니다. **개발자가 할 일이 다릅니다.**

### 막은 방법 2 — healed 의 뜻을 고쳤다

```python
# 전
healed=any(r.location.healed for r in step_results)

# 후
healed=any(r.location.healed for r in step_results
           if r.location and r.status == "ok")
```

시도만 하고 막힌 것을 healed 로 세면, 리포트가 "이미지로 찾아 진행했다" 고 말하는데
실제로는 아무것도 진행되지 않은 상태가 됩니다. **healed는 실제로 진행된 스텝만 셉니다.**

### 막은 방법 3 — 테스트가 좌표를 손으로 적지 않는다

원인은 코드가 아니라 테스트였습니다. `healed > 0` 만 봤기 때문에 통과했습니다.

```python
def measure(sut_base, path, selector):
    """정답 좌표를 실측한다 ('완벽한 VLM' 시뮬레이션)."""
    box = page.locator(selector).bounding_box()
    return (box["x"]/1280, box["y"]/800, ...)
```

그리고 수용 기준을 바꿨습니다.

```python
def test_기능_검증이_good과_같아진다(self, report_on):
    failed = [v for v in report_on.cases if v.verdict == "FAIL"]
    assert len(failed) == 1          # 라벨 탐지 케이스 하나만
    assert "-labels-" in failed[0].case_id
```

`nolabel` 은 검증 로직이 `good` 과 같으므로, 보정이 제대로 되면 판정도 같아야 합니다.
**이 기준이 있으면 좌표가 어긋난 순간 테스트가 터집니다.**

그리고 어긋난 좌표를 **일부러 넣는 테스트**를 따로 뒀습니다.

```python
class TestWrongCoordinates:
    def test_없는_결함을_만들어내지_않는다(self, report_wrong): ...
    def test_진행하지_못했으므로_healed가_아니다(self, report_wrong): ...
```

## 보정이 사실을 지우면 안 된다

보정을 켜면 `nolabel` 이 9 PASS / 1 FAIL 이 됩니다. 좋아 보입니다. 그런데 여기에 함정이
하나 있습니다.

**'기획서의 라벨로 요소를 지목할 수 없다' 는 것 자체가 결함입니다.** 기획-구현 불일치이면서
접근성 결함입니다. 스크린 리더 사용자는 그 버튼이 무슨 버튼인지 알 수 없습니다.

보정이 그걸 조용히 메워 주면, 도구는 결함을 **숨기는 장치**가 됩니다.

그래서 라벨 탐지 자체를 확인하는 케이스를 따로 만들고, 그 케이스는 **보정을 쓰지 않습니다.**

```python
def test_보정해도_라벨_탐지는_실패로_남는다(self, report_on):
    case = next(v for v in report_on.cases if "-labels-" in v.case_id)
    assert case.verdict == "FAIL", "보정이 접근성 결함을 지웠다"
    assert case.healed is False, "라벨 탐지 확인 자체는 보정을 쓰지 않는다"
```

리포트에도 남깁니다.

```
화면 이미지로 찾아 진행한 케이스 · 3건
접근성 속성으로 요소를 찾지 못해 좌표로 조작했습니다. 통과했더라도
기획서의 라벨로 요소를 지목할 수 없다는 사실은 그대로 남습니다.
```

통과율만 보는 사람에게도 "이 PASS는 이미지로 찾아서 나온 것" 이 보여야 합니다.

## 그럴듯한 오답을 걸러내는 관문

VLM은 못 찾았을 때도 **좌표를 냅니다.** "없습니다" 라고 하지 않습니다. 그래서 세 관문을
뒀습니다.

| 관문 | 거르는 것 |
|---|---|
| `confidence < 0.5` | 모델이 스스로 자신 없다고 한 답 |
| `is_sane()` | 0~1 범위 밖, 크기 0, 뒤집힌 좌표(x2 < x1) |
| `_require_actionable` | 그 자리에 조작 가능한 요소가 없는 좌표 |

세 번째가 앞의 두 개를 통과한 오답을 잡습니다 — 좌표가 범위 안이고 모델이 자신도 있는데
그냥 틀린 경우입니다. 실제로 그런 경우가 가장 위험합니다.

보정 상한도 뒀습니다.

```python
max_heal = 2   # 케이스당
```

라벨 연결이 통째로 깨진 화면에서 모든 스텝이 보정되면, 그 케이스는 '화면을 확인한 것' 이
아니라 '이미지로 조작한 것' 이 됩니다. 그건 검증이라 부를 수 없습니다.

## MockVLM이 증명하지 않는 것

지금 초록불은 **배관**을 증명합니다. 탐지 실패 → 스크린샷 → 좌표 → 클릭 → 판정이
이어지는지. 그것만입니다.

증명하지 않는 것은 **정확도**입니다. MockVLM은 CSS selector로 정답을 실측합니다 —
'완벽한 VLM' 시뮬레이션입니다. 실제 모델이 아이콘만 있는 버튼을 '검색' 으로 알아보는지는
전혀 다른 문제입니다.

이 구분을 흐리면 mock 초록불을 보고 "2차가 동작한다" 고 말하게 되고, 정작 실물 모델이
요소를 못 찾을 때 그 사실이 어디서도 드러나지 않습니다. 그래서 두 테스트 파일의 문서
문자열에 이걸 못 박아 뒀습니다.

## 실물 모델로 재 봤습니다

MIG 파티션은 9.50 GiB인데 7B가 UTIL=0.90으로 8.30 GiB를 씁니다. **남는 1.20 GiB에
3.17 GiB 가중치는 들어가지 않습니다.** 동시 적재는 불가능합니다.

그런데 `nodes.py`를 보면 **LLM과 VLM이 동시에 필요한 시점이 없습니다** — LLM은 S1·S2,
VLM은 S3입니다. 그래서 시간을 나눠 씁니다. 7B를 내리고 VL을 띄웠습니다.

### 좌표 정확도 — 시험지 50개로 쟀습니다 (`scripts/eval_vlm_iou.py`)

파이프라인으로 재면 PASS/FAIL만 보이고 **좌표가 얼마나 어긋났는지**는 안 보입니다.
그런데 그 값이 이 경로의 실용성을 정합니다. 그래서 판정 없이 좌표만 비교합니다.

처음에는 요소 넷으로 쟀습니다(4/4 적중). 그 넷을 고른 사람이 우리였고, 하나만 틀려도
75% 인 표본이라 숫자를 주장할 수 없었습니다. 그래서 시험지를 굳혔고(아래), 2026-08-22 에
실물 Qwen2.5-VL-3B-AWQ 로 50개를 채점했습니다. 전체 표는
`docs/measurements/vlm-iou-qwen-vl-2026-08-22.md` 입니다.

| 지표 | 값 | 뜻 |
|---|---|---|
| 탐지 성공률 (IoU≥0.5) | **21/40 = 52.5%** | 명세서 §9 가 요구한 지표 — **미달** |
| 적중률 (중심이 요소 안) | **36/40 = 90.0%** | 실제로 클릭이 되는 비율 |
| 오탐 (없는 것을 찾았다고 함) | **7/10 = 70.0%** | 낮아야 한다 — **가장 나쁜 숫자** |
| 관문이 버린 정답 | 0개 | 문턱값이 정답을 버리지는 않았다 |
| 평균 IoU · 호출 시간 | 0.502 · 평균 737ms | |

세 숫자가 서로 다른 말을 합니다. 하나로 합치면 어느 것도 고칠 수 없습니다.

**적중 90% 와 IoU 52.5% 의 차이는 '크기' 입니다.** 틀린 19개 중 15개가 '적중만' —
중심은 요소 안인데 상자가 큽니다. 입력란을 라벨까지 포함해 잡고, 버튼을 여백까지 잡습니다
(`signup-empty 가입하기` IoU 0.11, 중심 오차 0.24). 위치를 못 맞추는 것과 크기를 못
맞추는 것은 다르고, 클릭에 필요한 것은 위치뿐입니다. 그래서 **실행 성패는 적중률이
말하고, §9 의 IoU 기준으로는 미달**입니다 — 둘 다 적습니다.

진짜 실패(중심도 밖)는 4개입니다. `login-error 이메일`(오차 0.74) · `signup-error 닉네임`
(0.00 — 엉뚱한 곳) · 약관 동의 체크박스 둘. **에러 문구가 뜬 화면에서 어긋납니다** —
빨간 문구가 끼어들면 행을 잘못 셉니다. 체크박스는 작아서 라벨 글자를 잡습니다.

**오탐 70% 가 이 측정에서 얻은 가장 중요한 사실입니다.** 없는 요소 10개 중 7개를
신뢰도 0.8~0.9 로 '찾았다' 고 답했습니다 — 로그인 화면에서 '검색어' 를, 검색 화면에서
'비밀번호' 를 찾았다고 합니다. 신뢰도 관문은 이것을 한 개도 거르지 못했습니다(관문이
버린 정답도 0개 — 즉 관문이 아무 일도 안 했습니다. 이 모델의 신뢰도는 정보가 아닙니다).

이게 왜 위험한가. 2차 경로는 DOM 으로 못 찾았을 때 도는 길입니다. **요소가 정말 없는
화면**(구현이 빠뜨린 경우 — 바로 우리가 찾아야 할 결함)에서 모델이 엉뚱한 좌표를 내면,
도구는 그 자리를 누르고 케이스는 이어지며, 그 뒤의 FAIL 은 '구현 결함' 으로 보고됩니다.
**탐지 실패가 구현 결함으로 둔갑합니다.** 노트 17 에서 가장 경계한 모양입니다.

위의 세 관문 중 앞의 둘(신뢰도·`is_sane`)은 이 7개를 하나도 못 걸렀습니다. 셋째
`_require_actionable` 이 마지막 방어선인데, 이 시험지는 굳은 PNG 로 채점하므로 그
관문을 통과했을지는 재지 못했습니다 — 좌표가 빈 공간이면 걸리고, **다른 입력란 위에
떨어지면 통과합니다.** 검색 화면에서 '비밀번호' 를 찾았다는 답이 검색어 입력란 위라면,
그 관문은 "입력란이 있다" 고만 봅니다. 남은 일은 그 구멍을 재는 것과 막는 것입니다:
(1) 시험지에 DOM 스냅샷을 함께 굳혀 오탐 좌표가 셋째 관문을 통과하는지 센다,
(2) 좌표 아래 요소의 접근성 이름이 **기획서의 다른 요소 라벨**과 일치하면 탐지 실패로
돌린다 — 모델의 자기 신고 대신 화면의 사실로 거릅니다. 그 전까지는 리포트에 '보정으로
찾음' 이 붙은 케이스를 사람이 한 번 더 보는 것이 방어선입니다.

### 시험지를 굳힌 이유

시험지는 화면 13장, 항목 50개(있음 40 · 없음 10)입니다.
설계에서 지킨 것은 두 가지입니다.

**정답은 손으로 쓴 selector 로 잽니다.** `dom_locator` 로 정답을 찾으면 도구가 이미
찾을 수 있는 요소만 시험지에 들어갑니다. 2차 경로가 필요한 곳이 정확히 그 반대편이므로,
그건 시험에서 어려운 문제만 빼는 것과 같습니다.

**없는 요소 10개를 넣었습니다.** 모델은 못 찾았을 때도 그럴듯한 좌표를 냅니다. 그 좌표를
누르면 엉뚱한 곳을 누르고 케이스는 진행되며, 그 FAIL 이 구현 결함으로 보고됩니다 —
오탐입니다. '없다고 말하는가' 를 재지 않으면 그 경로가 보이지 않습니다.

채점 절차(VL 서버 교체 포함)는 `fixtures/iou/README.md` 에 있습니다.

### 파이프라인 결과

```
2차 경로 끔    1 PASS / 9 FAIL
2차 경로 켬    9 PASS / 1 FAIL   보정 8건, 케이스당 최대 1스텝
```

**mock 으로 얻은 값과 같습니다.** 이 화면에서는 실물 모델의 정확도 손실이 없었습니다.

### 실측이 찾아낸 구멍 — 켰다고 믿는 실행이 실제로는 꺼져 있었다

첫 실물 실행은 9건 전부 FAIL이었습니다. 그런데 실패 문구가 `'일치하는 요소가 없음'`
이었습니다 — VLM 오류가 아니라 **1차 경로의 탐지 실패 문구**입니다. 보정이 아예 진입하지
않았습니다.

원인은 모델 이름이었습니다. 서버를 `--served-model-name qwen-vl` 로 띄웠는데 클라이언트는
기본 이름으로 요청했습니다.

```
GET  /v1/models            -> 200   (서버는 살아 있다)
POST /v1/chat/completions  -> 404   (그런 모델 없다)
```

`health()` 가 **앞의 것만 봤습니다.** 그래서 실행은 정상 기동하고 로그에는
`2차 경로: vllm-vl @ http://localhost:8001/v1` 이 찍혔는데, `locate()` 마다 VLMError 가
나고 호출부가 그것을 탐지 실패로 되돌렸습니다. 결과가 **보정을 켜기 전과 완전히
같았습니다.**

이건 이 프로젝트가 반복해서 만나는 그 구멍입니다 —
**확인하지 않은 것과 확인해서 통과한 것은 다릅니다.** `health()` 가 "서버가 있다" 를
확인하고 "우리 모델이 있다" 는 확인하지 않았습니다.

고친 방식은 늘 같습니다. 기동 시점에 알 수 있는 사실이므로 그때 끊습니다.

```python
if self.model not in served:
    raise VLMError(
        f"VLM 서버가 '{self.model}' 을 서빙하지 않습니다. "
        f"서빙 중: {served or '(없음)'} — --vlm-model 로 이름을 맞추세요."
    )
```

그리고 `--vlm-model` 옵션을 뒀습니다. vLLM 은 서빙 이름을 배포마다 바꿀 수 있으므로
클라이언트가 고정 이름을 강요하면 안 됩니다.

**주의: 이 측정은 완전한 관통이 아닙니다.** 7B를 내린 상태라 S1·S2를 `--backend mock`
으로 돌렸습니다. 두 실물 모델을 한 실행에서 쓰려면 서버를 바꾸는 사이에 추출된 기획서를
보관해야 하고, 지금 CLI 에는 그 경로가 없습니다. 그래서 지금 측정된 것은
**S3 의 정확도**이고, S1·S2 의 실물 정확도는 앞서 따로 측정돼 있습니다.

## 이 노트에서 남길 것

1. **좌표 클릭은 실패해도 성공한다.** Playwright의 `mouse.click(x, y)` 는 빈 공간을
   눌러도 예외를 내지 않습니다. `fill()` 은 에러를 내는데 `click()` 은 조용합니다.
   조용한 실패가 판정 단계에서 **구현 결함으로 번역됩니다.**
2. **없는 결함을 보고하는 것이 결함을 놓치는 것보다 나쁠 수 있다.** 놓친 결함은
   도구의 한계로 남지만, 없는 결함 7건은 개발자의 시간을 쓰고 도구의 신뢰를 없앱니다.
3. **`healed > 0` 은 아무것도 확인하지 않는 수용 기준이다.** 보정이 일어났다는 사실과
   보정이 옳았다는 사실은 별개입니다. **"보정하면 판정이 good과 같아져야 한다"** 처럼
   결과로 기준을 세워야 합니다.
4. **테스트에 좌표를 손으로 적으면 안 된다.** 어림잡은 값이 통하는 것처럼 보이는 것이
   가장 위험합니다. 실측하거나, 틀린 좌표를 일부러 넣어 도구의 반응을 확인해야 합니다.
5. **탐지 실패와 구현 결함을 절대 섞지 않는다.** `element_not_found` 와
   `assertion_mismatch` 는 개발자가 할 일이 다릅니다. 확신할 수 없으면 탐지 실패로
   두는 쪽이 옳습니다 — 그건 "도구를 고쳐라" 로 읽히고, 그게 사실입니다.
6. **보정은 결함을 메우는 장치가 아니다.** 보정으로 살린 케이스가 통과해도 '라벨로
   지목할 수 없다' 는 사실은 리포트에 남아야 합니다. 사라지면 보정이 검증을 약화시킨
   것입니다.
7. **모델의 역할을 최대한 좁힌다.** VLM은 좌표만 냅니다. 판정은 결정적 규칙이 합니다.
   경계를 지키면 모델이 틀리는 방식이 하나로 제한되고, 그 하나는 검사할 수 있습니다.
8. **mock 초록불이 증명하는 범위를 문서에 적는다.** 배관과 정확도는 다른 문제이고,
   그 구분을 적어 두지 않으면 나중에 자기가 속습니다.
9. **'서버가 살아 있다' 는 '내 요청이 통한다' 가 아니다.** `/models` 가 200 을 주는 것과
   그 목록에 내 모델이 있는 것은 별개입니다. 이름이 틀리면 2차 경로가 통째로 죽는데
   리포트는 '요소를 못 찾았다' 로만 보입니다 — 보정을 켠 실행과 끈 실행이 구분되지
   않습니다. 기동 시점에 알 수 있는 사실은 그때 끊습니다.
10. **실측은 mock 이 못 찾는 결함을 찾는다.** `health()` 의 구멍은 mock 테스트 26건이
   전부 통과하는 동안 그대로 있었습니다. mock 은 서버 이름 같은 것을 다루지 않으니까요.
11. **한 숫자로 합치지 않는다.** 50개 채점은 적중 90% · IoU 52.5% · 오탐 70% 를 냈고,
   셋은 각각 다른 고칠 곳(없음 · 상자 크기 · '없다' 고 말하기)을 가리킵니다. 평균을
   내면 고칠 곳이 사라집니다. 그리고 **모델이 말하는 신뢰도는 관문이 아니었습니다** —
   오탐 7개가 전부 0.8 이상이었습니다. 관문은 화면의 사실로 만들어야 합니다.
   실물로 한 번 돌리는 것이 mock 테스트를 늘리는 것보다 나은 순간이 있습니다.
11. **측정하지 않은 것을 측정한 것처럼 적지 않는다.** 이번 관통은 S1·S2 를 mock 으로
   돌렸으므로 '두 실물 모델의 관통' 이 아닙니다. 그 한계를 적어 두지 않으면 나중에
   이 숫자를 근거로 잘못된 말을 하게 됩니다.

겹칩니다 — 같은 모양의 입력이 나란히 있고(시작일/종료일), 목록·합계는 눈에 보이는
테두리가 없고, **좌표를 통째로 놓친 항목(IoU 0.00)이 처음 나왔습니다.** 지금까지의
실패는 대개 '상자가 헐거운' 것이었지 다른 곳을 가리킨 것이 아니었습니다.

경계가 안 보이는 요소는 IoU 라는 지표 자체가 흔들리는 자리이기도 합니다 — 사람도
`주문 목록` 의 사각형을 정확히 그리라면 답이 갈립니다. 그래도 **문턱값을 낮추지
않습니다.** 지표를 움직여 점수를 올리는 것은 측정이 아닙니다.

### 이 표가 바꾸는 것

아무것도 바꾸지 않습니다 — 그게 결과입니다. selector-first 는 더 넓은 시험지에서
간격이 **벌어졌습니다**(95/90 -> 96.7/83.3). 새 화면에서 1차는 20/20 이고 2차는
14/20 입니다. 2차 경로는 여전히 1차가 닿지 못하는 자리(아이콘 버튼)에서만 값을
합니다.

2차 경로는 아직 옛 시험지의 점수입니다. VL 을 다시 올려야 채점할 수 있어서, 채점
스크립트가 **`dataset_id` 가 다르면 비교표를 만들지 않습니다.** 항목 id 는 열거
순서라 집합이 같아도 같은 id 가 다른 항목을 가리킬 수 있습니다 — 오늘 만든 모집단
가드가 못 잡는 구멍이었고, 시험지를 넓히는 바로 다음 작업에서 드러났습니다.

넓히면서 오탐을 3건 만들 뻔했습니다. 채점 스크립트가 세션 없이 경로만 열어 상품등록·
주문조회가 통째로 로그인 화면으로 리다이렉트됐고, 거기 있는 '비밀번호' 를 '없는 요소를
찾았다' 로 셌습니다. **도구 결함이 탐지 실패로 둔갑하는 모양**이라, 고치는 자리를
시험지 쪽에 뒀습니다 — 항목이 '이 화면에 어떻게 닿는가' 를 들고 다닙니다. 채점
스크립트마다 로그인 절차를 적으면 한쪽만 고쳐지는 날이 옵니다.
