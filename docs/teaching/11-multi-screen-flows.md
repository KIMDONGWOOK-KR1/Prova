# 11 · 화면 하나만 봐서는 알 수 없는 것 — 한 문서, 여러 화면, 그리고 화면 사이

이전: [10-counting-dom.md](10-counting-dom.md) — 화면이 말해 주지 않는 것을 확인하기

---

## 깨진 전제

1차 내내 이 전제 위에서 만들었습니다.

> 기획서 PDF 하나 = 화면 하나. `ScreenSpec` 하나.

우리가 만든 픽스처가 그랬으니까요. 실물 기획서는 그렇게 오지 않습니다. 한 문서에
화면이 여럿 들어 있고, **화면 사이의 흐름도 그 문서에 적혀 있습니다.**

그래서 두 가지를 붙였습니다.

```
다중 화면   한 PDF -> ScreenSpec 여러 개
흐름       화면을 이어서 밟는 케이스
```

두 번째가 이 노트의 본론입니다. 첫 번째는 배관 작업이고, 두 번째는 **지금까지 잡을 수
없던 종류의 결함**에 닿습니다.

---

## 왜 흐름이 필요한가 — 아무도 틀리지 않았는데 안 되는 경우

SUT 의 `bad` 구현에 이런 결함을 심었습니다.

> 회원가입이 입력을 다 검증하고, 완료 화면까지 보여주는데,
> **계정을 실제로 등록하지 않는다.**

이 결함을 화면별 검증으로 잡을 수 있는지 보면:

| 검증 | 결과 |
|---|---|
| 회원가입 화면 케이스 14건 | 전부 통과 — 입력 검증도 하고 완료 화면도 뜬다 |
| 로그인 화면 케이스 7건 | 전부 통과 — 등록된 계정으로는 정상 동작한다 |

**어느 화면도 결함이 아닙니다.** 결함은 두 화면 사이에 있습니다.

이게 실무에서 troubles 로 이어지는 기획-구현 불일치의 전형입니다. 화면 단위로 리뷰하면
다 맞는데 이어 붙이면 안 되는 것. 그래서 화면을 이어서 밟아 보는 경로를 뒀습니다.

```
FAIL 흐름 signup → login — 화면을 이어서 밟았을 때
     흐름 'signup_then_login' 가 마지막 화면에서 기대와 어긋났습니다.
     (경로 '/dashboard' 미이동; 문구 '환영합니다' 미노출)
     각 화면의 케이스가 모두 통과했다면 결함은 화면 안이 아니라 **화면 사이**에
     있습니다 — 앞 화면이 남긴 상태가 뒤 화면에 이어지지 않는 경우입니다.
```

---

## 흐름의 위험: FAIL 이 애먼 화면을 지목한다

계획 단계에서 이 기능을 **권하지 않았습니다.** 이유가 하나였습니다.

> 로그인 → 검색 흐름이 실패했을 때, 로그인이 깨진 건가 검색이 깨진 건가?

앞 화면이 깨지면 뒤 화면의 결과는 전부 무의미해집니다. 그런데 리포트는 마지막 화면의
이름을 달고 FAIL 을 보고합니다. 개발자는 검색 코드를 뒤지고, 아무것도 못 찾고, 도구를
신뢰하지 않게 됩니다. **지목이 틀린 FAIL 은 오탐보다 나쁩니다.**

그래서 흐름을 만들 때 이 문제를 먼저 해결했습니다.

### 화면을 넘길 때마다 도착을 확인한다

```
1 navigate /signup
2 fill 이메일 newuser@test.com
3 fill 비밀번호 Signup1!
4 fill 비밀번호 확인 Signup1!
5 click 가입하기
6 assert  signup 성공          <- 여기가 핵심
7 navigate /login
8 fill 이메일 newuser@test.com
9 fill 비밀번호 Signup1!
10 click 로그인
   기대: /dashboard 이동 + "환영합니다"
```

6번 스텝이 없으면 회원가입이 깨져도 로그인이 지목됩니다. 있으면 그 스텝이 끊긴 것으로
기록되고, S5 의 기존 규칙("스텝이 끊기면 그 원인이 케이스 실패 원인")이 그 화면을
지목합니다.

```
FAIL 흐름 'signup_then_login' 가 스텝 6(assert 'signup 성공') 실패:
     경로 '/welcome' 미이동
```

**새 판정 로직을 만들지 않았습니다.** 이미 있던 규칙이 정확히 필요한 일을 합니다.
그 규칙을 처음 쓸 때는 "요소를 못 찾아 스텝이 끊긴 경우" 를 위한 것이었는데,
같은 규칙이 흐름의 중간 끊김에도 그대로 맞았습니다.

### 도착 확인은 '판정' 이 아니다

이 확인을 S5 의 판정 함수로 하지 않았습니다. 목적이 다릅니다 — 다음 화면으로 넘어가도
되는지, 넘어가지 못했으면 어디서 끊겼는지를 남기는 것뿐입니다. navigate 스텝이 4xx 를
실패로 확정하는 것과 같은 성질이라 실행 단계(S4)에 뒀습니다.

그리고 **일부러 좁게** 만들었습니다. 에러 영역과 화면 텍스트를 구분하지 않고, 실패
분류도 하지 않습니다. 그 이상을 이 자리에서 판단하면 판정 책임이 두 단계로 흩어집니다.

### 확인 기준을 흐름 표에 다시 적게 하지 않는다

각 화면의 `success_condition` 을 그 단계의 기준으로 씁니다. 흐름 표에 "여기서
'가입이 완료되었습니다' 가 떠야 한다" 를 또 적게 하면 같은 사실이 두 곳에 있고,
언젠가 한쪽만 고쳐집니다.

## 값은 라벨로 이어진다

흐름의 두 번째 문제입니다. 회원가입에 쓴 계정으로 로그인해야 하는데, 두 화면의
예시값이 다릅니다.

```
회원가입 §5 예시   이메일 newuser@test.com · 비밀번호 Signup1!
로그인   §5 예시   이메일 user@test.com    · 비밀번호 Abcd123!
```

로그인의 예시값을 쓰면 흐름이 확인하는 것이 '가입한 계정으로 로그인되는가' 가 아니게
됩니다. 그래서 **앞 화면에 넣은 값을 뒤 화면의 같은 라벨에 다시 넣습니다.**

사람이 손으로 확인할 때 하는 일이 정확히 그것입니다 — 가입에 쓴 이메일로 로그인합니다.

`element_id` 가 아니라 **라벨**을 키로 쓰는 이유: 화면이 다르면 element_id 도 다를 수
있지만(`signup.email` vs `login.user_email`) 사용자가 보는 라벨은 같습니다. 대신
기획서가 라벨을 일관되게 쓴다는 전제가 깔립니다.

### 이어받은 값의 의존값도 다시 계산한다

여기 함정이 하나 있습니다. 비밀번호를 이어받으면 '비밀번호 확인' 도 그 값이어야
합니다. dict 를 그대로 덮으면 `same_as` 규칙이 깨져 흐름이 **첫 화면에서부터**
실패합니다.

```python
overrides = {e.element_id: carried[e.label] for e in inputs if e.label in carried}
values, _ = resolve_values(inputs, overrides=overrides)   # 의존값 재계산
```

`resolve_values` 는 8번 노트에서 교차 필드 제약을 다루려고 만든 함수입니다. 그때
"위반값을 고정하고 의존값을 재계산한다" 는 계약으로 만들어 뒀는데, 흐름의 값 이어받기가
정확히 같은 모양이어서 그대로 쓸 수 있었습니다.

## 다중 화면: 경계를 어디서 가르나

화면 개요 표('화면 ID' 행이 있는 2열 표)의 등장이 새 화면의 시작입니다. 여기까지는
표를 읽는 것이라 결정적입니다. 문제는 **경계의 해상도**입니다.

**페이지 단위로만 가릅니다.** 개요 표가 페이지 중간에 있어도 그 페이지 전체를 새 화면의
것으로 봅니다.

페이지 안까지 쪼개려면 본문과 표를 순서 있는 블록으로 다시 읽어야 하는데(지금
`ParsedPage` 는 본문을 페이지당 한 덩어리로 담습니다), 그러면 **이미 검증된 세 화면의
추출 경로가 전부 영향권에 들어갑니다.** 실물 기획서는 화면마다 페이지를 새로 시작하는
것이 보통이므로, 이득이 확실할 때까지 미뤘습니다.

대신 가를 수 없는 경우를 조용히 넘기지 않습니다.

```
WARN 3페이지에 화면 개요 표가 2개 있습니다 (login, signup).
     페이지 단위로는 가를 수 없어 한 화면으로 묶었습니다 —
     화면마다 페이지를 새로 시작하세요.
```

앞 화면에 몰아 넣으면 뒤 화면의 요소 표가 앞 화면 것으로 추출되어 **두 화면의 검증이
모두 조용히 어긋납니다.**

### 표지 페이지

첫 개요 표 앞의 페이지(문서번호·작성일)는 첫 화면에 붙입니다. 별도 문서로 떼면 요소가
없는 빈 '화면' 이 하나 생기고, 버리면 앞머리에 적힌 화면 공통 규칙이 조용히 사라집니다.
화면당 PDF 하나였던 기존 기획서도 표지와 첫 화면이 같은 페이지에 있었으므로, 붙이는
쪽이 기존 동작과도 일치합니다.

### 화면마다 따로 LLM 을 부른다

세 화면을 한 번에 넣지 않습니다. 이유가 둘입니다.

1. **컨텍스트.** 8192 토큰 창을 금세 넘깁니다. 넘치지 않더라도 입력이 길어질수록 7B 가
   행을 빠뜨리는 빈도가 올라갑니다 — 이미 7행 표에서 버튼 행을 놓친 적이 있습니다.
2. **실패 격리.** 한 화면의 추출이 흔들려도 다른 화면의 결과가 오염되지 않습니다.

## 또 같은 실패 — 이번엔 필수 입력 문구

화면 세 개를 한 문서에 담고 처음 돌렸을 때 **오탐이 하나 났습니다.**

```
FAIL [required] 검색어 미입력 검증
     기대: '필수 항목을 입력하세요.'
     실제: '검색어를 입력하세요.'  <- 구현이 맞다
```

`필수 항목을 입력하세요.` 는 프롬프트 **few-shot 예시의 문구**입니다. 기획서에는
"검색어를 입력하세요." 라고 적혀 있었습니다. 단일 문서로 돌렸을 때는 맞혔는데, 문서를
합치자 틀렸습니다.

프롬프트에는 이미 이렇게 적어 뒀습니다.

> 상황 표현은 기획서마다 다릅니다 — 표현이 아니라 **의미**로 찾으세요.
> ## 예시의 값을 베끼지 마세요

**프롬프트는 보장이 아니라 부탁입니다.** 그리고 이 값도 결국 표에 그대로 적혀 있습니다.

| 상황 | 처리 |
|---|---|
| 검색어가 비어 있음 | "검색어를 입력하세요." 노출, 검색하지 않음 |

그래서 `declared_required_message()` 로 코드가 읽습니다. 이제 이 목록이 일곱 개입니다.

```
declared_element_ids        요소 ID
declared_element_types      유형 (목록 -> list)
declared_screen_meta        화면 ID · 경로
declared_sample_values      예시값
declared_scenarios          입력-결과 짝 + 건수
declared_required_message   필수 입력 문구       <- 이번에 추가
declared_flows              화면 흐름            <- 이번에 추가
```

### 확신할 수 있을 때만 답한다

'값이 비어 있는 상황' 행을 찾는 데는 표현 목록이 필요합니다(`비어 있`, `입력하지 않`,
`미입력`, `누락`, `공백`). 열거는 못마땅하지만, 프롬프트에 적어 둔 "의미로 찾으세요" 를
코드로 옮긴 것입니다. 그리고 **못 찾으면 LLM 의 판단을 그대로 씁니다** — 표현을 놓치는
것이 검증을 없애지 않습니다.

후보가 둘 이상이면 `None` 을 돌려줍니다. 요소별로 다른 문구를 쓰는 기획서에서는 어느
것이 화면 공통 문구인지 알 수 없고, 억측한 문구는 오탐이 됩니다.

`선택하지 않음`·`동의하지 않음` 은 후보에서 뺐습니다. 그것들은 요소 하나의 상태에
대한 문구이고(가입 경로 미선택, 약관 미동의), `required_message` 는 **화면 공통** 문구
입니다. 넣으면 회원가입 기획서에서 후보가 셋이 되어 판별을 포기하게 됩니다.

### 보정은 조용히 하지 않는다

```
! 설계 문서 경고: [search] 필수 입력 문구를 기획서 실패 조건 표대로
  '검색어를 입력하세요.' 로 맞췄습니다 (모델: '필수 항목을 입력하세요.').
  프롬프트를 확인하세요.
```

경고가 없으면 프롬프트가 나빠지고 있는지 알 수 없습니다. `[search]` 접두사는 화면이
여럿일 때만 붙습니다 — 어디를 고쳐야 하는지가 경고의 위치로 드러나야 합니다.

## 리포트: 흐름을 화면 칸에 넣지 않는다

처음엔 흐름 케이스를 마지막 화면(`login`) 칸에 넣었습니다. 결과가 이랬습니다.

```
login   전체 9  통과 3  실패 6      <- 로그인에 결함이 6개인 것처럼 읽힌다
```

로그인 자체의 결함은 4개입니다. 나머지 둘은 화면 사이의 결함이고 **고칠 곳이
다릅니다.** 그래서 따로 셉니다.

```
대상                            종류   전체  통과  실패
로그인   login                  화면      7     3     4
회원가입 signup                 화면     14    11     3
상품검색 search                 화면      8     4     4
화면 사이 signup_link_to_login   흐름      1     0     1
화면 사이 signup_then_login      흐름      1     0     1
```

같은 표에 두되 행을 구분합니다. 나란히 놓여야 **'화면은 다 통과인데 흐름만 실패'**
라는 모양이 한눈에 보이고, 그 모양이 곧 '결함은 화면 사이에 있다' 는 진단입니다.

## 주소로 이동하면 링크가 검증되지 않는다

여기까지 만들고 흐름의 스텝을 다시 봤더니 구멍이 하나 있었습니다.

```
 8 click     가입하기
 9 assert    signup 성공
10 navigate  /login        <- Prova 가 주소를 직접 친다
```

10번입니다. **화면을 잇는 요소가 검증되지 않습니다.** 완료 화면의 '로그인하러 가기'
링크가 엉뚱한 곳을 가리켜도, 링크가 아예 없어도, 흐름은 통과합니다. 도구가 스스로
주소를 치고 들어가니까요.

잘못된 링크는 실무에서 흔한 기획-구현 불일치인데 그 경로가 비어 있었습니다.

### 이동 방법을 기획서가 적는다

```
| 흐름 ID | 화면 순서 | 이동 방법 |
|---|---|---|
| signup_link_to_login | signup → login | 로그인하러 가기 |
| signup_then_login | signup → login | - |
```

이동 방법이 있으면 `navigate` 대신 그 요소를 누르고, **다음 화면의 경로에 도착했는지**
확인합니다.

```
10 click     로그인하러 가기
11 assert    login 도착        <- url_contains: /login
```

`bad` 의 링크를 `/search` 로 돌려 놓고 돌리면 이렇게 나옵니다.

```
FAIL 흐름 signup → login ('로그인하러 가기' 를 눌러 이동)
     흐름 'signup_link_to_login' 가 스텝 11(assert 'login 도착') 실패:
     경로 '/login' 미이동 (현재 http://localhost:8100/bad/search)
```

도착 확인이 **문구가 아니라 경로만** 보는 이유가 있습니다. 도착 직후의 화면은 아직
아무 동작도 하지 않은 상태이므로, 기획서의 성공 조건(제출 후 결과)을 요구하면 항상
실패합니다. 확인할 수 있는 것은 '여기로 왔는가' 뿐입니다.

### 흐름이 둘이 된 이유

처음엔 흐름 하나에 이동 방법을 넣었습니다. 그러자 **E1 이 가려졌습니다.**

E2(잘못된 링크)가 스텝 11에서 흐름을 끊으니, 그 뒤의 로그인 시도가 아예 실행되지
않아 E1(계정 미등록)이 보고되지 않습니다. 스텝이 끊기면 이후 판정이 무의미하다는
규칙 때문이고, **그 규칙 자체는 옳습니다.** 대신 확인하려는 질문이 둘이면 케이스도
둘이어야 합니다.

    signup_link_to_login   링크를 눌러 로그인 화면에 닿는가   -> 화면을 잇는 요소
    signup_then_login      주소로 가서 그 계정으로 되는가     -> 이어진 상태

같은 화면 쌍을 밟지만 확인하는 것이 다릅니다. 그래서 제목에 이동 방법을 넣습니다 —
제목이 같으면 리포트에서 어느 쪽이 실패했는지 구분할 수 없습니다.

## 기획서의 '유형' 열이 처음으로 검증된다

세 번째 결함 유형이 남았습니다.

> 기획서는 링크라고 했는데 구현은 버튼이다.

지금까지 기획서의 '유형' 열은 **우리 쪽에서만** 쓰였습니다. 체크박스면 `check()`,
선택이면 `select_option()` 을 부르는 식으로 액션을 고르는 데만 썼습니다. 구현이 그
유형을 지켰는지는 아무도 확인하지 않았습니다.

그래서 이 불일치가 통과했습니다. S3 는 role 로 못 찾아도 텍스트 일치로 찾아내
눌러 주니까요. 눌러지니까 아무 말 없이 지나가고, **기획서가 유형을 적어 둔 것이 검증에
아무 영향을 주지 않습니다.**

```python
def _check_declared_role(page, target, hint):
    if hint is None or hint.type not in ROLE_CHECKED_TYPES:
        return
    role = _role_for(hint)
    if page.get_by_role(role, name=target, exact=True).count() == 0:
        raise SpecTypeMismatch(target, hint.type, role)
```

### 탐지 실패와 나눠 둔다

`SpecTypeMismatch` 를 `GroundingError` 와 따로 뒀습니다. 이건 탐지 실패가 아니라
**기획-구현 불일치**입니다. 같은 실패로 묶으면 리포트에서 '요소를 못 찾았다' 로
분류되어 개발자가 라벨을 고치려 듭니다. 고쳐야 할 것은 요소의 종류입니다.

그래서 `element_not_found` 가 아니라 `assertion_mismatch` 로 분류합니다. 그리고
**요소가 아예 없는 경우**는 여전히 탐지 실패입니다 — 요소를 만드는 일과 종류를
바꾸는 일은 다릅니다. 순서를 그렇게 뒀습니다: 먼저 찾고, 찾은 뒤에 유형을 봅니다.

### 버튼과 링크만 대조한다

role 매핑을 신뢰할 수 있는 유형만 봅니다. 입력란은 넣을 수 없습니다 —
`input[type=password]` 는 ARIA 에서 textbox role 을 갖지 않으므로, 대조하면
**비밀번호 칸마다 '유형 불일치' 가 떠서 전부 오탐이 됩니다.**

버튼과 링크는 그 대조가 정확하고, **가장 값진 대조이기도 합니다.** 둘의 차이가
사용자에게 실제로 드러나기 때문입니다 — 링크는 새 탭으로 열 수 있고 주소를 복사할 수
있고 스크린리더가 '링크' 로 읽습니다.

확인할 수 없는 것을 확인한다고 주장하지 않습니다. 그게 이 도구에서 지켜야 하는
선입니다.

### 사유는 기획서가 쓴 낱말로

```
기획서의 유형('링크')과 구현이 다릅니다 —
link role 로는 찾을 수 없고 다른 종류의 요소로 구현돼 있습니다
```

처음엔 `'link'` 라고 적혀 나왔습니다. 리포트를 읽는 사람은 기획서와 대조하는데,
기획서에는 '링크' 라고 적혀 있습니다. 같은 낱말이어야 찾는 시간이 줄어듭니다.

로컬 7B 실측입니다.

| 대상 | good | bad |
|---|---|---|

화면별로 뜯어 보면 단일 문서로 돌렸을 때와 **정확히 같습니다.**

| 화면 | 단일 문서 bad | 통합 문서 bad |
|---|---|---|
| 로그인 | 3 PASS / 4 FAIL | 3 PASS / 4 FAIL |
| 회원가입 | 11 PASS / 3 FAIL | 11 PASS / 3 FAIL |

이게 이 작업의 수용 기준이었습니다. 문서를 합친 것만으로 화면별 판정이 달라지면 그건
확장이 아니라 후퇴입니다.

S1 골든 대조는 **54/54**, 전체 테스트는 **331개**입니다.

### 골든 파일을 새로 만들지 않았다

통합 문서의 화면들은 단일 화면 기획서와 **같은 표**를 담고 있으므로 정답도 같아야
합니다. 골든 JSON 을 하나 더 두면 같은 사실이 두 곳에 적히고, 한쪽만 고쳐졌을 때 어느
쪽이 맞는지 알 수 없게 됩니다. 그래서 기존 세 골든을 그대로 정답으로 씁니다.

덤이 있었습니다. **한 문서에 담았을 때 추출이 달라지는지**가 그대로 드러났고, 실제로
드러났습니다 — 위의 `required_message` 오탐이 이 대조에서 잡혔습니다.

## mock 도 내용을 보고 답해야 한다

작은 일인데 짚어 둘 만합니다. 화면이 여럿이면 mock 백엔드가 ScreenSpec 응답을 여러 번
돌려줘야 합니다. 호출 순서대로 주면 간단합니다 — 그런데 **화면 분리가 뒤바뀌어도
테스트가 통과합니다.** mock 은 첫 호출에 로그인을 주고, 파이프라인은 그것을 로그인
화면의 명세로 받아들입니다. 정작 넘긴 텍스트가 회원가입 것이었어도 알 수 없습니다.

그래서 프롬프트에 그 화면의 `화면 ID | login |` 행이 실려 있는지 보고 고릅니다. 못
고르면 오류를 냅니다. 테스트 도구가 무엇을 확인했는지 스스로 보증해야 합니다.

## 남은 구멍: SUT 의 상태가 실행 사이에 남는다

정직하게 적어 둡니다. 계정 등록은 SUT 프로세스의 상태이므로, `good` 을 한 번 돌리면 그
계정이 남습니다. 같은 SUT 에서 `good` 을 두 번째로 돌릴 때는 흐름이 '앞선 실행이 등록해
둔 계정' 으로 통과할 수 있습니다.

결함 탐지 방향은 이 영향을 받지 않습니다 — `bad` 는 어떤 순서로 돌려도 등록하지
않으므로 항상 실패합니다. 그래서 수용 기준의 무게를 `bad` 쪽에 뒀습니다. 다만 `good` 의
통과가 '이번 실행이 등록했기 때문' 이라는 증명은 첫 실행에서만 성립합니다.

`good` 과 `bad` 의 계정 저장소를 나눈 것도 같은 이유입니다. 공유하면 `good` 이 가입시킨
계정을 `bad` 의 로그인이 찾아내고, **심어 둔 결함이 실행 순서에 따라 사라집니다.**

## 이 노트에서 남길 것

1. **화면 단위 검증에는 구조적 사각지대가 있다.** 어느 화면도 틀리지 않았는데 이어
   붙이면 안 되는 결함이 있고, 그게 실무에서 가장 자주 troubles 로 이어지는 모양이다.
2. **기능을 넣기 전에 그 기능의 오진 가능성을 먼저 막는다.** 흐름의 위험은 '애먼 화면을
   지목하는 것' 이었고, 중간 도착 확인이 그것을 막는다. 위험을 막을 방법이 없으면
   기능을 넣지 않는 편이 낫다.
3. **이미 있는 규칙이 새 요구에 맞는지 먼저 본다.** '스텝이 끊기면 그 원인이 케이스
   실패 원인' 은 요소 미탐지를 위해 만든 규칙인데, 흐름의 중간 끊김에 그대로 맞았다.
4. **경계의 해상도를 욕심내지 않는다.** 페이지 안까지 쪼개면 정확하지만 이미 검증된
   경로가 전부 흔들린다. 못 가르는 경우를 경고로 알리는 편이 낫다.
5. **집계 단위가 진단을 만든다.** 흐름 실패를 화면 칸에 합치면 그 화면에 결함이 하나 더
   있는 것처럼 읽힌다. 숫자를 어디에 넣느냐가 읽는 사람의 행동을 바꾼다.
6. **표에 적힌 사실은 코드가 읽는다 — 여섯 번째, 일곱 번째 확인.** 프롬프트에 "예시를
   베끼지 마세요" 라고 적어 둔 것이 문서가 길어지자 무력해졌다. 프롬프트는 보장이
   아니라 부탁이다.
7. **도구가 대신 해 주는 일은 검증되지 않는다.** 주소로 이동하면 편하지만, 화면을 잇는
   요소가 검증에서 빠진다. '우리가 대신 하고 있는 것이 무엇인가' 를 물어야 그 구멍이
   보인다.
8. **기획서가 적어 둔 것이 검증에 쓰이는지 확인한다.** '유형' 열은 우리 액션을 고르는
   데만 쓰이고 구현과 대조되지 않았다. 기획서에 적혀 있는데 아무도 확인하지 않는
   항목이 있으면, 그건 기획서가 아니라 도구의 구멍이다.
9. **확인할 수 없는 것을 확인한다고 하지 않는다.** input[type=password] 는 textbox
   role 이 없으므로 입력란의 유형은 대조하지 않는다. 범위를 넓히면 오탐이 되고,
   오탐은 미탐보다 도구의 신뢰를 빨리 무너뜨린다.
