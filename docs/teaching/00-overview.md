# 00. Prova가 하는 일 — 전체 그림

> 이 문서를 먼저 읽으세요. 나머지 노트는 각 단계를 자세히 다룹니다.

---

## 한 문장

**기획서를 읽고 "여기 적힌 검증 규칙이 실제 웹사이트에 구현됐는지" 사람 대신 확인해주는 프로그램.**

---

## 왜 만드나

㈜WITCHES가 이 프로젝트를 의뢰한 이유는 **기획과 구현이 어긋나서 생기는 트러블**입니다.

기획자가 "비밀번호는 8자 이상, 대문자 1자 이상"이라고 문서에 썼는데, 개발자가 구현할 때
대문자 검사를 빼먹었다고 해봅시다. 이걸 발견하는 방법은 지금은 하나뿐입니다 — QA 담당자가
기획서를 읽고, 테스트할 값을 손으로 만들고, 브라우저에서 하나씩 입력해보는 것입니다.

화면 하나에 규칙이 10개면 케이스가 10개 이상 나오고, 화면이 20개면 200번을 손으로 해야 합니다.
그리고 개발자가 코드를 수정하면 **처음부터 다시** 해야 합니다.

Prova는 이 과정을 자동화합니다.

---

## 실제로 무슨 일이 일어나는가

기획서에 이렇게 적혀 있다고 해봅시다.

> **비밀번호**
> - 최소 길이는 8자다.
> - 영문 대문자를 1자 이상 포함해야 한다.
> - 특수문자를 1자 이상 포함해야 한다.
> - 위 규칙 중 하나라도 위반하면 "비밀번호는 8자 이상이며 대문자·특수문자를 각 1자 이상
>   포함해야 합니다." 를 노출한다.

Prova는 이 문장을 읽고 **스스로 이렇게 생각합니다**.

| 검사할 규칙 | 그 규칙만 어기는 값 | 기대하는 결과 |
|---|---|---|
| 8자 이상 | `Aa1!aaa` (7자) | 에러 문구가 떠야 함 |
| 대문자 포함 | `a1!aaaaa` (대문자만 없음) | 에러 문구가 떠야 함 |
| 특수문자 포함 | `Aa1aaaaa` (특수문자만 없음) | 에러 문구가 떠야 함 |

그리고 **진짜 크롬 브라우저를 열어서** 이 값들을 직접 입력하고 로그인 버튼을 누릅니다.

- 에러가 뜨면 → **PASS** (구현이 규칙을 지키고 있다)
- 에러가 안 뜨면 → **FAIL** (개발자가 그 검증을 빼먹었다)

우리가 만든 `bad` 앱(일부러 검증을 빼먹은 버전)에서 실제로 이렇게 나왔습니다.

```
FAIL [require_uppercase] 비밀번호 대문자 검증
     기획서의 'require_uppercase' 검증 규칙이 구현에서 확인되지 않았습니다.
     기대: '비밀번호는 8자 이상이며 대문자·특수문자를 각 1자 이상 포함해야 합니다.'
     실제: '로그인 정보를 확인해주세요.'
```

개발자는 이 한 줄만 보고 **어느 검증 코드를 추가해야 하는지** 바로 알 수 있습니다.

## 지금까지의 결과 (2026-08-16 실측)

로그인·회원가입·검색 세 화면을 각각 두 개의 웹앱에 대해 검증했습니다.

| 화면 | 대상 | 결과 |
|---|---|---|
| 로그인 | `good` — 기획서를 지킨 구현 | **9건 전부 PASS** (통과율 100%) |
| 로그인 | `bad` — 검증을 일부러 빼먹은 구현 | **3 PASS / 6 FAIL** |
| 회원가입 | `good` | **16건 전부 PASS** |
| 회원가입 | `bad` | **12 PASS / 4 FAIL** |
| 검색 | `good` | **9건 전부 PASS** |
| 검색 | `bad` | **5 PASS / 4 FAIL** |
| 통합 문서 (3화면+흐름 2) | `good` | **36건 전부 PASS** |
| 통합 문서 (3화면+흐름 2) | `bad` | **20 PASS / 16 FAIL** |

로그인 `bad`에서 FAIL로 잡힌 것: 이메일 형식 검증 · 비밀번호 길이 · 대문자 · 특수문자 —
**정확히 빼먹은 것 4개**입니다.

그리고 중요한 점: **`bad`에서도 PASS가 나옵니다.** "필수 입력" 검증은 `bad`에도 구현돼
있어서입니다. 한 리포트 안에 "구현된 규칙은 PASS, 빼먹은 규칙은 FAIL"이 함께 나오는 것이
이 판정을 신뢰할 수 있는 근거입니다. 전부 FAIL이 나오면 도구가 고장난 건지 구분할 수 없습니다.

회원가입 화면이 이걸 더 잘 보여줍니다. "필수 입력" 규칙을 가진 요소가 **6개**인데 검증이
빠진 것은 약관 동의 하나뿐이고, Prova는 **그 하나만** FAIL로 지목합니다. 닉네임도
"2자 이상"은 PASS인데 "10자 이하"만 FAIL입니다 — 한 입력란의 규칙 중 일부만 구현된
경우까지 규칙 단위로 갈라냅니다.

검색 화면은 **검증하는 것 자체가 다릅니다.** 앞의 두 화면은 "규칙을 어긴 값에 에러가
뜨는가"였는데 검색은 "정상 입력에 정해진 결과가 나오는가"입니다. `bad`에 심은
'대소문자 구분' 결함이 그 차이를 보여줍니다 — 입력값에 흠이 없고 구현도 검사를 하는데
**검사 방법이 기획서와 다릅니다.** 규칙을 어긴 값을 만드는 방식으로는 절대 잡을 수 없는
종류입니다.

화면 확장에서 무엇이 새로 필요했는지는 [08-screen-expansion.md](08-screen-expansion.md)
(회원가입)와 [09-search-scenarios.md](09-search-scenarios.md)(검색)에 있습니다.
검색의 확인 경로를 문구에서 DOM 으로 넓힌 이야기는 [10-counting-dom.md](10-counting-dom.md)
에 있습니다 — 통과하고 있었지만 실은 아무것도 확인하지 않던 케이스를 찾은 기록입니다.

## 6단계 파이프라인

`src/prova/` 폴더가 이 순서대로 정리돼 있습니다. 각 단계는 앞 단계의 결과를 받아 다음 단계에
넘깁니다.

```
login_spec.pdf  (기획서 PDF)
      │
      ▼
   [S1] 기획서 읽기            s1_spec_extractor/
      │  ScreenSpec (화면 하나의 명세)
      ▼
   [S2] 테스트 케이스 만들기    s2_case_generator/
      │  TestCase[] (검사할 시나리오 목록)
      ▼
   [S3] 화면에서 요소 찾기      s3_grounder/
      │  ElementLocation (실제 입력란·버튼 위치)
      ▼
   [S4] 실제로 조작하기         s4_executor/
      │  StepResult[] (각 동작의 결과 + 스크린샷)
      ▼
   [S5] 판정하기                s5_verifier/
      │  Verdict (PASS/FAIL + 근거)
      ▼
   [S6] 리포트 만들기           s6_report/
      │
      ▼
   report.html
```

### 각 단계 한 줄 설명

| 단계 | 하는 일 | AI 사용 |
|---|---|---|
| **S1** | PDF에서 화면 명세를 뽑는다 | **사용** (문장 → JSON 변환) |
| **S2** | 명세에서 테스트 케이스를 만든다 | 거의 안 씀 (제목만) |
| **S3** | "이메일"이라는 라벨로 실제 입력란을 찾는다 | 1차는 안 씀 (2차에 VLM) |
| **S4** | 브라우저를 조작한다 | 안 씀 |
| **S5** | 기대와 실제를 비교해 판정한다 | 안 씀 |
| **S6** | 결과를 모아 리포트를 만든다 | 안 씀 |

**AI를 쓰는 곳이 S1뿐**이라는 게 중요합니다. 이유는 [03-llm-vs-code.md](03-llm-vs-code.md)에서
자세히 다룹니다.

## 어디서 무엇이 돌아가는가

GPU가 필요한 부분과 브라우저가 필요한 부분을 나눠 놓았습니다.

```
[CHEETAH GPU 서버]                      [내 노트북 (Windows)]

 vLLM                                    Prova 본체
 └ Qwen2.5-7B-AWQ  ←── SSH 터널 ──→      ├ S1·S2·S5·S6
   (:8000)                                └ S3·S4 (Playwright + 크롬)

                                         테스트 대상 웹앱 (SUT)
                                         └ FastAPI (:8100)
```

**왜 나눴나?** GPU 서버에 크롬을 설치할 필요가 없고, 코드 입장에서 GPU 모델은 그냥
`http://localhost:8000`이 됩니다. SSH 터널이 그 연결을 만들어 줍니다.

## 테스트 대상 웹앱을 두 개 만든 이유

`sut/app.py`에 화면마다 두 버전이 있습니다.

- `/good/login`, `/good/signup`, `/good/search` — 기획서를 **전부 지킨** 구현
- `/bad/login`, `/bad/signup`, `/bad/search` — 일부러 **각각 3가지를 빼먹은** 구현

두 앱의 **HTML은 완전히 동일**하고 검증 로직만 다릅니다. 이게 중요합니다. 만약 HTML도
다르면, FAIL이 났을 때 "검증을 빼먹어서인가, 요소를 못 찾아서인가"를 구분할 수 없습니다.
**변수를 하나만 두는 것**이 실험의 기본입니다.

로그인 `bad`에 심어둔 것:
1. 비밀번호 복잡도(대문자·특수문자) 검증 없음
2. 이메일 형식 검증 없음
3. 에러 문구가 기획서와 다름 ("로그인 정보를 확인해주세요.")

회원가입 `bad`에는 **로그인에서 확인할 수 없었던 종류**를 골라 심었습니다. 같은 종류를
한 번 더 심으면 화면을 늘린 만큼의 검증력을 얻지 못합니다.

1. 비밀번호 확인 일치 검증 없음 — 값 하나만 봐서는 판정할 수 없는 규칙
2. 약관 동의 필수 검증 없음 — 입력이 아니라 '체크 상태'를 보는 규칙
3. 닉네임 최대 길이 검증 없음 (최소 길이만 구현) — 한 입력란의 규칙 중 일부만 빠진 경우

3번이 "규칙 하나당 케이스 하나" 설계의 근거입니다. 최소·최대를 한 케이스로 묶어 검사하면
최소 쪽이 걸려 에러가 뜨고, **최대 검증이 없다는 사실이 가려집니다.**

검색 `bad`에는 또 다른 종류를 심었습니다.

1. **영문 대소문자를 구분한다** (기획서는 구분하지 않는다고 명시) — 값에 흠이 없는데
   결과가 틀립니다. 규칙 위반으로는 표현할 방법이 없습니다
2. **결과가 0건일 때 안내 문구를 노출하지 않는다** — 틀린 것을 보여주는 게 아니라
   보여줘야 할 것을 안 보여주는 누락입니다
3. 검색어 최소 길이 검증 없음 — 규칙 기반 경로가 이 화면에서도 도는지 확인하는 역할

1번이 검색 화면을 추가한 이유입니다. 로그인·회원가입의 결함은 모두 '값을 검사하지
않았다'였고 위반값 생성으로 잡혔습니다. 이건 검사는 하는데 **방법이 기획서와 다릅니다.**

## 용어 사전

처음 보면 막히는 단어들입니다.

| 용어 | 쉽게 말하면 |
|---|---|
| **SUT** | System Under Test. 테스트 **대상** 웹앱. 우리가 만든 `good`/`bad` 미니 로그인 앱 |
| **pydantic** | 데이터 모양을 미리 정해두고, 어기면 바로 알려주는 파이썬 도구. `models.py`가 이걸로 쓰여 있다 |
| **JSON Schema** | "이 데이터는 이런 필드를 가져야 한다"를 기계가 읽을 수 있게 적은 것 |
| **response_format** | AI에게 "이 형식 밖으로 나가지 마"라고 강제하는 기능. 없으면 AI가 필드 이름을 멋대로 지어낸다 |
| **AWQ 양자화** | 모델을 압축해 메모리를 4분의 1로 줄이는 기술. 7B 모델이 15GB → 5.3GB가 된다 |
| **VRAM** | 그래픽카드(GPU)의 메모리. 우리는 10.2GiB만 쓸 수 있다 |
| **KV 캐시** | AI가 긴 글을 처리할 때 앞부분 계산을 기억해두는 공간. 이게 있어야 빠르다 |
| **vLLM** | AI 모델을 서버로 띄워 여러 요청을 효율적으로 처리하는 프로그램 |
| **Playwright** | 사람 대신 브라우저를 조작하는 도구. 클릭·입력·스크린샷을 코드로 한다 |
| **selector** | 웹페이지에서 특정 요소를 가리키는 주소. `#email` 같은 것 |
| **DOM** | 웹페이지의 구조를 나무 모양으로 표현한 것. HTML의 내부 표현 |
| **LangGraph** | 여러 단계를 "상태 기계"로 연결하는 도구. 조건 분기와 재시도를 다룬다 |
| **VLM** | Vision-Language Model. 이미지를 보고 이해하는 AI. 2차에서 스크린샷으로 버튼 위치를 찾는 데 쓴다 |
| **positive / negative 케이스** | 정상 케이스 / 일부러 규칙을 어기는 케이스 |
| **오탐 (false positive)** | 문제가 없는데 문제라고 보고하는 것. QA 도구에서 가장 위험하다 |
| **미탐 (false negative)** | 문제가 있는데 놓치는 것 |
| **관통 / walking skeleton** | 전 단계를 얇게라도 끝까지 연결해 돌아가게 만드는 것 |
| **회귀 테스트** | 새 기능을 넣었을 때 기존 기능이 망가지지 않았는지 확인하는 테스트 |

## 직접 눈으로 보기

숫자와 로그만 보면 실감이 안 난다. 브라우저를 띄워 Prova 가 스스로 입력하고 클릭하는 것을
지켜볼 수 있다.

```powershell
# 테스트 대상 웹앱 (별 터미널)
uv run uvicorn sut.app:app --port 8100

# bad 구현에 한 케이스만 천천히 실행 — 브라우저 창이 뜬다
uv run prova run --pdf fixtures/specs/login_spec.pdf `
  --url http://localhost:8100/bad `
  --only require_uppercase --headed --slow 500
```

| 옵션 | 하는 일 |
|---|---|
| `--headed` | 브라우저 창을 띄운다 (기본은 화면 없이 실행) |
| `--slow 500` | 동작 사이 0.5초 지연. 없으면 0.1초에 끝나 눈으로 못 따라간다 |
| `--only <패턴>` | `case_id` 에 패턴이 든 케이스만 실행 |
| `--video` | 실행 영상(webm)을 `runs/<run-id>/video/` 에 녹화 |

`--url` 을 `.../good` 으로 바꿔 한 번 더 실행하면 차이가 분명해진다. 같은 값을 넣었는데
한쪽은 기획서가 지정한 에러 문구가, 다른 쪽은 엉뚱한 문구가 뜬다.

**주의**: `--only` 가 아무 케이스도 고르지 못하면 실행을 멈춘다. 빈 목록으로 진행하면
"0건 실행, 통과율 100%" 리포트가 나오는데, 그건 아무것도 검증하지 않은 상태다.
