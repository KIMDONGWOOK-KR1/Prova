# 23 · 두 단계 실행 — 한 GPU 에 두 모델을 시간분할로 싣는다

이전: [22-figma-merge.md](22-figma-merge.md) — 두 입력이 어긋나면 판정하지 않고 보고한다

## 문제 — 두 실물 모델이 한 GPU 에 같이 안 들어간다

Prova 는 실물 모델을 두 군데서 씁니다. S1 추출에 7B(텍스트 LLM), S3 의 2차
경로에 VL(화면을 보는 VLM). 그런데 우리 MIG 조각은 9.50 GiB 이고 7B 혼자
8.30 GiB 를 씁니다 — 동시 적재가 물리적으로 불가능합니다 (README 의 GPU
제약 절). 그래서 지금까지 "두 실물 모델을 한 실행에서" 는 못 했고, 각각
따로만 측정했습니다.

시간으로 나누면 됩니다. 추출이 끝나면 7B 는 더 필요 없고, 탐지가 시작되기
전에는 VL 이 필요 없습니다 — 두 모델이 **같은 시각에** 필요한 순간은 원래
없습니다. 없던 것은 그 사이를 건너는 다리뿐입니다.

    uv run prova run --pdf spec.pdf --url http://... --plan-only   # 7B 로 S1~S2
    (tmux 에서 7B 를 내리고 VL 을 올린다)
    uv run prova run --resume runs/<id> --vlm http://... --vlm-model ...  # S3~S6

## 경계는 원래 거기 있었다

`pipeline.py` 에는 이미 `build_plan`(S1~S2, 브라우저 불필요)과 그 뒤(S3~S6,
브라우저 필요)의 경계가 있었습니다 — 웹 UI 의 계획 승인 화면 때문에 먼저
생긴 경계입니다. 이번 작업은 그 경계에 파일 하나(`plan.json`)를 끼워 넣은
것뿐입니다. 좋은 경계는 이렇게 두 번 값을 합니다: 처음엔 "사람이 실행 전에
계획을 본다" 를 위해, 이번엔 "서버를 바꾸는 사이에 계획이 살아남는다" 를
위해.

재개가 **LLM 없이 성립한다**는 사실이 이 기능의 존재 근거입니다. S3~S6 에
LLM 이 한 줄도 없다는 것은 노트 여러 곳에서 반복한 신뢰 근거인데, 여기서는
그 사실이 기능이 됩니다 — 7B 를 내린 뒤에도 나머지 절반이 돌아야 하니까요.
거꾸로 말하면, S3~S6 에 LLM 을 넣고 싶어지는 날 이 기능이 먼저 깨집니다.
`resume_pipeline` 이 `llm` 인자를 아예 받지 않는 이유입니다.

## 저장·복원이 산출물을 바꾸면 안 된다

`plan.json` 에는 입력 기록(pdf 경로와 sha256, 대상 URL)과 산출물(문서,
케이스 전체, 선택 목록)이 들어갑니다. 계약은 하나입니다 — **재개한 실행이
한 번에 돌린 실행과 같은 판정을 낸다.** 저장·복원이 산출물을 조금이라도
바꾸면 "사람이 승인한 계획과 다른 것이 도는" 사고가 됩니다.
`test_two_stage_e2e.py` 가 두 실행의 판정을 케이스 단위로 대조해 이 계약을
지키고, 코드 쪽에서는 두 경로가 같은 `_execute` 를 지나게 해서 구조로도
보장합니다.

같은 이유로 선택된 케이스 본문을 두 번 저장하지 않습니다. `plan.json` 은
전체 케이스(`all_cases`)와 선택된 id 목록만 담고, 복원은 항상 전체에서 id 로
골라냅니다 — 본문 사본이 둘이면 어긋날 자리가 생깁니다.

## 조용히 무시하지 않는다

두 군데서 기존 규칙이 반복됩니다.

- `--resume` 에 `--pdf` 나 `--request` 를 함께 주면 **에러**입니다. 재개의
  입력은 전부 계획에서 옵니다 — 다시 받으면 승인된 계획과 다른 것이 돌 수
  있고, 받고서 조용히 버리면 사용자는 적용됐다고 믿습니다. 반대로
  `--plan-only` 에 `--vlm` 같은 실행 단계 옵션을 주는 것도 에러입니다.
- 계획 이후 pdf 가 바뀌면(sha256 불일치) **경고가 리포트까지** 갑니다.
  재개는 pdf 를 다시 읽지 않으므로 판정은 계획 시점 문서 기준입니다 — 그
  사실을 사람이 모르면, 바뀐 기획서로 검증했다고 착각합니다.

리포트에는 "두 단계 실행" 상자가 생깁니다 — 추출을 누가(백엔드) 언제 했는지,
실행이 별도로 수행됐다는 사실. 재개 실행은 `llm=None` 으로 돌기 때문에 계획
기록이 없으면 추출 백엔드가 리포트에서 사라집니다 — mock 리포트를 실제로
착각하는 사고와 같은 부류라서, 계획이 백엔드 이름을 갖고 다닙니다.

## 실물 두 모델로 관통시켰습니다 (2026-08-26)

배관이 도는지는 mock 으로 압니다. 이 기능이 존재하는 이유는 **실물 7B 와 실물
VL 을 한 실행에 넣는 것**이므로, 그것으로 재 봤습니다. 대상은 `nolabel`
(검색 화면, 아이콘 전용 버튼 — 라벨이 없어 1차 경로가 막히는 화면)입니다.

    # 7B 가 8000 에 있는 상태
    uv run prova run --pdf fixtures/specs/search_spec.pdf         --url http://localhost:8100/nolabel --run-id two-model-real --plan-only
    # tmux 에서 7B 를 내리고 VL 을 올린다 (8001)
    uv run prova run --resume runs/two-model-real         --vlm http://localhost:8001/v1 --vlm-model qwen-vl

| | 2차 경로 없음 (기준선) | 실물 VL |
|---|---|---|
| 판정 | 1 PASS / 9 FAIL | **9 PASS / 1 FAIL** |
| 이미지로 찾아 진행 | 0건 | **8건** |

기준선은 같은 계획을 `--vlm` 없이 재개한 것입니다 — 같은 계획, 같은 화면,
2차 경로만 다릅니다.

남은 FAIL 1건은 탐지 실패가 아니라 **심어 둔 결함**입니다: `요소 라벨 확인`
이 "'검색': 일치하는 요소가 없음" 으로 떨어졌고, 그게 `nolabel` 의 라벨
누락입니다. 2차 경로가 8건을 이미지로 살려내면서도 그 결함은 덮지 않았다는
것이 이 표에서 읽어야 할 부분입니다 — 화면을 보는 모델을 넣으면 "어떻게든
진행하는" 쪽으로 기울기 쉬운데, 라벨 결함은 라벨 결함으로 남았습니다.

리포트에는 추출이 `vllm:Qwen/Qwen2.5-7B-Instruct-AWQ` 로 기록됐습니다.
재개 실행에는 LLM 이 한 줄도 없는데도 그렇습니다 — 계획이 백엔드 이름을 갖고
다니기 때문입니다.

이 실행이 증명하지 않는 것: **VL 의 좌표 정확도**입니다. 그건 판정이 아니라
좌표로 재야 하고, 시험지 50개로 따로 쟀습니다(노트 13). 여기서 보이는 9 PASS
는 "이 화면에서 클릭이 됐다" 이지 "탐지가 정확하다" 가 아닙니다.
