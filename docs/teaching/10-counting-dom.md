# 10 · 화면이 말해 주지 않는 것을 확인하기 — 건수를 DOM 에서 센다

이전: [09-search-scenarios.md](09-search-scenarios.md) — 규칙으로 표현할 수 없는 검증

---

## 무엇이 문제였나

9번 노트에서 검색 화면을 붙이면서 이렇게 확인했습니다.

```
notebook 을 검색하면  ->  화면에 "검색 결과 3건" 이 떠야 한다
```

돌아갑니다. `good` 은 통과하고 `bad` 는 대소문자 구분 결함에 걸려 실패합니다.
그런데 이 검증에는 **기획서가 아니라 구현에 대한 가정**이 하나 숨어 있습니다.

> 화면이 건수를 문구로 보여준다.

우리 SUT 는 그렇게 만들었으니 당연히 성립합니다. WITCHES 실물 화면은 다를 수 있습니다.
결과 목록만 렌더하고 "3건" 이라는 글자를 아무 데도 안 찍는 화면이 흔합니다.
그러면 이 케이스는 **아무것도 확인하지 못한 채 초록불이 됩니다.**

확인하지 않은 것과 확인해서 통과한 것은 다릅니다. 그런데 리포트에서는 똑같이 PASS 로
보입니다. 이게 이번 작업을 한 이유입니다.

## 왜 `expect_text` 를 재해석하지 않았나

가장 손쉬운 방법은 `expect_text` 에 `"3"` 을 적고 그 값을 개수로 읽는 것입니다.
필드를 안 늘려도 되고 S1 도 안 고쳐도 됩니다.

하지 않았습니다. `expect_text` 는 '화면에서 찾을 문구' 이고, 그 의미로 판정 함수가
쓰고 있습니다. `"3"` 을 넣으면 화면 아무 곳의 3 에나 걸립니다 — 가격, 페이지 번호,
"3개월 무이자". 통과는 하는데 검증은 없습니다.

9번 노트에 미리 적어 둔 그대로 했습니다.

> 나중에 건수를 DOM 에서 직접 세거나 URL 을 확인해야 하면 **필드를 추가한다.**
> 이 필드의 의미를 넓혀 재해석하면 안 된다 — 필드 이름이 할 수 있는 일을 말하고
> 있어야 한다.

`Scenario.expect_count`, `Expectation.count`, `Expectation.count_target`,
`ExpectedType` 에 `result_count`. 이름이 하는 일을 말합니다.

## 어려운 지점: S3 의 계약을 건드려야 한다

4번 노트에 적힌 S3 의 계약이 이것입니다.

> **정확히 1개 & 보이는 것만 확정한다.** 후보가 0개면 못 찾은 것이고, 여러 개면 어느
> 것을 조작해야 할지 모른다. 아무거나 집어서 진행하면 그 케이스의 FAIL 이 구현 결함
> 때문인지 잘못된 요소를 눌러서인지 구분할 수 없게 된다.

이 계약이 지금까지 판정을 신뢰할 근거였습니다. 그런데 **세려면 여러 개를 봐야 합니다.**

계약을 느슨하게 만들면(“여러 개도 허용”) 검색 화면은 되지만 로그인·회원가입의 판정
근거가 함께 약해집니다. 이미 초록불인 세 화면을 위험에 넣는 변경입니다.

### 한 겹 내려가면 계약이 안 깨진다

세는 대상을 다시 보면 두 층입니다.

```
컨테이너   검색 결과 목록      <- 1개여야 한다 (어디를 셀 것인가)
  항목     Notebook Pro 15   <- 여러 개다   (몇 개인가)
  항목     Notebook Air 13
  항목     Notebook Slim 14
```

모호한 것은 항목의 개수뿐이고, 그건 **세면 답이 나옵니다.** '어디를 셀 것인가' 는
전혀 모호하지 않습니다. 그러면 계약을 건드릴 필요가 없습니다.

```python
def count_items(page, target, hint=None) -> CollectionCount:
    container = page.get_by_role(container_role, name=target, exact=True)
    found = container.count()
    if found > 1:
        # 컨테이너의 '정확히 1개' 계약은 세는 경로에서도 유지한다
        return CollectionCount(target, status="ambiguous", count=found, ...)
    n = container.get_by_role(item_role).count()
    return CollectionCount(target, status="ok", count=n, ...)
```

`ground()` 는 한 줄도 고치지 않았습니다. 경로를 하나 더 뒀을 뿐입니다.

**기존 코드를 고쳐서 새 요구를 담을지, 옆에 새 경로를 둘지**는 확장할 때마다 나오는
갈림길입니다. 판단 기준은 '어느 쪽이 코드가 짧은가' 가 아니라 **'이미 신뢰하는 것을
위험에 넣는가'** 입니다.

## 진짜 함정: 0건

이번 작업에서 가장 오래 생각한 부분입니다.

검색 결과가 0건인 화면은 목록을 **아예 렌더하지 않습니다.** 조건부 렌더링이고,
그게 정상 구현입니다.

```html
{% if results %}
<ul class="results" aria-label="검색 결과 목록">...</ul>
{% endif %}
```

그러면 `zzzz` 를 검색한 뒤 목록을 찾으면 없습니다. 이걸 탐지 실패로 처리하면
**구현이 완벽한 화면에서 '0건이어야 한다' 는 케이스가 FAIL 이 됩니다.** 오탐입니다.

반대로 목록 부재를 항상 0건으로 처리하면, 3건이 나와야 하는데 목록이 없는 진짜 실패를
놓칩니다. 미탐입니다.

### '못 찾았다' 와 '0개다' 는 다른 사실이다

숫자로는 둘 다 0 입니다. 합치면 판정이 거짓말을 합니다. 그래서 나눠 담습니다.

```python
@dataclass
class CollectionCount:
    target: str
    status: str          # "ok" | "absent" | "ambiguous"
    count: int = 0
    detail: str = ""
```

그리고 **판단은 S3 가 하지 않습니다.** S3 는 무엇을 봤는지만 사실대로 보고하고,
기대값과 맞춰 보는 것은 S5 의 일입니다.

```python
if got.status == "absent":
    if want == 0:
        return True, f"{target!r} 이 렌더되지 않음 — 0건으로 확인"
    return False, f"{want}건이 나와야 하는데 ... 찾지 못했습니다"
```

같은 `status="absent"` 인데 기대값에 따라 PASS 와 FAIL 로 갈립니다. 관측과 판단을
나눠 두지 않았으면 이 갈림을 표현할 자리가 없었을 것입니다.

### 원인을 단정하지 않는다

목록이 없는 이유는 둘일 수 있습니다.

1. 구현이 결과를 못 찾았다 (진짜 결함)
2. 목록에 접근성 이름이 없어 도구가 못 찾았다 (도구의 한계 또는 접근성 결함)

화면만 보고는 구분할 근거가 없습니다. 그래서 하나로 단정하지 않고 양쪽을 사유에 함께
적습니다.

```
3건이 나와야 하는데 '검색 결과 목록' 을 화면에서 찾지 못했습니다.
결과가 0건이거나, 목록에 접근성 이름('검색 결과 목록')이 없습니다.
```

억측한 원인을 적으면 개발자가 엉뚱한 곳을 고칩니다. 그건 오탐보다 더 나쁩니다 —
FAIL 은 맞는데 지목이 틀린 상태라 도구를 신뢰할 수 없게 됩니다.

## 부수 효과: 접근성 이름이 필요해졌다

목록을 지목하려면 이름이 있어야 합니다.

```html
<ul class="results" aria-label="검색 결과 목록">
```

검증을 위한 장치처럼 보이지만 아닙니다. `list-style:none` 인 목록은 스크린리더
사용자에게도 이름이 없으면 무엇의 목록인지 알 수 없습니다. 원래 있어야 하는 속성입니다.

그리고 뒤집어 보면 이게 쓸모가 있습니다 — **실물 화면에 이 이름이 없으면 Prova 가
목록을 못 찾고, 그 사실 자체가 접근성 결함 보고가 됩니다.** S3 가 처음부터 접근성
속성을 먼저 보도록 설계한 것(4번 노트)이 여기서 한 번 더 값을 냈습니다.

## 표에서 건수를 읽는 방법 — 제목이 아니라 값의 모양

기획서 §6 이 이렇게 바뀌었습니다.

| 검색어 | 결과 건수 | 노출돼야 하는 문구 |
|---|---|---|
| notebook | 3 | 검색 결과 3건 |
| zzzz | 0 | 검색 결과가 없습니다. |

9번 노트의 교훈("표에 그대로 적힌 사실은 코드가 읽는다")대로 `pdf_parser` 가 읽습니다.
그런데 **어느 열이 건수 열인지** 를 어떻게 아느냐가 남습니다.

열 제목으로 찾으면 안 됩니다. 기획서마다 '결과 건수'·'개수'·'건수'·'결과 수' 로
다르게 쓰고, 표현을 하나 놓칠 때마다 건수 검증이 조용히 사라집니다.

**값의 모양으로 찾습니다.** 비어 있지 않은 칸이 전부 정수인 열이 건수 열입니다.

```python
count_col = next(
    (i for i in other_cols if _is_integer_column(table.rows[1:], i)), None
)
```

'노출돼야 하는 문구' 열의 값("검색 결과 3건")은 정수가 아니므로 섞이지 않습니다.
표현에 흔들리지 않고, 새 표현이 나와도 코드를 안 고칩니다.

같은 생각으로 요소 표의 **'유형' 열도** 코드가 읽게 바꿨습니다
(`declared_element_types`). '목록' 은 `list` 이고 '입력' 은 `input` 입니다 —
추론할 여지가 없습니다. 유형이 틀리면 검증이 조용히 사라지므로(목록을 `text` 로 읽으면
건수 케이스가 아예 안 만들어집니다) 이것도 LLM 에 맡길 일이 아니었습니다.

단, **모르는 표현은 건드리지 않습니다.** 기획서가 '멀티셀렉트' 같은 새 유형을 쓰면
매핑하지 않고 LLM 의 판단을 남깁니다. 억지로 매핑하면 틀린 유형을 확신을 갖고 덮어씁니다.

## 결과

로컬 7B 실측입니다.

| 화면 | good | bad |
|---|---|---|
| 로그인 | 7/7 | 3 PASS / 4 FAIL |
| 회원가입 | 14/14 | 11 PASS / 3 FAIL |
| 검색 | **8/8** | **4 PASS / 4 FAIL** |

검색이 6건에서 8건으로 늘었습니다 — 예시 2건이 각각 문구 케이스와 건수 케이스로
나뉘었습니다. `bad` 의 FAIL 이 3 에서 4 로 늘어난 이유가 중요합니다.

```
FAIL search-scenario-005  문구 '검색 결과 3건' 미노출
FAIL search-count-005     3건이 나와야 하는데 목록을 찾지 못했습니다
FAIL search-scenario-006  문구 '검색 결과가 없습니다.' 미노출
PASS search-count-006     '검색 결과 목록' 이 렌더되지 않음 — 0건으로 확인
```

같은 결함(대소문자 구분)이 두 경로에서 잡혔습니다. 중복 보고처럼 보이지만 두 경로는
서로를 대신하지 못합니다 — 구현이 문구는 올바르게 찍고 목록만 빠뜨리면 문구 경로는
통과하고 건수 경로만 잡습니다. **같은 결함이 두 곳에서 보이는 것과, 한 곳에서만 보일 수
있는 결함을 놓치는 것 중에서는 앞쪽이 낫습니다.**

그리고 `search-count-006` 이 PASS 인 것이 이 작업의 품질입니다. D2(0건 안내 누락)는
문구 결함이지 목록 결함이 아닙니다. 건수 경로가 그것까지 잡겠다고 나서면 오탐이 됩니다.

S1 추출은 세 화면 **45/45** 통과했고, 7B 가 `유형: 목록` 을 `type: "list"` 로 옮기는
것과 건수 열을 `expect_count` 로 담는 것을 프롬프트만으로 맞혔습니다 — 결정적 보정
계층이 한 번도 개입하지 않았습니다(개입하면 경고가 남습니다). 예방이 먼저 듣고 탐지는
조용한 상태가 원하는 모습입니다. 전체 테스트는 246개입니다.

## 이 노트에서 남길 것

1. **초록불이 '확인했다' 를 뜻하지 않을 수 있다.** 문구 비교는 화면이 그 문구를 찍는다는
   가정 위에 있었고, 가정이 깨지면 조용히 아무것도 확인하지 않는다.
2. **필드의 의미를 넓히지 말고 필드를 추가한다.** 이름이 할 수 있는 일을 말해야 판정
   함수가 값을 유형에 따라 다르게 해석하지 않는다.
3. **신뢰하는 계약은 고치지 말고 옆에 경로를 둔다.** 한 겹 내려가 보면 계약을 깨지 않고
   요구를 담을 수 있는 경우가 많다.
4. **관측과 판단을 나눈다.** S3 는 무엇을 봤는지만 보고하고, 같은 관측이 기대값에 따라
   PASS 와 FAIL 로 갈리는 것은 S5 가 정한다.
5. **구분할 근거가 없으면 원인을 단정하지 않는다.** 지목이 틀린 FAIL 은 오탐보다 나쁘다.
