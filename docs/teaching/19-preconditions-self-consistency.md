# 19 · 전제가 있는 화면 — 그리고 화면이 스스로 모순인지 보는 판정

이전: [18-natural-language-request.md](18-natural-language-request.md) — 자연어로 요청받기

---

## 무엇이 새로운가

지금까지의 네 화면(로그인·회원가입·검색·비밀번호 찾기)에는 공통 가정이 하나
숨어 있었습니다 — **전부 빈 상태에서 열 수 있는 화면**이었다는 것입니다.
브라우저를 띄우고 URL 로 가면 화면이 있고, 값을 넣으면 반응이 옵니다.

2차 범위의 두 화면은 그 가정을 깹니다.

| 화면 | 처음 생기는 것 |
|---|---|
| 상품등록 | **상태 전제** — 로그인한 판매자여야 열린다 |
| 주문조회 | **데이터 전제** — 이미 있는 주문이 보여야 하고, 정렬·합계가 맞아야 한다 |

데이터 계약(`models.py`)에는 전제를 표현할 자리가 없었고, 판정에는 순서·계산을
확인할 유형이 없었습니다. 이 노트는 그 둘을 더한 이야기입니다 — 그리고 언제나처럼,
**더하면서 무엇이 깨질 뻔했고 어떻게 막았는가**가 본론입니다.

---

## 전제는 기획서에 적는다

로그인이 필요하다는 사실을 도구가 아는 방법은 두 가지가 있습니다. 화면에 가 보고
리다이렉트되면 로그인이 필요하다고 **추측**하거나, 기획서가 **말해 주거나**.

추측은 이 도구의 방향이 아닙니다 — Prova 의 판정은 항상 '기획서 대비' 입니다.
리다이렉트를 보고 로그인을 추측하면, **가드가 빠진 구현(결함)을 "로그인이 필요
없는 화면"으로 읽게 됩니다.** 결함이 기준선이 되어 버립니다.

그래서 기획서에 절 하나를 더했습니다.

```markdown
## N. 전제

이 화면은 판매자 계정으로 로그인한 상태에서 동작한다.
비로그인 상태로 접근하면 로그인 화면으로 이동시킨다.

| 이메일 | 비밀번호 |
|---|---|
| seller@test.com | Seller1! |
```

계정 표는 "테스트 계정" 절과 같은 형식입니다 — **표는 코드가 읽는다**는 원칙
그대로(노트 02). 그리고 두 번째 문장("비로그인이면 이동시킨다")은 안내문이
아니라 **그 자체가 검증 대상**입니다. 뒤에서 다시 나옵니다.

---

## 로그인 스텝은 누가 만드는가

S1(7B 모델)의 몫은 "전제 절이 있다, 계정은 이것이다"를 **옮겨 적는 것뿐**입니다.
로그인 스텝을 만드는 판단은 모델에 주지 않았습니다 — 7B 에 선택지를 늘리면
추출이 흔들린다는 것을 Scenario 표 때 배웠습니다(노트 09).

스텝은 S2 의 순수 함수가 만듭니다(`s2_case_generator/precondition.py`).

```
expand_precondition(pre, doc):
  1. navigate  로그인 화면의 url_path
  2. fill      로그인 화면의 '이메일' 라벨      <- 계정 이메일
  3. fill      로그인 화면의 '비밀번호' 라벨    <- 계정 비밀번호
  4. click     로그인 화면의 제출 버튼
```

라벨을 **로그인 화면의 ScreenSpec 에서** 가져온다는 점이 중요합니다. 흐름이 값을
라벨로 이었던 것(노트 11)과 같은 원리입니다 — 탐지는 라벨로 한다는 규칙을 전제
스텝도 지킵니다. 로그인 화면이 문서에 없으면? 스텝을 지어내지 않고 경고를
남깁니다. 기획서의 문제는 기획서의 문제라고 말해야 합니다.

이 스텝들은 전제가 있는 화면의 **모든 케이스** 앞에 붙습니다(`setup_steps`).
각 스텝 결과에는 `phase: "setup" | "test"` 가 남아 리포트가 "준비"와 "실행"을
구분해 보여줍니다.

---

## '버튼을 눌렀다' 와 '로그인됐다' 는 다르다

위의 네 스텝만으로 배포했다면 조용한 오분류가 하나 숨었을 겁니다.

**비밀번호가 틀려도 제출 버튼은 눌립니다.** Playwright 관점에서 그 클릭은
실패가 아닙니다. 그러면 틀린 계정으로도 setup 네 스텝이 전부 '성공' 으로
기록되고, 본 스텝이 **아직 로그인 화면에 남아 있는 채로** 실행됩니다. 상품명
입력란을 찾다가 실패하고, 분류는 `element_not_found` 가 됩니다.

"전제가 깨졌다"는 진짜 원인이 리포트에서 사라지는 것입니다.

그래서 다섯 번째 스텝이 있습니다 — 로그인 화면이 성공 시 이동한다고 **기획서에
적은 경로**에 실제로 도착했는지를 확인하는 assert 입니다.

```python
steps.append(TestStep(
    seq=5, action="assert", target="로그인 성공",
    expected=Expectation(type="redirect", url_contains=success_path),
))
```

여기 실패하면 `phase="setup"` 인 채로 남고, 판정은 아래의 `precondition_failed`
로 갑니다. **"있는 것과 동작하는 것은 다르다"**(노트 04)의 전제판입니다 —
버튼이 눌린 것과 로그인이 된 것은 다릅니다.

---

## 전제가 깨지면 누구 잘못인가

전제(로그인)를 세우지 못한 케이스를 어떻게 판정할까요. 선택지가 셋 있었습니다.

| 선택지 | 문제 |
|---|---|
| PASS | 아무것도 확인 못 했는데 초록불 — 논외 |
| SKIPPED (제3의 판정값) | summarize·리포트·UI·통과율 정의 전부에 파급된다 |
| FAIL + 새 분류 | 이진 판정 유지, 분류로 사연을 남긴다 |

세 번째를 골랐습니다. `failure_category` 에 `precondition_failed` 를 추가하고,
리포트가 이렇게 말합니다.

```
전제 미충족 — 전제(로그인)를 세우지 못했습니다. 이 화면의 결함이 아닙니다.
로그인 화면의 결과를 먼저 확인하세요.
```

그리고 **화면별 결함 집계에서 따로 셉니다.** 로그인이 깨지면 로그인 화면
케이스가 이미 자신의 FAIL 을 냅니다. 상품등록 케이스들의 전제 실패까지 상품등록
결함으로 합치면 **같은 결함 하나가 여러 화면의 결함처럼 불어납니다.** 흐름을
화면 칸에 섞지 않은 것(노트 11)과 같은 이유입니다.

이 경로는 테스트 전용 기획서로 검증했습니다 — 전제 절에 **일부러 틀린
비밀번호**(`Wrong1!`)를 적은 `product_badlogin_spec` 으로 good SUT 를 돌리면,
SUT 에 아무 결함이 없는데도 상품등록 케이스들이 `precondition_failed` 로
분류됩니다. 결함을 심은 변형이 아니라 **기획서 쪽을 틀리게** 만들어 잰 것입니다.

한 겹 더: 로그인 화면이 문서에 없어 **스텝을 만들 수조차 없던** 케이스는
아예 실행하지 않고 곧바로 같은 분류로 판정합니다(`precondition_unmet`).
로그인 없이 본 스텝을 돌리면 그 실패가 구현 결함인지 전제 부재인지 구분할 수
없는 잡음이 되기 때문입니다.

## 전제 문장 자체도 검증 대상이다 — 가드 케이스

기획서의 "비로그인 상태로 접근하면 로그인 화면으로 이동시킨다"에서 케이스가
하나 나옵니다. setup **없이** 대상 화면으로 직접 가서, 로그인 화면으로
리다이렉트되는지 봅니다.

```
product-precondition-guard-011
  navigate /product  →  기대: redirect, url_contains="/login"
```

bad 상품등록에 심은 결함 P2(가드 누락 — 비로그인도 열림)를 이 케이스가
잡습니다. 다른 모든 케이스는 로그인**하고** 들어가는데, 이 케이스만 로그인
**안 하는 것이 조건**입니다.

그리고 바로 그 성질이 사고를 하나 만들었습니다.

---

## 오탐이 될 뻔했다 — 케이스 격리

E2E 를 돌리자 가드 케이스가 **good 에서 FAIL** 이 났습니다. 기획서를 지킨
구현을 결함이라고 말한 것입니다 — 이 프로젝트가 가장 금지하는 결과, 오탐입니다.

원인은 실행 순서였습니다. 앞 케이스들이 setup 으로 로그인하면서 세션 쿠키가
남고, 가드 케이스가 도착했을 때 브라우저는 **이미 로그인 상태**입니다. 그러니
리다이렉트가 안 되고, "가드가 없다"로 읽힙니다.

처음 나온 수정안은 "가드 케이스를 목록 맨 앞으로 옮기자"였습니다. 리뷰에서
막았습니다 — **증상 패치**입니다. 순서에 기대는 순간, 자연어 요청으로 케이스를
골라 돌리거나(노트 18) 사람이 계획 화면에서 일부만 켜면 다시 깨집니다. 케이스의
판정이 **실행 순서라는 보이지 않는 변수**에 묶이는 것이 진짜 문제입니다.

근본 수정은 케이스 격리입니다 — 모든 케이스 실행 전에 쿠키를 지웁니다.

```python
# 케이스 격리 — 앞 케이스가 남긴 세션이 다음 판정을 오염시키지 않게 한다.
state.page.context.clear_cookies()
```

전제가 있는 케이스는 어차피 setup 으로 매번 로그인하므로 잃는 것이 없고,
가드 케이스는 순서와 무관하게 정직해집니다. 필터 없이 문서 전체를 돌려도
성립한다는 것을 테스트로 못 박았습니다(`TestFullDocumentNoFilter`).

> 세션이라는 것이 SUT 에 처음 생기자마자 나온 사고입니다. **상태가 생기면
> 격리가 따라와야 합니다** — 상태는 케이스 사이로 샙니다.

## 주문조회 — 화면이 스스로 모순인지 본다

주문조회 기획서에는 데이터 표가 있습니다.

```markdown
## M. 테스트 주문 데이터

주문조회 화면은 아래 주문이 등록된 상태를 전제한다. 주문일 내림차순(최신순)으로
표시하며, 합계는 표시된 주문 금액의 합이다.

| 주문번호 | 주문일 | 상품명 | 금액 | 상태 |
| ORD-005 | 2026-08-15 | 노트북 | 1,290,000 | 배송중 |
| ...     |            |        |           |        |
```

SUT 는 이 표를 그대로 시드합니다. 여기서 판정 유형 두 개가 새로 나옵니다 —
`sorted_desc`(주문일이 내림차순인가)와 `sum_matches`(합계가 행 합과 같은가).

설계에서 가장 중요한 결정은 **씨앗 표와 대조하지 않는다**는 것입니다. 판정은
화면에 찍힌 날짜들을 그 화면 안에서 비교하고, 화면에 찍힌 금액들의 합을 화면에
찍힌 합계와 비교합니다. 화면이 **스스로 모순인지**만 봅니다.

씨앗과 대조하면 어떻게 될까요. 판정이 "화면이 옳은가"가 아니라 "씨딩과 화면이
같은가"를 묻게 됩니다. 그러면 씨드 데이터가 바뀔 때마다 판정이 같이 흔들리고,
화면 자체의 정렬 로직 결함(문자열 정렬로 날짜를 섞는 종류)을 놓칠 수 있습니다.
자기일관 판정은 LLM 없이 결정적이고, 시드가 바뀌어도 성립합니다.

반복 요소를 라벨로 찾는 경로는 건수 세기(노트 10)가 이미 뚫어 놓았습니다.
그 경로를 재사용하고 '값 파싱 + 비교'만 얹었습니다 — 날짜는 `YYYY-MM-DD`,
금액은 쉼표·'원' 을 벗긴 정수로 기획서에 형식을 고정하고, 파서는 순수 함수 +
단위 테스트입니다.

## 판정 불능은 FAIL 이다 — 세 군데

이 도구의 오래된 원칙(판정 불능 = FAIL, 노트 05)이 새 판정에서 세 번 다시
나옵니다.

**항목이 0개면 FAIL.** 빈 목록은 '정렬 규칙을 어기지 않았다'가 아니라
'아무것도 확인하지 못했다'입니다. 통과시키면 목록이 렌더되지 않는 결함이
있어도 초록불이 납니다 — 아무것도 확인하지 않은 초록불은 오탐보다 나쁩니다.

**파싱에 실패하면 FAIL.** 날짜가 `YYYY-MM-DD` 가 아니거나 금액을 정수로 읽지
못하면, 대충 건너뛰지 않고 어떤 값이 왜 안 읽혔는지와 함께 실패합니다.

**합계 요소가 여럿 찾히면 FAIL.** 금액 열은 반복이 정당하지만 합계는 하나여야
합니다. 여럿을 조용히 첫 값으로 접으면 근거가 거짓이 됩니다.

```
합계('합계') 요소가 2개 찾혔습니다 — 어느 것이 합계인지 판정할 수 없습니다
```

그라운딩의 '정확히 1개' 원칙(노트 04)이 판정 층에서 반복된 것입니다.

## 심은 결함이 서로 맞물렸다

bad 주문조회에 심은 결함은 둘입니다.

```
O1  주문일 오름차순으로 정렬한다 (기획서는 내림차순)
O2  합계에서 화면에 마지막으로 '표시된' 행의 금액을 뺀다
```

O1 은 검색 화면의 대소문자 결함(노트 09)과 같은 부류입니다 — 값에 흠이 없는데
**순서가** 틀립니다. 위반값 생성으로는 절대 못 잡고, 정상 데이터로만 잡힙니다.

그리고 둘은 맞물립니다. O1 때문에 bad 는 오름차순으로 표시하므로 마지막 표시
행이 가장 최근 주문 ORD-005(1,290,000)가 되고, 합계는 1,859,000 이 아니라
**569,000** 으로 뜹니다. SUT 는 이 값을 하드코딩하지 않고 계산합니다.

```python
total = sum(o["금액"] for o in rows) - rows[-1]["금액"]
```

"569,000 이어야 한다"고 박아 두면 시드 표를 고치는 순간 결함이 결함이 아니게
됩니다. **결함도 데이터가 바뀌어도 정직하게 유지되도록 심어야 합니다.**
(구현 계획서에는 이 값이 1,847,000 으로 잘못 적혀 있었고, 실행 중 리뷰가
잡아냈습니다 — 문서의 산수도 틀립니다. 그래서 계산으로 심는 것입니다.)

| 주문조회 | `good` | **5/5 PASS** |
| 주문조회 | `bad` | **3 PASS / 2 FAIL** — O1(정렬)·O2(합계) 정확히 지목 |

오탐 0건. 그리고 `bad` 에서도 PASS 가 함께 나옵니다 — 심은 결함:잡는 케이스가
1:1 이고 나머지는 동일하다는, 노트 00 부터의 실험 설계 그대로입니다.

자연어 요청 층과 웹 UI 는 **코드를 바꾸지 않고** 새 화면을 얻었습니다. 화면
이름과 라벨이 어휘에 자동으로 들어가고, 계획 화면의 화면별 그룹·확인 범위에
자동으로 나타납니다. 층이 제대로 나뉘었다는 가장 값싼 증거입니다.

## 실모델로 관통했다 (2026-08-20 후기)

위 표는 mock 백엔드 결과였습니다. 같은 날 CHEETAH 7B 로 다시 쟀고, 상품등록은
한 번에 통과했습니다 — good 20/20, bad 12P/8F(로그인 결함 6 + P1 + P2), 오탐 0.
전제 스텝(로그인 setup)을 실모델 추출로 만든 케이스가 전 구간을 돌았습니다.

주문조회는 **S1 에서 막혔습니다.** 7B 가 '주문 조회' 화면의 요소 4개를 두 번 다
**0개** 추출했습니다. 로그인 3개·상품등록 4개는 성공했으니 패턴이 분명합니다 —
**입력·버튼 요소는 옮기는데 표시 전용 요소(목록·텍스트)는 통째로 빠뜨립니다.**
요소가 없으니 정렬·합계 케이스가 생성되지 않았고, O1·O2 는 실행조차 안 됐습니다.

도구는 조용히 죽지 않았습니다. 경고가 정확히 말했습니다 —
"기획서 UI 요소 표에는 4개 요소가 있는데 추출된 것은 0개입니다."

그리고 그 문장이 답을 반쯤 말하고 있었습니다. **경고가 "표에는 4개" 라고 아는
것은 파서가 표를 이미 읽고 있다는 뜻입니다.** 대조까지만 하던 것을 백필로
올렸습니다 — 모델이 빠뜨린 요소를 표에서 직접 채우고, 채운 사실을 경고로
남깁니다. "표에 그대로 적힌 사실은 LLM 에 맡기지 않는다"(노트 14)의 연장이고,
전제 계정·시드 표와 같은 원리입니다.

채우지 않는 것도 정했습니다. 검증 규칙 셀("8자 이상, 대문자 1자 이상")은 자유
서술이라 결정적으로 옮길 수 없습니다 — 규칙이 적힌 요소를 백필하면 "위반
케이스가 생성되지 않는다" 를 따로 경고합니다. 미탐은 보이게 만듭니다. 같은
라벨의 요소가 이미 있으면(모델이 ID 를 지어낸 경우) 채우지 않습니다 — 쌍둥이
요소는 그라운딩의 '정확히 1개' 원칙과 충돌합니다.

재관통 결과, 주문조회 good 15/15 · bad 7P/8F — O1 은 "'2026-07-28' 다음에 더
최근인 '2026-08-03' 이 옴", O2 는 "행 5개의 합은 1859000 인데 화면의 '합계' 는
569000" 으로 정확히 지목됐습니다. 오탐 0. **2차 범위의 수용 기준 1·2 가
실모델로 충족됐습니다.**

### 성공 리포트가 가르쳐 준 것 — 틀린 경고 두 줄

15/15 통과한 화면에 이 경고가 떠 있었습니다.

```
버튼 요소를 하나도 추출하지 못했습니다. … 모든 케이스가 실패로 나옵니다.
입력 검증 규칙이 하나도 추출되지 않았습니다. … S1 추출 실패를 의심하세요.
```

주문조회에는 폼이 없고, 표의 규칙 열은 전부 `-` 입니다. 둘 다 사실과 다른
경고입니다 — 늑대 소리는 진짜 경고를 묻습니다(노트 18에서 세운 원칙).
버튼 경고는 채울 수 있는 요소(입력·선택·체크박스)가 있을 때만, constraints
경고는 표가 '규칙 없음' 을 말해 주지 않을 때만 내도록 좁혔습니다.

### 요청 해석 홀드아웃은 6/9

주문조회 항목을 더해 다시 쟀습니다. "주문 내역이 최신순으로 나오는지 확인해줘"
에 7B 가 12건 중 2건을 골랐는데 정작 `orders-sorted` 를 빠뜨렸습니다 — 설계의
수용 기준 5 는 실모델에서 **미달**입니다. 홀드아웃을 보고 프롬프트를 고치면
튜닝 세트가 되므로 고치지 않았고, 미달 사실을 설계 문서(v1.2)에 기록했습니다.
방어선은 노트 18의 화면별 확인 범위 경고입니다 — 계획 화면이 "이 화면을
지목했는데 일부만 골랐다" 를 짚습니다.
