Prova는 기획서를 읽고 스스로 테스트한다

기획서에 적힌 검증 규칙이 실제 구현에 빠져 있는지 사람 대신 확인하는 웹 GUI QA 에이전트. PDF 화면기획서를 읽어 테스트 케이스를 만들고, 진짜 브라우저를 열어 실행하고, 어느 규칙이 구현되지 않았는지 짚어낸다.

기획서 한 줄이 테스트 세 개가 된다

S1 → S2 단계에서 실제로 일어나는 일

기획서에 이렇게 적혀 있다고 하자.

기획서 · 비밀번호

최소 길이는 8자다. 영문 대문자를 1자 이상 포함해야 한다. 특수문자를 1자 이상 포함해야 한다. 위 규칙 중 하나라도 위반하면 "비밀번호는 8자 이상이며 대문자·특수문자를 각 1자 이상 포함해야 합니다."를 노출한다.

Prova는 이 문장에서 규칙 세 개를 뽑아내고, 각 규칙만 어기는 입력값을 만든다. 규칙 하나당 케이스 하나다.

검사할 규칙 constraints 키 그 규칙만 어기는 값 왜 이 값인가
8자 이상 min_length: 8 Aa1!aaa 7자로 짧지만 대문자·숫자·특수문자는 충족
대문자 1자 이상 require_uppercase: 1 a1!aaaaa 대문자만 없음. 길이·숫자·특수문자는 충족
특수문자 1자 이상 require_special: 1 Aa1aaaaa 특수문자만 없음. 나머지는 충족
왜 한 번에 하나만 어기나

서비스명세서의 예시 케이스는 abcd1234를 쓴다 — 대문자도 없고 특수문자도 없다. 이 케이스가 FAIL이면 개발자는 "대문자 검증이 없나, 특수문자 검증이 없나, 둘 다인가"를 알 수 없다.

규칙 하나당 케이스 하나여야 리포트에서 규칙과 실패가 1:1로 연결되고, 개발자가 어느 검증 코드를 추가해야 하는지 바로 안다.

여섯 단계, 그리고 AI를 쓰는 곳

각 단계는 앞 단계의 결과 타입을 그대로 받는다

S1

기획서 읽기

pdfplumber로 표와 글자를 뽑고(코드), 그 텍스트를 로컬 7B가 JSON으로 구조화한다. 표를 마크다운 표로 다시 조립해서 넘기는 것이 핵심 — 그냥 글자로 뽑으면 어느 값이 "검증 규칙" 열인지 알 수 없다.

S2

테스트 케이스 만들기

규칙에서 위반값을 만드는 일은 AI가 아니라 순수 함수가 한다. 결정적이고, 공짜이고, 생성값이 정말 그 규칙만 어기는지 단위 테스트로 보증할 수 있다.

S3

화면에서 요소 찾기

기획서에는 "이메일"이라고만 적혀 있다. 그것이 #email인지 input[name=userEmail]인지는 구현을 봐야 안다. 접근성 라벨 → placeholder → role → 텍스트 순으로 찾고, 정확히 1개이고 화면에 보일 때만 확정한다.

S4

실제로 조작하기

Playwright로 진짜 크롬을 열어 입력하고 클릭한다. 매 단계 스크린샷과 HTML을 남긴다 — 개발자가 "정말 그래?"라고 물을 때 보여줄 증거다.

S5

판정하기

위반 케이스는 판정이 뒤집혀 있다. 에러가 떠야 PASS다. 규칙을 어긴 값을 넣었으니 기획서대로면 에러가 나와야 한다.

S6

리포트 만들기

외부 의존이 없는 단일 HTML. 실패를 위에 모으고 각 실패에 위반 규칙·기대·실제· 스크린샷을 붙인다. 폐쇄망에서도 열려야 하므로 CDN을 쓰지 않는다.

같은 기획서, 다른 구현, 다른 결과

이 대조가 1차 목표의 완료 조건이었다

테스트 대상 웹앱을 두 버전 만들었다. HTML 마크업은 완전히 동일하고 검증 로직만 다르다. 마크업까지 다르면 FAIL이 났을 때 "검증을 빼먹어서인가, 요소를 못 찾아서인가"를 구분할 수 없다 — 변수를 하나만 두는 것이 실험의 기본이다.

/good/login 전부 통과

7 / 7

기획서를 그대로 구현한 버전. 통과율 100%.

/bad/login 4건 실패

3 / 7

일부러 검증을 빼먹은 버전. 빼먹은 것을 정확히 4건 지목했고 오탐은 0건이었다.

  • FAIL 이메일 형식 검증 없음
  • FAIL 비밀번호 길이·대문자·특수문자 검증 없음
  • PASS 필수 입력 검증은 있음 (2건)
왜 bad에서도 3건이 통과해야 하나

bad 버전에도 "필수 입력" 검증은 구현돼 있다. 그래서 그 케이스는 PASS로 나온다. 한 리포트 안에 구현된 규칙은 PASS, 빠진 규칙은 FAIL이 함께 나오는 것이 이 판정을 신뢰할 근거다.

전부 FAIL이 나오면 도구가 고장난 것인지 구현이 잘못된 것인지 구분할 수 없다.

실제 출력은 이렇다.

FAIL [require_uppercase] 비밀번호 대문자 검증
     기획서의 'require_uppercase' 검증 규칙이 구현에서 확인되지 않았습니다.
     기대: '비밀번호는 8자 이상이며 대문자·특수문자를 각 1자 이상 포함해야 합니다.'
     실제: '로그인 정보를 확인해주세요.'

개발자는 이 한 줄로 어느 검증 코드를 추가해야 하는지 바로 안다. 이것이 ㈜WITCHES가 의뢰한 것 — QA 담당자가 기획서를 읽고 손으로 값을 만들어 하나씩 눌러보던 일이다.

판단 명세서 우리 구현과 이유
위반 케이스의 범위 대문자와 특수문자를 동시에 빠뜨린 abcd1234 규칙 하나당 케이스 하나. FAIL이 떴을 때 어느 규칙이 미구현인지 분리돼야 개발자가 고칠 코드를 안다.
위반값 생성 주체 LLM이 케이스를 생성 (§10-2는 "로컬 유력"으로 판단) LLM을 아예 쓰지 않는 순수 함수. 결정적이고 공짜이고, 생성값이 정말 그 규칙만 어기는지 테스트로 보증된다.
PDF 추출 🔴 API 후보 — 강한 멀티모달 추론 필요 pdfplumber(결정적) + LLM(구조화) 2단계. 텍스트 레이어가 있는 PDF는 로컬 7B로 충분했다 — 골든 비교 10/10 통과.

구현하지 않고는 알 수 없었던 것

문제 대응
PDF는 원문 공백을 복원하지 못한다 대문자·\n특수문자의 개행은 지워야 맞고 8자\n이상은 공백으로 바꿔야 맞은데, 한글은 글자 단위로도 줄바꿈되어 판별할 수 없다. → 복원을 포기하고 비교를 정규형에서 한다(공백만 무시).
필수 입력 문구는 요소별이 아니다 기획서 §2 표의 에러 메시지는 형식 검증용이고, "필수 입력 항목입니다."는 §4에 화면 공통으로 따로 있었다. → ScreenSpec.required_message 추가. 문구를 모르면 억측하지 않고 "에러가 떴는지"만 확인한다.
규칙을 만족하는 값 ≠ 로그인되는 값 코드가 만든 Aa1!aaaa는 규칙을 다 지키지만 등록된 계정이 아니라 정상 케이스가 구현 결함 없이 실패했다(오탐). → UIElement.sample_value에 기획서 테스트 계정을 담는다.
guided_json이 조용히 무시된다 vLLM 0.24에서 제거됐는데 에러가 나지 않는다. 요청한 screen_name 대신 screenName이 코드펜스에 감싸여 온다. 스키마가 안 걸리면 검증이 조용히 무력해진다. → OpenAI 표준 response_format으로 교체하고, prova check가 필드명까지 대조한다.
오탐이 미탐보다 위험하다

버그를 놓치면(미탐) 아쉽지만 사람이 나중에 발견한다. 없는 버그를 보고하면(오탐) 개발자가 확인해보고 "아니네"를 반복하다가 도구를 신뢰하지 않게 된다. 그러면 진짜 버그 보고도 무시당한다.

그래서 확신이 없으면 약하게 판정한다. 기대 문구를 모를 때 그럴듯한 문구를 지어 넣지 않고 "에러가 떴는지"만 확인하는 것이 그 원칙의 적용이다.

다음에 할 일

화면 확장을 VLM보다 먼저 하는 이유

지금은 로그인 화면 하나만 검증한다. 다음은 회원가입과 검색으로 넓힌다. VLM(프로젝트의 핵심 차별점)을 먼저 붙일 수도 있지만, 코드를 익혀야 하는 시점에 새 기술을 얹기보다 기존 구조를 확장하며 이해하는 편이 낫다. 그리고 확장하면 약한 부분이 드러난다.

실제로 회원가입 화면을 검토하니 결함 네 개가 나왔다.

결함 어디서 터지나 / 무엇이 필요한가
체크박스에 fill()을 호출한다 회원가입의 "약관 동의"에서 즉시. check/uncheck 액션을 추가해야 한다.
select의 선택지를 담을 곳이 없다 드롭다운이 있는 화면. UIElement.options 추가.
교차 필드 제약을 표현할 수 없다 가장 어려움 "비밀번호 확인"은 다른 필드와 같아야 한다는 제약인데 현재 constraints는 단일 필드 규칙만 표현한다. same_as 키를 추가하고 값 생성 순서를 정렬해야 한다.
ScreenSpec이 1화면만 담는다 한 기획서에 두 화면이 있으면 하나만 추출한다. 이번엔 화면별 PDF로 분리하고, 다중 화면 추출은 실물 기획서가 올 때 다룬다.
확장의 완료 조건

회원가입이 통과하는 것만으로는 부족하다. 로그인 결과가 그대로 유지돼야 한다. 회원가입을 지원하려고 위반값 생성 로직의 계약을 건드리는데, 그 변경이 로그인 검증을 조용히 망가뜨리면 확장이 아니라 후퇴다. 회귀 테스트가 그 안전망이다.
