# 15 · 검증 대상 웹앱도 우리가 만들었다

이전: [14-real-spec-robustness.md](14-real-spec-robustness.md) — 우리가 만든 문서에서만 동작하고 있었다

---

## 같은 질문을 반대편에 던졌다

14번 노트에서 얻은 것이 하나 있었습니다.

> 모든 성공 문장에는 조건이 숨어 있다. '오탐 0건' 은 **우리가 만든 기획서에서는** 이었다.

그런데 조건이 하나 더 있었습니다. **검증 대상 웹앱도 우리가 만들었습니다.**

`sut/app.py` 는 우리가 쓴 FastAPI 앱입니다. 폼을 제출하면 서버가 검증하고 결과가 들어 있는
HTML 을 돌려줍니다. 동기식입니다. **실물 웹앱은 대개 그렇지 않습니다.**

```
우리 SUT     제출 → 서버가 검증 → 결과가 담긴 HTML 응답 → 화면에 이미 있다
실물 웹앱     제출 → fetch → (그 사이 화면에 아무것도 없다) → 응답 → 화면을 갈아 끼움
```

S3·S4 가 전제하는 것이 뭔지 코드로 확인했습니다.

```python
locator.click(timeout=ctx.step_timeout_ms)
...
page_state = capture_page_state(state.page, ...)   # 곧바로 DOM 을 읽는다
```

**클릭 직후 DOM 을 읽습니다.** 기다리지 않습니다. 지금 통하는 이유는 SUT 가 동기식이라
응답 HTML 에 결과가 이미 있기 때문입니다.

---

## 변수 하나만 다른 변형을 만들었다

`nolabel` 을 만들 때 지킨 원칙을 그대로 썼습니다 — **검증 로직은 `good` 과 완전히 같고,
바꾸는 변수는 하나.**

`slow` 변형은 서버가 보낸 에러 문구와 검색 결과를 브라우저가 **400ms 뒤에** DOM 에 넣습니다.
문구도, 마크업도(`aria-label` 포함), 서버 코드도 `good` 과 같습니다.

```javascript
setTimeout(function () {
  var box = document.createElement("div");
  box.className = "error";
  box.setAttribute("role", "alert");
  box.textContent = {{ error | tojson }};
  document.getElementById("late-slot").appendChild(box);
}, 400);
```

400ms 로 잡은 근거: 사람은 거의 눈치채지 못하고, 도구는 기다리지 않으면 확실히 놓치는
구간입니다. 너무 길게 잡으면 '도구가 기다리는가' 가 아니라 '얼마나 오래 기다리나' 를 재는
시험이 됩니다.

먼저 변형 자체가 의도대로 동작하는지 실측했습니다.

```
       안내문구                 클릭직후   700ms후
 good  '이메일을 입력하세요'      True      True
 slow  '이메일을 입력하세요'      False     True     <- 시점만 다르다

       목록 항목 즉시   700ms후   aria-label
 good        3            3      '검색 결과 목록'
 slow        0            3      '검색 결과 목록'
```

## 결과 — 오탐 7건, 그리고 틀린 단정

```
good  10 PASS / 0 FAIL
slow   3 PASS / 7 FAIL     검증 로직은 한 줄도 다르지 않다
```

실패 사유가 이랬습니다.

```
FAIL 비밀번호 대문자 포함 규칙 위반 (입력값 'a1!aaaaa') — 규칙 강제 여부 확인
     기획서에 적힌 'password' 의 'require_uppercase' 검증 규칙이 구현에서
     확인되지 않았습니다. (에러가 전혀 노출되지 않음 — 구현이 이 규칙을
     강제하지 않는다)
```

**구현은 그 규칙을 강제합니다.** 도구가 못 기다린 것을 구현 결함으로 **단정했습니다.**

이 프로젝트에서 세 번째로 만난 같은 종류의 사고입니다.

| 언제 | 원인 | 결과 |
|---|---|---|
| 2차 경로 | 좌표가 버튼을 비켜 갔다 | 없는 결함 7건 |
| 기획서 훼손 | 모델이 요구사항을 발명했다 | 없는 결함 1건 |
| 비동기 렌더 | 도구가 기다리지 않았다 | 없는 결함 7건 |

원인은 매번 다른데 **모양이 같습니다** — 도구가 확인하지 못한 것을 구현 결함으로 보고합니다.
그리고 매번 사유 문구가 자신 있습니다.

---

## 시도했다가 버린 설계 — 'DOM 이 안정될 때까지'

처음 떠오른 것은 이것이었습니다.

> DOM 변화가 250ms 동안 없으면 화면이 안정된 것으로 보고 그때 읽는다.

판정과 독립적이라 깔끔해 보였습니다. S4 가 S5 의 기대를 알 필요가 없습니다.

**그런데 성립하지 않습니다.** 400ms 뒤에 렌더하는 화면은 그 전 250ms 동안 아무 변화가
없습니다. MutationObserver 는 그 정적을 '안정됐다' 로 읽고 렌더 전에 멈춥니다.

> **아직 시작하지 않은 것과 끝난 것을 구분할 수 없다.**

`networkidle` 도 안 됩니다 — 이 변형은 `setTimeout` 이라 네트워크가 없습니다. 실물 앱은
대개 fetch 를 쓰니 도움이 되겠지만, 폴링이나 웹소켓이 있는 앱에서는 영원히 idle 이 오지
않습니다.

**일반적으로 '앱이 렌더를 끝냈는지' 는 알 수 없습니다.** 그래서 기대를 알고 기다립니다 —
Playwright 의 assertion 이 재시도하는 것과 같은 이유입니다.

## 고친 방법 — 판정이 통과할 때까지, 상한까지

```python
verdict = judge()
broke = any(r.status != "ok" for r in step_results)
if verdict.verdict == "PASS" or broke or state.settle_timeout_ms <= 0:
    return verdict

waited = 0
while waited < state.settle_timeout_ms:
    state.page.wait_for_timeout(interval_ms)
    waited += interval_ms
    verdict = judge()
    if verdict.verdict == "PASS":
        verdict.evidence["settled_ms"] = waited
        return verdict
return verdict
```

**재시도를 S4 가 아니라 오케스트레이션(`nodes.py`)에 뒀습니다.** S4 는 실행하고, S5 는
순수 함수로 판정합니다. 그 경계를 지키면서 '언제 판정할지' 만 밖에서 정합니다.

### 이 대기가 판정을 무르게 만들지 않는가

**이게 이 변경에서 가장 조심한 부분입니다.** 대기는 FAIL 을 PASS 로 바꿀 수 있고 그 반대는
없습니다. 그 방향성이 결함을 덮는 데 쓰이면 이 도구의 값이 사라집니다.

세 가지를 지켰습니다.

**① 상한이 있습니다.** 넘으면 마지막 판정을 그대로 보고합니다. 통과할 때까지 무한정
기다리면 진짜 결함이 전부 사라집니다.

**② 기다린 시간을 근거에 남깁니다.**

```
결과를 기다린 뒤 통과한 케이스 (7건, 최대 300ms)
제출 직후에는 화면에 결과가 없었고, 기다린 뒤 나타났습니다. 판정은 유효합니다 —
이 화면이 결과를 비동기로 렌더한다는 뜻입니다. 기다리지 않으면 올바른 구현이
FAIL 로 나옵니다.
```

2차 경로의 `healed` 를 남기는 것과 같은 이유입니다. **도구가 편의를 제공했으면 그 사실이
리포트에 있어야 합니다.**

**③ 스텝이 끊긴 케이스는 기다리지 않습니다.** 요소를 못 찾아 실패한 케이스는 기다려도
달라지지 않습니다. 그런데도 기다리면 진짜로 깨진 케이스마다 상한만큼 시간을 버립니다.

## 수용 기준을 세 개 뒀다

가장 중요한 것은 두 번째입니다.

```python
def test_로그인_판정이_good과_같다(self, slow_login):        # 오탐을 안 만든다
def test_bad_로그인_판정이_그대로다(self, sut_base, tmp_path):  # 결함 탐지가 안 무르다
def test_대기를_끄면_오탐이_돌아온다(self, sut_base, tmp_path):  # 대기가 원인임을 증명
```

세 번째가 없으면 `slow` 가 통과하는 이유가 **대기 때문인지 다른 이유인지 알 수 없습니다.**
`settle_timeout_ms=0` 으로 돌려 오탐이 돌아오는 것을 확인합니다 — 없으면 이 변형이 아무것도
시험하지 않는다는 뜻입니다.

그리고 실패한 케이스에 `settled_ms` 가 없어야 합니다. 있으면 '기다려서 통과했다' 는 뜻인데
판정은 FAIL 이라는 모순입니다.

## 측정 결과

```
                오탐 있던 상태      고친 뒤
login  good      10P / 0F          10P / 0F      기다린 케이스 0건
login  slow       3P / 7F          10P / 0F      기다린 케이스 7건, 최대 300ms
login  bad        4P / 6F           4P / 6F      기다린 케이스 0건
search slow           —            10P / 0F      기다린 케이스 1건
search bad         6P / 4F          6P / 4F      기다린 케이스 0건
```

**`bad` 판정이 그대로인 것이 핵심입니다.** 그리고 `good` 은 기다린 케이스가 0건입니다 —
동기식 화면에 대기 비용을 물리지 않습니다.

실물 7B 로 기획서 4종 × 구현 2종을 다시 돌려 판정이 전부 그대로임을 확인했습니다.

### 비용

테스트 전체가 282초 → 445초가 됐습니다. 진짜로 실패하는 케이스마다 상한(2000ms)까지
기다리기 때문입니다. **줄이지 않았습니다** — 기다림이 짧으면 오탐이 나고, 오탐은 이 도구가
낼 수 있는 최악의 결과입니다. 느린 것은 참을 수 있고 틀린 것은 참을 수 없습니다.
설정으로 조절할 수 있게 뒀습니다(`settle_timeout_ms`).

## 이 노트에서 남길 것

1. **자기가 만든 입력으로만 시험하면 도구가 아니라 짝을 만든 것이다.** 기획서에 그랬고
   검증 대상 웹앱에도 그랬습니다. 같은 질문을 양쪽에 던져야 합니다.
2. **같은 사고가 다른 원인으로 반복된다.** 좌표가 어긋나서, 모델이 발명해서, 기다리지
   않아서 — 원인은 매번 다른데 결과는 매번 '없는 결함을 자신 있게 보고' 입니다. 그 모양을
   알아 두면 다음 것을 더 빨리 알아봅니다.
3. **실패 사유에 단정을 쓰지 마라.** "구현이 이 규칙을 강제하지 않는다" 는 관찰이 아니라
   결론입니다. 도구가 확인한 것은 '에러 문구가 안 보였다' 뿐입니다.
4. **'앱이 렌더를 끝냈는지' 는 일반적으로 알 수 없다.** DOM 정적 상태는 '아직 시작하지
   않음' 과 구별되지 않습니다. 그래서 기대를 알고 기다립니다.
5. **한 방향으로만 바꾸는 장치는 상한과 기록이 필요하다.** 대기는 FAIL 을 PASS 로만
   바꿉니다. 상한이 없으면 결함이 사라지고, 기록이 없으면 통과의 성질이 사라집니다.
6. **'그 기능이 원인임' 을 증명하는 테스트를 따로 둔다.** 끄면 오탐이 돌아오는지 확인해야
   통과가 그 기능 덕분이라고 말할 수 있습니다. 그게 없으면 초록불의 이유를 모릅니다.
7. **느린 것과 틀린 것 중에서는 느린 쪽을 고른다.** 대기 상한을 줄이면 테스트가 빨라지지만
   오탐 위험이 돌아옵니다. QA 도구에서 그 교환은 성립하지 않습니다.
8. **변형은 변수를 하나만 바꾼다.** `slow` 는 렌더 시점 하나만 다릅니다. 마크업이나 로직을
   같이 바꿨다면 FAIL 이 났을 때 무엇 때문인지 가릴 수 없었습니다.
