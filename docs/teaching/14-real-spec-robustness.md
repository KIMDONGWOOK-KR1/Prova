# 14 · 우리가 만든 문서에서만 동작하고 있었다

이전: [13-vlm-fallback.md](13-vlm-fallback.md) — 화면 이미지로 요소를 찾는다

---

## 물어야 했던 질문

400개가 넘는 테스트가 통과하고, 세 화면과 화면 사이 흐름을 검증하고, 오탐 0건을
유지하고 있었습니다. 그런데 이 문장에는 조건이 하나 숨어 있습니다.

> **우리가 만든 기획서에서는** 오탐 0건이다.

픽스처 기획서 4개는 전부 제가 마크다운으로 써서 스크립트로 PDF 로 만든 것입니다.

```
| 요소 ID | 유형 | 라벨 | 필수 | 입력 검증 규칙 | 안내 문구 | 에러 메시지 |
| email  | 입력 | 이메일 | 필수 | 이메일 형식(@ 포함) | 이메일을 입력하세요 | ... |
```

7열이 정확히 이 순서로, 정확한 헤더 이름으로, 표 형태로 있습니다. **S1 의 결정적 표
독해 여덟 개가 전부 이 모양을 전제합니다.**

실제 회사의 화면기획서가 이렇게 생길 이유가 없습니다. Figma 캡처와 산문, 표가 이미지,
열 이름이 '항목/설명', 셀 병합 — 실물 문서의 흔한 모양들입니다.

**S1 이 깨지면 그 뒤의 모든 것이 무의미합니다.** 그런데 그게 어떻게 깨지는지 한 번도
재 본 적이 없었습니다.

---

## 재는 것은 '깨지는가' 가 아니라 '어떻게 깨지는가'

이 구분이 이 노트의 핵심입니다.

```
조용한 실패    일부를 놓치고도 경고 없이 정상처럼 보인다     <- 가장 위험
시끄러운 실패  경고를 남기거나 예외로 끊는다                 <- 괜찮다
```

앞쪽이면 사람이 초록불을 믿고 넘어갑니다. 뒤쪽이면 사람이 문서를 고치거나 도구를
고칩니다. **이 도구의 가치는 전부 후자로 만드는 데 있습니다.**

그래서 기획서를 일부러 훼손하는 측정기를 만들었습니다(`scripts/probe_s1_robustness.py`).

| 훼손 | 무엇을 흔드는가 |
|---|---|
| 열 이름 변경 (`요소 ID` → `항목`) | 표 판별 조건 |
| 열 누락 (`안내 문구` 열 제거) | 있는 열만 읽는지 |
| 산문 서술 (표를 문장으로) | 표가 아예 없을 때 |
| 셀 병합 (한 요소가 두 줄) | 행 단위 짝짓기 |
| 표 이미지화 (표를 못 읽음) | pdfplumber 가 무시할 때 |
| 절 번호 없음 (`## 2.` → `##`) | 절 탐색이 번호에 의존하는지 |

훼손은 **하나씩만** 적용합니다. 둘을 겹치면 어느 것이 원인인지 분리되지 않습니다 —
negative 케이스가 규칙을 하나씩만 위반하는 것과 같은 이유입니다.

그리고 **mock LLM 을 쓰지 않습니다.** mock 은 PDF 를 읽지 않고 정답을 돌려주므로,
훼손된 문서에서도 같은 답을 냅니다. 측정이 아예 성립하지 않습니다.

## 1차 측정 — 그리고 제 판정 로직이 틀렸다

```
훼손             표    요소    규칙    안내    경고    판정
원본             O    3     4     2     0     영향 없음
열 이름 변경        X    3     4     2     0     영향 없음
열 누락           O    3     4     2     0     영향 없음
산문 서술          X    3     4     2     0     영향 없음
셀 병합           O    3     4     2     0     영향 없음
표 이미지화         X    2     4     2     1     시끄러운 실패
절 번호 없음        O    3     4     2     0     영향 없음
```

좋아 보였습니다. '조용한 실패 없음' 이 나왔습니다.

**그런데 이 판정이 틀렸습니다.** 옆의 표를 보면 이유가 보입니다.

```
결정적 표 독해가 무엇을 돌려줬나:
  원본              ids=3 types=3 placeholders=2
  열 이름 변경         ids=0 types=0 placeholders=0   <- 전부 빈손
  산문 서술           ids=0 types=0 placeholders=0   <- 전부 빈손
```

`열 이름 변경` 은 결과가 원본과 같습니다. 그런데 그건 **7B 가 우연히 맞혔기 때문**이고,
결정적 검증망은 통째로 사라진 상태입니다.

제가 잰 것은 '데이터를 잃었는가' 였습니다. 재야 했던 것은 **'검증을 잃었는가'** 입니다.

이건 이 프로젝트가 계속 만나는 그 교훈을 제 측정 도구에 그대로 적용한 것입니다 —
**필드가 있다는 것과 그 값이 검증된다는 것은 별개입니다.**

---

## 파고들었더니 진짜 오탐이 나왔다

`열 누락` 이 이상했습니다. `안내 문구` 열을 지웠는데 `안내=2` 입니다. 문서에 없는 값이
어디서 왔을까요.

```
=== 열 누락 (안내 문구 열 제거) ===
  email     placeholder='이메일 입력'
  password  placeholder='비밀번호 입력'
```

**7B 가 지어냈습니다.** 문서에 '이메일 입력' 이라는 말이 한 글자도 없습니다.

그래서 이 기획서로 **올바른 구현**을 검증해 봤습니다.

```
결과: 전체 10 · 통과 9 · 실패 1

FAIL 입력 안내 문구 확인
     문구가 다름 — '이메일': 기대 '이메일 입력', 화면 '이메일을 입력하세요'
```

**없는 결함을 자신 있게 보고했습니다.** 구현은 완벽하게 기획서를 지켰습니다 —
기획서가 안내 문구를 요구하지 않았으니까요. 경고도 하나 없었습니다.

이게 [13번 노트](13-vlm-fallback.md)의 '없는 결함 7건' 과 같은 종류의 사고입니다.
다만 원인이 다릅니다. 그때는 좌표가 어긋났고, 이번에는 **모델이 요구사항을 발명했습니다.**

---

## 왜 아무것도 이걸 막지 않았나

코드를 따라가면 경로가 하나로 모입니다.

```
_element_table() 이 None           헤더에 '요소 ID' 와 '유형' 이 둘 다 있어야 한다
  -> declared_* 여덟 개가 전부 빈손
  -> _apply_declared_types        : if not declared: return    (조용히)
  -> _apply_declared_placeholders : if not declared: return    (조용히)
  -> structural_warnings          : if declared:  <- 검사 자체를 건너뜀
```

`_apply_declared_*` 는 '표에 적힌 사실로 모델 답을 덮어쓴다' 는 장치입니다. 표가 없으면
할 일이 없으니 반환하는 게 맞습니다. 각각은 옳습니다.

**틀린 것은 그 조용함입니다.** 여덟 개가 동시에 무력해졌다는 사실은 리포트를 읽는
사람에게 반드시 필요한 정보인데, 어디에도 남지 않았습니다.

그리고 `열 누락` 은 더 미묘합니다. 표는 찾았고 다른 열은 다 읽었습니다. 다만 한 열이
없어서 그 열에 대한 검증만 사라졌고, 그 자리를 모델의 상상이 채웠습니다.

---

## 고친 방법 1 — 기획서 본문에 없는 문구는 요구사항이 아니다

첫 생각은 '표에서 읽은 값만 신뢰한다' 였습니다. 그런데 그러면 **산문으로 쓴 기획서에서
검증이 사라집니다.** 그리고 실측에서 7B 는 산문에 적힌 안내 문구를 정확히 읽어냈습니다 —
버릴 이유가 없는 정보입니다.

더 나은 기준이 있었습니다. **그 문자열이 문서 본문에 있는가.**

```python
def _drop_invented_strings(spec, doc) -> None:
    text = normalize_ws(doc.to_llm_text())

    def declared_in_document(value: str) -> bool:
        return normalize_ws(value) in text

    for element in spec.elements:
        if element.placeholder and not declared_in_document(element.placeholder):
            spec.warnings.append(f"'{element.label}' 의 안내 문구 ... 버렸습니다")
            element.placeholder = None
        ...
```

표든 산문이든 통합니다. 문서에 그 문자열이 있으면 기획서가 요구한 것이고, 없으면 모델이
만든 것입니다. **추론이 필요하지 않습니다** — 이 프로젝트가 계속 지켜 온 방식입니다.

### 이 검사가 진짜 요구사항을 지우면 어쩌나

이게 더 위험한 쪽입니다. PDF 는 원문을 그대로 복원하지 못합니다(그것도 이미 겪었습니다).
이 장치가 진짜 요구사항을 조용히 지우면 리포트가 근거 없이 초록불이 됩니다.

그래서 **구현하기 전에** 픽스처 3종의 정답 문구 전체로 재 봤습니다.

```
login_spec.pdf   5개  전부 찾아짐
search_spec.pdf  3개  전부 찾아짐
signup_spec.pdf 11개  전부 찾아짐
찾지 못한 값: 0 건
```

19/19 입니다. 공백만 정규화하면 충분했습니다. 그리고 이 성질을 테스트로 못 박았습니다 —
픽스처나 PDF 생성을 바꿀 때 깨지면 거기서 잡힙니다.

### 버린 뒤에는 어떻게 되나

이미 격하 경로가 있었습니다.

```python
if message:
    return Expectation(type="error_message", value=message)
# 문구를 모를 때는 격하한다. 억측한 문구로 오탐을 만드는 것보다,
# '에러가 떴고 이동하지 않았다' 만 확인하는 편이 낫다.
return Expectation(type="error_shown", value="")
```

주석에 제가 필요했던 원칙이 그대로 적혀 있었습니다. 문구를 잃은 위반 케이스는
`error_shown` 으로 떨어집니다 — **검증이 약해지지만 거짓이 되지는 않습니다.**

안내 문구 케이스는 아예 생성되지 않고, 그 사실이 경고로 남습니다.

## 고친 방법 2 — 검증망이 없다는 사실을 말한다

```python
else:
    # 표를 못 찾으면 결정적 독해 여덟 개가 전부 빈손이 되고 ...
    warnings.append(
        "UI 요소 정의 표를 찾지 못했습니다('요소 ID' 와 '유형' 열이 함께 있는 "
        "표를 찾습니다). 표에 적힌 사실로 모델 답을 대조하는 검증이 모두 "
        "비활성화되어, 요소·유형·안내 문구가 검증 없이 쓰입니다."
    )
```

**결과가 맞았을 때도 알려야 합니다.** `열 이름 변경` 실행은 우연히 원본과 같은 답을
냈지만, 틀렸다면 아무것도 잡지 못했습니다. 확인하지 않은 것과 확인해서 통과한 것은
다릅니다.

### 이 수정이 테스트 하나를 깨뜨렸다

```python
def test_대조할_표가_없으면_누락_검사를_하지_않는다(self):
    """ID 열이 없는 기획서에서 없는 누락을 경고하면 안 된다."""
    assert structural_warnings(spec, doc) == []
```

**옛 동작을 옳다고 못 박아 둔 테스트입니다.** 그리고 절반은 여전히 옳습니다 — '요소가
빠졌다' 고 하면 안 됩니다. 빠진 것이 아니라 대조할 근거가 없는 것이고, 둘은 개발자가 할
일이 다릅니다.

그래서 테스트를 둘로 갈랐습니다.

```
test_대조할_표가_없으면_없는_누락을_경고하지_않는다   여전히 성립
test_대조할_표가_없다는_사실은_경고한다              새로 못 박는다
```

테스트가 실패했을 때 **테스트가 틀린 경우**가 있습니다. 그걸 구분하는 근거는 측정입니다 —
이번에는 실물 7B 로 훼손된 문서를 돌려 본 결과가 근거였습니다.

## 2차 측정

```
훼손             표    요소    규칙    안내    경고    판정
원본             O    3     4     2     0     영향 없음
열 이름 변경        X    3     4     2     1     검증망 없음을 경고
열 누락           O    3     4     0     2     지어낸 문구를 버림
산문 서술          X    3     4     2     1     검증망 없음을 경고
셀 병합           O    3     4     2     0     영향 없음
표 이미지화         X    2     4     0     4     경고 4건
절 번호 없음        O    3     4     2     0     영향 없음
```

그리고 같은 훼손 기획서로 올바른 구현을 다시 검증했습니다.

```
전 : 9 PASS / 1 FAIL   <- 없는 결함
후 : 9 PASS / 0 FAIL   + 경고 2건으로 이유를 남김
```

**원본에는 경고가 하나도 늘지 않았습니다.** 그리고 실물 7B 로 기획서 4종 × 구현 2종을
다시 돌려 판정이 전부 그대로임을 확인했습니다 (로그인 10/10·4-6, 회원가입 17/17·13-4,
검색 10/10·6-4, 통합 39/39·23-16). 오탐 0건 유지입니다.

## 뜻밖의 좋은 소식 두 개

**7B 가 산문을 읽습니다.** 표를 없애고 문장으로만 쓴 기획서에서 요소 3개와 규칙 4개를
정확히 뽑아냈습니다. 안내 문구도 맞혔습니다. 실물 기획서가 표를 안 쓰더라도 완전히
못 쓰는 상황은 아닙니다.

**셀 병합과 절 번호는 영향이 없습니다.** 두 훼손은 결정적 독해가 그대로 동작했습니다.
절 탐색이 번호에 의존하지 않게 만들어 둔 것이 여기서 값을 했습니다.

깨지는 것은 **표 자체를 못 찾을 때** 하나입니다. 그리고 이제 그 사실이 리포트에
드러납니다.

## 이 노트에서 남길 것

1. **모든 성공 문장에는 조건이 숨어 있다.** '오탐 0건' 은 '우리가 만든 기획서에서는'
   이었습니다. 그 조건을 찾아 명시하는 것이 다음 작업을 정합니다.
2. **자기가 만든 입력으로만 시험하면 도구가 아니라 짝을 만든 것이다.** 픽스처를 실물에
   가깝게 만드는 것 자체가 검증입니다.
3. **'깨지는가' 가 아니라 '어떻게 깨지는가' 를 재라.** 시끄럽게 깨지는 도구는 쓸 수
   있고, 조용히 깨지는 도구는 해롭습니다.
4. **측정 도구의 판정 기준도 틀릴 수 있다.** 제 1차 판정은 '데이터를 잃었는가' 를 봤고
   '검증을 잃었는가' 를 놓쳤습니다. 결과가 우연히 맞으면 통과로 보입니다.
5. **모델은 값을 지어낸다 — 그리고 그게 요구사항이 된다.** 기획서에 없는 안내 문구를
   만들어내면 도구가 그것으로 올바른 구현을 FAIL 로 보고합니다. LLM 이 무엇을 못 읽는지
   보다 **무엇을 만들어내는지**가 더 위험합니다.
6. **'문서에 그 문자열이 있는가' 는 강력하고 값싼 기준이다.** 표든 산문이든 통하고,
   추론이 필요하지 않고, 정규식 하나도 쓰지 않습니다.
7. **지우는 장치를 만들 때는 지우면 안 되는 것부터 재라.** 정답 문구 19개가 전부 본문에서
   찾아지는 것을 구현 **전에** 확인했습니다. 순서가 반대면 조용한 검증 상실을 만듭니다.
8. **검증이 약해지는 것과 거짓이 되는 것은 다르다.** 문구를 모를 때 `error_shown` 으로
   격하하면 확인 범위가 줄지만 결론은 참입니다. 억측한 문구로 대조하면 결론이 거짓입니다.
9. **테스트가 실패할 때 테스트가 틀린 경우가 있다.** 옛 동작을 옳다고 못 박은 테스트를
   고쳤습니다. 그 판단의 근거는 측정이어야 합니다 — 느낌이면 안 됩니다.
10. **결과가 맞았을 때도 검증망이 없다는 사실은 알려야 한다.** 우연히 맞은 실행과 확인해서
   맞은 실행은 다릅니다. 리포트가 그 차이를 말하지 않으면 사람이 구분할 방법이 없습니다.
