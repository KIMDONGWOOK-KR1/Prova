## 이 변경이 답하는 질문

지금까지 S3 는 접근성 속성으로 요소를 찾았습니다. 전략이 네 개입니다.

```
1. get_by_label("이메일")           <label for=...> 연결
2. get_by_role("button", "로그인")   버튼의 접근 가능한 이름
3. placeholder 대조
4. element_id 로 CSS selector
```

`good` 에서는 전부 통합니다. 그런데 **실물 화면은 이렇게 친절하지 않습니다.**

```html
<!-- 기획서: 요소 '검색' -->
<button type="submit">🔍</button>
```

아이콘만 있는 제출 버튼입니다. 접근 가능한 이름이 없고 라벨도 placeholder 도 없습니다.
네 전략이 모두 막힙니다. 검색 버튼, 닫기 버튼, 아이콘 툴바가 대개 이렇습니다.

시험용으로 `sut/` 에 **`nolabel` 변형**을 만들었습니다. 검증 로직은 `good` 과 **완전히
같고** 제출 버튼 마크업만 다릅니다. 그래야 "보정이 되면 판정이 `good` 과 같아져야 한다"
는 기준을 세울 수 있습니다.

```
2차 경로 끔    1 PASS / 9 FAIL   전부 element_not_found
2차 경로 켬    9 PASS / 1 FAIL   보정 8건
```

## ⚠️ 리뷰에서 반드시 봐 주셔야 하는 것 — 없는 결함 7건

이 경로에는 **다른 기능에 없는 위험**이 있습니다. 실제로 사고를 냈습니다.

MockVLM 에 좌표를 손으로 어림잡아 넣고 돌렸습니다. 테스트가 통과했습니다 (`healed > 0`
이었으니까). 그런데 리포트를 열어 보니 **FAIL 이 7건** 있었습니다. 결함이 하나도 없는
화면인데요.

```
1. 어림잡은 좌표가 버튼을 살짝 비켜 갔다 (폼 안 빈 여백)
2. Playwright 의 mouse.click(x, y) 는 거기에 아무것도 없어도 조용히 성공한다
3. 폼이 제출되지 않았다
4. 에러 문구도 결과도 나오지 않았다
5. S5 는 그것을 "기획서가 지정한 에러가 안 뜬다" 로 읽었다
6. 리포트: 구현 결함 7건
```

**이게 이 도구가 낼 수 있는 최악의 리포트입니다.** 개발자가 없는 버그를 일곱 개 찾습니다.
그리고 못 찾습니다 — 없으니까요. 그다음에는 도구를 믿지 않게 됩니다.

`fill()` 은 그래도 낫습니다 — 입력란이 아닌 곳에 타이핑하면 Playwright 가 에러를 냅니다.
치명적인 건 `click()` 입니다. **좌표 클릭은 빈 공간을 눌러도 성공합니다.**

### 방어 1 — 누르기 전에 그 자리를 본다

```python
hit = ctx.page.evaluate("""([x, y, sel]) => {
    const el = document.elementFromPoint(x, y);
    if (!el) return null;
    return el.closest(sel) ? el.tagName.toLowerCase() : "";
}""", [x, y, selector])

if not hit:
    raise GroundingError(location.target, [Attempt(
        strategy=f"vlm-좌표({round(x)},{round(y)})에 조작 가능한 요소 없음", count=0)])
```

`closest()` 를 쓰는 이유: VLM 이 버튼 안의 `<svg>` 나 `<span>` 을 가리키는 것이
정상입니다. 조상에 버튼이 있으면 누를 수 있습니다.

없으면 **누르지 않고 탐지 실패로 되돌립니다.** 살릴 수 없는 것을 살린 척하면 그 뒤의
판정이 전부 거짓이 됩니다.

> `element_not_found` = "도구를 고쳐라" · `assertion_mismatch` = "구현을 고쳐라"
> **개발자가 할 일이 다릅니다.** 확신할 수 없으면 탐지 실패로 두는 쪽이 옳습니다.

### 방어 2 — `healed` 의 뜻을 고쳤다

```python
# 전
healed=any(r.location.healed for r in step_results)
# 후
healed=any(r.location.healed for r in step_results
           if r.location and r.status == "ok")
```

시도만 하고 막힌 것을 healed 로 세면, 리포트가 "이미지로 찾아 진행했다" 고 말하는데
실제로는 아무것도 진행되지 않은 상태가 됩니다.

### 방어 3 — 수용 기준을 바꿨다 (원인은 코드가 아니라 테스트였습니다)

```python
def test_기능_검증이_good과_같아진다(self, report_on):
    failed = [v for v in report_on.cases if v.verdict == "FAIL"]
    assert len(failed) == 1              # 라벨 탐지 케이스 하나만
    assert "-labels-" in failed[0].case_id
```

`nolabel` 은 검증 로직이 `good` 과 같으므로, 보정이 제대로 되면 판정도 같아야 합니다.
**이 기준이 있으면 좌표가 어긋난 순간 테스트가 터집니다.** 그리고 어긋난 좌표를
일부러 넣는 `TestWrongCoordinates` 를 따로 뒀습니다.

테스트도 좌표를 손으로 적지 않고 Playwright 로 **실측**합니다.

## 보정이 결함을 메우지 못하게 했습니다

보정을 켜면 케이스가 통과합니다. 여기에 함정이 있습니다.

**'기획서의 라벨로 요소를 지목할 수 없다' 는 것 자체가 결함입니다.** 기획-구현 불일치이면서
접근성 결함입니다 — 스크린리더 사용자는 그 버튼이 무슨 버튼인지 알 수 없습니다.

보정이 그걸 조용히 메워 주면 도구는 결함을 **숨기는 장치**가 됩니다.

그래서 라벨 탐지 자체를 확인하는 케이스(`labels_findable`)를 따로 두고, 그 케이스는
**보정을 쓰지 않습니다.** 리포트에도 '화면 이미지로 찾아 진행한 케이스' 구획을 둬서
통과율만 보는 사람도 그 PASS 가 어떻게 나온 것인지 알 수 있게 했습니다.

## 모델의 역할을 최대한 좁혔습니다

```python
class VLMClient(Protocol):
    def locate(self, *, image_png: bytes, target: str, hint: str) -> Located: ...
```

*이 이미지에서 이 이름의 요소가 어디 있는가.* 그 하나만 묻습니다. **판정은 여전히 S5 의
결정적 규칙이 합니다.** 경계를 지키면 모델이 틀리는 방식이 "좌표가 어긋난다" 하나로
제한되고, 그 하나는 검사할 수 있습니다.

그럴듯한 오답을 거르는 관문이 셋입니다.

| 관문 | 거르는 것 |
|---|---|
| `confidence < 0.5` | 모델이 스스로 자신 없다고 한 답 |
| `is_sane()` | 0~1 범위 밖, 크기 0, 뒤집힌 좌표(x2 < x1) |
| `_require_actionable` | 그 자리에 조작 가능한 요소가 없는 좌표 |

세 번째가 앞의 둘을 통과한 오답을 잡습니다 — 좌표가 범위 안이고 모델도 자신 있는데 그냥
틀린 경우이고, 실제로 그게 가장 위험합니다.

케이스당 보정 상한도 뒀습니다(`max_heal = 2`). 모든 스텝이 보정되면 그 케이스는 '화면을
확인한 것' 이 아니라 '이미지로 조작한 것' 입니다.

## mock 초록불이 증명하지 않는 것

증명하는 것은 **배관**입니다 — 탐지 실패 → 스크린샷 → 좌표 → 클릭 → 판정이 이어지는지.

증명하지 않는 것은 **정확도**입니다. MockVLM 은 CSS selector 로 정답을 실측합니다
('완벽한 VLM' 시뮬레이션). 이 구분을 흐리면 mock 초록불을 보고 "2차가 동작한다" 고 말하게
됩니다. 그래서 두 테스트 파일의 문서 문자열에 못 박아 뒀습니다.
