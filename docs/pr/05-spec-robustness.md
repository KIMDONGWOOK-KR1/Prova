## 재는 것은 '깨지는가' 가 아니라 '어떻게 깨지는가'

이 구분이 이 커밋의 핵심입니다.

```

시끄러운 실패  경고를 남기거나 예외로 끊는다                 <- 쓸 수 있다
```

**이 도구의 가치는 전부 후자로 만드는 데 있습니다.**

[`scripts/probe_s1_robustness.py`](../../scripts/probe_s1_robustness.py) 가 기획서를
일부러 훼손합니다. 6종이고 **하나씩만** 적용합니다 — 둘을 겹치면 어느 것이 원인인지
분리되지 않습니다(negative 케이스가 규칙을 하나씩만 위반하는 것과 같은 이유).

그리고 **mock LLM 을 쓰지 않습니다.** mock 은 PDF 를 읽지 않고 정답을 돌려주므로 훼손된
문서에서도 같은 답을 냅니다 — 측정이 아예 성립하지 않습니다.

## 찾은 것 1 — 도구가 요구사항을 발명하고 있었다

`안내 문구` 열을 지운 문서에서 7B 가 값을 지어냈습니다.

```
email     placeholder='이메일 입력'        <- 문서에 이런 말이 없다
password  placeholder='비밀번호 입력'      <- 없다
```

그 기획서로 **올바른 구현**을 검증하니:

```
결과: 전체 10 · 통과 9 · 실패 1

FAIL 입력 안내 문구 확인
     문구가 다름 — '이메일': 기대 '이메일 입력', 화면 '이메일을 입력하세요'
```

**없는 결함을 자신 있게, 경고 하나 없이 보고했습니다.** 구현은 완벽합니다 — 기획서가
안내 문구를 요구하지 않았으니까요.

`048cc0e` 의 '없는 결함 7건' 과 같은 종류의 사고인데 원인이 다릅니다. 그때는 좌표가
어긋났고, 이번에는 **모델이 요구사항을 발명했습니다.**

## 찾은 것 2 — 검증망이 사라진 사실이 어디에도 남지 않는다

```
_element_table() 이 None          헤더에 '요소 ID' 와 '유형' 이 둘 다 있어야 한다
  -> declared_* 여덟 개가 전부 빈손
  -> _apply_declared_types        : if not declared: return    (조용히)
  -> _apply_declared_placeholders : if not declared: return    (조용히)
  -> structural_warnings          : if declared:  <- 검사 자체를 건너뜀
```

**열 이름을 `요소 ID` → `항목` 으로 바꾸는 것 하나로 이 상태가 됩니다.**

`_apply_declared_*` 는 '표에 적힌 사실로 모델 답을 덮어쓴다' 는 장치입니다. 표가 없으면
할 일이 없으니 반환하는 게 맞습니다. **각각은 옳습니다. 틀린 것은 그 조용함입니다.**

그 실행은 우연히 원본과 같은 답을 냈습니다. 틀렸다면 아무것도 잡지 못했습니다.

## 고친 방법 1 — 기획서 본문에 없는 문구는 요구사항이 아니다

첫 생각은 '표에서 읽은 값만 신뢰한다' 였습니다. **그런데 그러면 산문으로 쓴 기획서에서
검증이 사라집니다.** 그리고 실측에서 7B 는 산문에 적힌 안내 문구를 정확히 읽어냈습니다 —
버릴 이유가 없는 정보입니다.

더 나은 기준이 있었습니다 — **그 문자열이 문서 본문에 있는가.**

```python
def _drop_invented_strings(spec, doc) -> None:
    text = normalize_ws(doc.to_llm_text())

    def declared_in_document(value: str) -> bool:
        return normalize_ws(value) in text
    ...
```

표든 산문이든 통합니다. 문서에 그 문자열이 있으면 기획서가 요구한 것이고, 없으면 모델이
만든 것입니다. **추론이 필요하지 않습니다** — 이 프로젝트가 계속 지켜 온 방식입니다.

### ⚠️ 리뷰에서 봐 주셔야 하는 것 — 이 검사가 진짜 요구사항을 지우면?

**이쪽이 더 위험합니다.** PDF 는 원문을 그대로 복원하지 못합니다(그것도 이미 겪었습니다).
이 장치가 진짜 요구사항을 조용히 지우면 리포트가 근거 없이 초록불이 됩니다.

그래서 **구현하기 전에** 픽스처 3종의 정답 문구 전체로 재 봤습니다.

```
login_spec.pdf   5개  전부 찾아짐
search_spec.pdf  3개  전부 찾아짐
signup_spec.pdf 11개  전부 찾아짐
찾지 못한 값: 0 건
```

공백만 정규화하면 충분했습니다. 그리고 그 성질을 파라미터화 테스트로 못 박았습니다 —
픽스처나 PDF 생성을 바꿀 때 깨지면 거기서 잡힙니다.

> **지우는 장치를 만들 때는 지우면 안 되는 것부터 재라.** 순서가 반대면 조용한 검증
> 상실을 만듭니다.

### 버린 뒤에는 어떻게 되나 — 이미 격하 경로가 있었습니다

```python
if message:
    return Expectation(type="error_message", value=message)
# 문구를 모를 때는 격하한다. 억측한 문구로 오탐을 만드는 것보다,
# '에러가 떴고 이동하지 않았다' 만 확인하는 편이 낫다.
return Expectation(type="error_shown", value="")
```

주석에 필요한 원칙이 그대로 적혀 있었습니다.

> **검증이 약해지는 것과 거짓이 되는 것은 다르다.**

## 고친 방법 2 — 검증망이 없다는 사실을 말한다

```python
else:
    warnings.append(
        "UI 요소 정의 표를 찾지 못했습니다('요소 ID' 와 '유형' 열이 함께 있는 "
        "표를 찾습니다). 표에 적힌 사실로 모델 답을 대조하는 검증이 모두 "
        "비활성화되어, 요소·유형·안내 문구가 검증 없이 쓰입니다."
    )
```

**결과가 맞았을 때도 알려야 합니다.** 확인하지 않은 것과 확인해서 통과한 것은 다릅니다.

### 이 수정이 테스트 하나를 깨뜨렸습니다 — 그리고 테스트가 틀렸습니다

```python
def test_대조할_표가_없으면_누락_검사를_하지_않는다(self):
    """ID 열이 없는 기획서에서 없는 누락을 경고하면 안 된다."""
    assert structural_warnings(spec, doc) == []
```

**옛 동작을 옳다고 못 박아 둔 테스트입니다.** 그리고 절반은 여전히 옳습니다 — '요소가
빠졌다' 고 하면 안 됩니다. 빠진 것이 아니라 대조할 근거가 없는 것이고, 둘은 개발자가 할
일이 다릅니다. 그래서 테스트를 둘로 갈랐습니다.

```
test_대조할_표가_없으면_없는_누락을_경고하지_않는다   여전히 성립
test_대조할_표가_없다는_사실은_경고한다              새로 못 박는다
```

> **테스트가 실패할 때 테스트가 틀린 경우가 있다.** 그 판단의 근거는 측정이어야 합니다 —
> 느낌이면 안 됩니다.

## 뜻밖의 좋은 소식 둘

**7B 가 산문을 읽습니다.** 표를 없애고 문장으로만 쓴 기획서에서 요소 3개와 규칙 4개를
정확히 뽑아냈고 안내 문구도 맞혔습니다. 실물 기획서가 표를 안 쓰더라도 완전히 못 쓰는
상황은 아닙니다.

**셀 병합과 절 번호는 영향이 없습니다.** 절 탐색이 번호에 의존하지 않게 만들어 둔 것이
여기서 값을 했습니다.

**깨지는 것은 표 자체를 못 찾을 때 하나**이고, 이제 그 사실이 리포트에 드러납니다.
