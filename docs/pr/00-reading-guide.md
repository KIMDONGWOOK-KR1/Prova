## 한 시간 있다면 — 파이프라인을 따라가세요

6단계이고 각각 디렉터리 하나입니다. **각 노드는 `(state) -> state` 함수 하나**입니다.

```
<화면>_spec.pdf
   │
   S1  spec_extractor    PDF -> SpecDocument (화면들 + 화면 사이 흐름)
   │
   S2  case_generator    TestCase[]  (한 케이스가 한 규칙만 위반한다)
   │
   S3  grounder          기획서의 라벨로 화면의 요소를 찾는다
   S4  executor          Playwright 로 조작한다
   S5  verifier          결정적 규칙으로 판정한다 (LLM 을 쓰지 않는다)
   │
   S6  report            report.html
```

읽는 순서:

1. **[`src/prova/models.py`](../../src/prova/models.py)** — 계약
2. **[`src/prova/s1_spec_extractor/pdf_parser.py`](../../src/prova/s1_spec_extractor/pdf_parser.py)** —
   PDF 에서 표를 읽는 코드. **LLM 을 전혀 쓰지 않습니다.** 이 프로젝트에서 가장 값진
   교훈이 여기 있습니다(아래 참고)
3. **[`src/prova/s2_case_generator/rule_expander.py`](../../src/prova/s2_case_generator/rule_expander.py)** —
   '대문자 1자 이상' 규칙에서 '대문자가 없는 값' 을 만드는 순수 함수
4. **[`src/prova/s5_verifier/assertion_engine.py`](../../src/prova/s5_verifier/assertion_engine.py)** —
   판정. 여기에 LLM 이 없는 것이 이 도구의 신뢰 근거입니다
5. **[`src/prova/nodes.py`](../../src/prova/nodes.py)** — 위를 잇는 배선

## 리뷰할 때 봐 주면 좋은 것

코드 스타일보다 **판단**을 봐 주세요. 특히 이 셋입니다.

### 1. LLM 에 무엇을 맡기고 무엇을 안 맡기는가

이 PR 에서 가장 값진 교훈입니다.

> **표에 그대로 적힌 사실은 LLM 에 맡기지 않는다.**

7B 가 기획서 표의 행을 조용히 빠뜨리고, few-shot 예시의 문구를 복사하고, 없는
`screen_id` 를 만들어냈습니다. 그 결과가 리포트에서는 **'전 케이스 실패'** 로 보이는데
원인은 구현이 아니라 추출입니다.

그래서 표에서 읽을 수 있는 것은 전부 결정적 함수로 읽습니다 —
`declared_element_ids`, `declared_element_types`, `declared_screen_meta`,
`declared_sample_values`, `declared_scenarios`, `declared_placeholders`,
`declared_required_message`, `declared_flows` 여덟 개입니다.

공통 원칙: **확신할 수 있을 때만 답한다.** 애매하면 `None`/빈 값을 돌려주고 LLM 의 답을
그대로 둡니다 — 틀린 확신이 침묵보다 나쁩니다.

### 2. 확인하지 않은 것을 어떻게 다루는가

이 도구가 낼 수 있는 **가장 위험한 리포트는 FAIL 이 아닙니다.**

> "33/33 통과" 인데 실은 기획서의 일부를 확인하지 않은 리포트

FAIL 은 눈에 띄지만 '확인하지 않음' 은 아무 흔적도 남기지 않습니다. 그래서 기획서가 적어
둔 문구를 모두 모아, 어떤 케이스의 기대값에도 들어가지 않는 것을 리포트에 항목으로
씁니다(`s2_case_generator/coverage.py`).

그 검출기가 **가장 처음 만든 로그인 화면**에서 구멍을 찾았습니다.

### 3. 없는 결함을 보고하지 않는가

놓친 결함은 도구의 한계로 남지만, **없는 결함은 개발자의 시간을 쓰고 도구의 신뢰를
없앱니다.** 이 PR 에서 그런 사고를 **세 번** 겪었고 셋 다 코드에 방어가 남아 있습니다.

| 원인 | 결과 |
|---|---|
| 2차 경로의 좌표가 버튼을 비켜 갔다 | 없는 결함 7건 |
| 모델이 기획서에 없는 안내 문구를 발명했다 | 없는 결함 1건 |
| 도구가 비동기 렌더를 기다리지 않았다 | 없는 결함 7건 |

원인은 매번 다른데 **모양이 같습니다** — 도구가 확인하지 못한 것을 구현 결함으로
보고하고, 사유 문구가 매번 자신 있습니다. 그 모양을 알아 두면 다음 것을 더 빨리 봅니다.
